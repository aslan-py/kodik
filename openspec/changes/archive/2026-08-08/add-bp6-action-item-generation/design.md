## Context

См. proposal.md — Why. Решения по объёму (одна задача = одна строка, только П1/П2, отдел без исполнителя, не трогать уже сгенерированное) уже согласованы с пользователем — здесь фиксируется техническая реализация вокруг них.

`ActionItem.showcase_event_id` — FK на `showcase_event`, не на `categorized_event`: значит перенос физически возможен только ПОСЛЕ BP-4 (когда строка витрины уже существует), не сразу в BP-3. `showcase_event.categorized_event_id` (`unique=True`) даёт путь назад к `categorized_event.task`/`expected_result`/`department_id`.

## Goals / Non-Goals

**Goals:**
- Рабочий `run_bp6()`, встающий в реестр пайплайна вместо заглушки этапа 6.
- Идемпотентность через watermark-поле, по аналогии с `showcase_event.alerted_at` (BP-5) и `categorized_at > updated_at` (BP-4).

**Non-Goals:**
- Не переоткрываем вопрос про перекатегоризацию — уже решено (п.3 согласованных решений): изменившиеся задачи не переносятся повторно в этой версии.
- Не трогаем ручное создание `action_item` через `api/crud/action_items.py` — оно продолжает работать как есть, автогенерация — дополнительный источник строк, не замена.
- Не решаем судьбу `src/bp5/ai_assistant.py` (личная заглушка) в рамках этого change — отдельный вопрос.

## Decisions

**Watermark на `showcase_event`, не на `categorized_event`.** Критерий отбора — по аналогии с `alerted_at`/`categorized_at`: новая колонка (например, `action_items_generated_at`, nullable datetime). Отбор: `priority IN ('П1', 'П2') AND action_items_generated_at IS NULL`. Не используем `updated_at > action_items_generated_at` (как у BP-5) — умышленно: п.3 решения говорит НЕ перегенерировать при изменении задач, значит `IS NULL` как единственное условие, без реакции на `updated_at`.

**Почему не критерий "нет строк в action_item".** Тот же довод, что уже разбирался для BP-3 (`NOT EXISTS categorized_event`) и явно ОТВЕРГНУТ для BP-5 (`README` BP-5, «Почему не по журналу alert»): событие могло быть честно обработано и дать НОЛЬ строк (пустой `task[]`) — тогда `NOT EXISTS action_item` не отличит «ещё не проверено» от «проверено, задач не было», и такое событие проверялось бы заново на каждом прогоне. Watermark на `showcase_event` решает это так же, как в BP-4/BP-5.

**Резолв `department_id`.** `categorized_event.department_id` уже resolved (BP-3 сам резолвит имя отдела из LLM в id через `ActionPlanningModule`/`dep_name_to_id`, см. `save_results_module.py`) — просто копируем `categorized_event.department_id` в `action_item.department_id`, никакого повторного лукапа по имени не нужно.

**Своя сессия vs встраивание в BP-4/BP-5.** `run_bp6()` — самостоятельный прогон со своей сессией и commit, как у остальных этапов (`run_bp2`/`run_bp4`/`run_bp5`), а не довесок к BP-4 или BP-5. Обоснование: BP-6 логически независим (свой номер этапа, свой preflight на `ShowcaseEvent` в реестре — уже есть), встраивание в чужой модуль создало бы неявную связь и усложнило бы `is_stub` переключение только для одного этапа.

## Risks / Trade-offs

- [Риск] Если у события `task[]` пуст (LLM не сформировала задач), watermark всё равно проставляется, и `action_item` не создаётся вообще — это ожидаемо (см. Non-goals BP-3-спеки: «сохранение не завершается ошибкой»), но стоит явно вернуть в сводке `run_bp6()`, сколько событий обработано vs сколько строк реально создано, чтобы не выглядело как «ничего не сработало».
- [Риск] Новая колонка на `showcase_event` — тот же класс проблемы, что уже описан в `BP4_README.md`/`BP5_README.md` («Если в витрину добавили колонку») — старые строки при миграции получат `NULL`, что здесь и есть штатное «ещё не обработано», поэтому разового пересбора витрины в этом случае НЕ требуется (в отличие от миграций, где `NULL` означало бы потерянные данные).
