## Why

При реальном сборе (`TRUE_PARSING=True`) HTML-снимок страницы теряется: в БД `raw_item.html_file_path` заполнен, а физический файл на диске — 0 байт. Обнаружено при ручной проверке `connect-real-bp1-parsing` на реальном источнике (`ptsecurity.com`).

Причина — конфликт двух модулей, работающих с одним и тем же файлом:

- `src/bp1/adaptive/processing/parser.py::_save_html()` сохраняет HTML **сразу в целевую папку** (`settings.bp1_html_dir`) — так и задумано, докстринг прямо говорит «не во временную папку, как специализированные RPA-адаптеры»;
- `src/bp1/storage.py::copy_html_file()` вызывается после этого и пытается скопировать файл **в ту же самую папку** — источник и назначение оказываются одним и тем же путём.

На Windows `shutil.copy2` в этой ситуации не ловится ожидаемым `SameFileError` (для которого в коде есть отдельная ветка), а падает с `PermissionError` (`WinError 32`, файл занят). После трёх неудачных попыток включается ручной fallback:

```python
with (
    open(parser_file_path, 'rb') as f_in,
    open(dest_path, 'wb') as f_out,   # тот же файл — 'wb' обнуляет его при открытии
):
    shutil.copyfileobj(f_in, f_out)   # читаем уже пустой файл → пишем 0 байт
```

`open(dest_path, 'wb')` обрезает файл до нуля в момент открытия. Поскольку `dest_path` и `parser_file_path` — один и тот же файл, чтение через `f_in` тоже видит уже обнулённое содержимое. Результат — гарантированная потеря снимка при каждом реальном сборе на Windows, при этом БД молча показывает, что файл сохранён.

Drill-down до исходного HTML — прямое требование прозрачности из ТЗ (см. комментарий `NormalizedItem.raw_item_id` в `src/bp2/models.py`); сейчас оно тихо не выполняется для адаптивного сбора.

## What Changes

- `src/bp1/storage.py::copy_html_file()` — при совпадении источника и назначения (после разрешения в абсолютные пути) копирование пропускается, функция сразу возвращает путь без обращения к `shutil.copy2`/fallback. Это тот же исход, что и сегодняшняя ветка `SameFileError`, только гарантированно достижимый, а не зависящий от того, поймает ли ОС эту ситуацию как `SameFileError` или как `PermissionError`.
- Ручной fallback (шаг 2, чтение+запись) получает ту же проверку — на случай, если совпадение путей обнаружится не на первом шаге.
- Регрессионный тест: `copy_html_file(path, dest_dir)`, где `path` уже лежит в `dest_dir` с тем же именем, не должен изменять содержимое файла.

## Capabilities

### Modified Capabilities
- `bp1/adaptive-collection-run`: снимок HTML сохраняется корректно при реальном сборе, а не обнуляется совпадением путей источника/назначения.

Требует `connect-real-bp1-parsing` заархивированным (капабилити `bp1/adaptive-collection-run` появляется в основных спеках только после архивации) — до этого delta-спек ссылается на ещё не существующий main spec.

## Impact

- Код: `src/bp1/storage.py::copy_html_file()`.
- Данные: не восстанавливает уже потерянные (обнулённые) HTML-файлы — только останавливает потерю новых. Существующие `raw_item` с пустыми файлами по `html_file_path` остаются как есть (путь в БД валиден, файла с содержимым нет).
- Тесты: новый регрессионный тест на `copy_html_file` с совпадающими путями.
- Не входит: восстановление уже потерянных снимков, изменение `_save_html()` (её текущее поведение — сохранять сразу в целевую папку — само по себе не проблема, проблема в повторном копировании поверх).
