## Context

См. proposal.md — Why. Здесь только то, что определяет форму решения.

Что зашито в код на момент планирования:

```
src/bp3/modules/source_finder_module.py  (вызов поиска источников)
    max_results=2          сколько источников за запрос
    search_depth='basic'   глубина поиска — фиксированный набор значений
    time_range='week'      окно поиска
    topic='news'           тип запроса

src/bp3/config.py  (клиент LLM)
    API_BASE = 'https://openrouter.ai/api/v1'   # + закомментированная альтернатива
    temperature=0
    max_tokens=4096
```

`settings.bp3_model` и `settings.openrouter_api_key` уже вынесены — блок BP-3 в `core/config.py` существует, новые поля дополняют его, а не заводят новый.

## Goals / Non-Goals

**Goals:**
- Стоимостью и глубиной прогона BP-3 можно управлять из конфигурации.
- Значение с фиксированным набором вариантов проверяется до обращения к внешнему сервису.

**Non-Goals:**
- Не меняем поведение по умолчанию: все значения по умолчанию равны текущим литералам.
- Не трогаем промпты и логику модулей BP-3 — только параметры вызовов.
- Не выносим `topic='news'`: это не эксплуатационная ручка, а тип запроса, определяемый назначением модуля (см. Decisions).

## Decisions

**`search_depth` становится перечислением в `core/enums.py`, а не строковой настройкой.** Значение допускает фиксированный набор вариантов, и проект уже описывает такие наборы перечислениями (`LimitWindow`, `DeliveryMode`, `PriorityLevel` и остальные — все `enum.StrEnum`). Поле `Settings` типизируется этим перечислением, поэтому pydantic отвергает опечатку при старте. _Альтернатива —_ оставить строкой: отвергнута, ошибка тогда всплывает ответом внешнего сервиса посреди прогона, уже после того как часть новостей обработана и токены потрачены.

**`time_range` тоже выносим, но обычной строкой.** Формально у него тоже ограниченный набор значений, но, в отличие от глубины поиска, он расширяемый и завязан на API внешнего сервиса. Заводить под него перечисление — значит обязаться его сопровождать при каждом изменении на стороне сервиса.

**`topic='news'` не выносим.** Это не настройка, а суть вызова: модуль ищет именно новостные источники, и смена типа запроса означала бы другую задачу модуля, а не другую его настройку. Тот же критерий, что в `centralize-parsing-settings`: выносим то, что крутят при эксплуатации, а не то, что определяет назначение кода.

**`API_BASE` становится настройкой, а закомментированная альтернатива удаляется.** Комментарий с вторым адресом рядом с константой — это переключатель, реализованный копипастой. После выноса в настройку он не нужен: оба адреса просто становятся возможными значениями переменной. Второй адрес стоит упомянуть в пояснении к переменной в `.env.example`, чтобы знание о нём не потерялось.

**Ключ и адрес API остаются раздельными полями и не сводятся с LLM-доступами BP-1/BP-6.** У проекта три независимых набора доступов к моделям (`openrouter_api_key` для BP-3, `deepseek_token` для BP-6, `LLM_API_KEY` для BP-1). Провайдеры разные, и объединение — отдельное решение с последствиями для всех трёх этапов, не для этой задачи.

## Risks / Trade-offs

- [Риск] **Увеличение глубины или объёма поиска напрямую увеличивает расход по внешним сервисам.** Настройка делает это лёгким действием — в том числе случайным. → Митигация: в пояснении к переменным в `.env.example` явно указать, что параметры влияют на стоимость прогона; значения по умолчанию оставить консервативными (текущими).
- [Риск] **Перечисление глубины поиска может разойтись с набором значений внешнего сервиса**, если тот добавит или переименует вариант. → Митигация: набор маленький и меняется редко; расхождение проявится ошибкой сервиса с понятным текстом, а неверное значение всё равно не пройдёт валидацию при старте.
- [Компромисс] **Часть параметров вызова остаётся в коде** (`topic`, состав полей ответа: `include_answer`, `include_raw_content`). Это осознанно: они определяют, что модуль делает, а не как он настроен под площадку.
