# BP-4: Витрина данных под BI

BP-4 схлопывает два слоя в один: ФАКТЫ из `normalized_item` (BP-2) и СМЫСЛЫ
из `categorized_event` (BP-3). На выходе — плоская таблица `showcase_event`,
где вместо id стоят читаемые имена, а вместо кодов enum'а — готовые подписи.
BI-система (DataLens) подключается к ней напрямую и читает **без единого джойна**.

Новых справочников BP-4 не заводит и данные не сочиняет: он только
перекладывает уже готовое и подставляет имена из `region`, `competitor`,
`category`, `department`.

---

## Контракт витрины `showcase_event`

Это ровно строка целевого xlsx-отчёта. **Набор колонок — контракт с BI-слоем:**
переименование или удаление колонки ломает дашборды, такие изменения
согласуются с аналитиком.

| Поле | Тип | Откуда берётся | Описание |
|------|-----|----------------|----------|
| `id` | int | БД | Первичный ключ строки витрины |
| `categorized_event_id` | int | `categorized_event.id` | Ключ UPSERT: одна строка витрины на размеченное событие. `UNIQUE` |
| `raw_item_id` | int | `normalized_item.raw_item_id` | Drill-down до исходного снимка — из любой строки витрины можно дойти до сырья |
| `published_at` | date | `normalized_item.published_at` | Дата события |
| `title` | string | `normalized_item.title` | Заголовок |
| `media` | string | `normalized_item.media_name` | СМИ-публикатор: `Big-news.ru, Москва` |
| `region` | string | `region.name_display` | Регион: `Калуга`. `NULL`, если не распознан в BP-2 |
| `macro_region` | string | `region.macro_region` | Федеральный округ: `ЦФО` — для карты рынка |
| `latitude` | float | `region.latitude` | Широта центра региона (WGS-84) — метка на карте |
| `longitude` | float | `region.longitude` | Долгота центра региона (WGS-84) — метка на карте |
| `competitor` | string | `competitor.name` | Конкурент / объект |
| `source_url` | string | `normalized_item.url` | Ссылка на само событие (не на поисковый запрос парсера) |
| `priority` | string | `categorized_event.priority` | `П1`, `П2`, `П3`, `П4` — подпись, а не код `p1` |
| `category` | string | `category.name` | Категория события |
| `tonality` | string | `categorized_event.tonality` | `позитивная` / `нейтральная` / `негативная` |
| `media_index` | numeric | `categorized_event.media_index` | Медиаиндекс из лицензионного агрегатора. `NULL`, если источника нет |
| `action` | string | `categorized_event.action` | Требуемое действие |
| `deadline` | date | `categorized_event.deadline` | Срок реакции |
| `department` | string | `department.name` | Ответственный отдел |
| `comment` | string | `categorized_event.comment` | Комментарий разметки |
| `updated_at` | datetime | BP-4 | Когда строка последний раз собиралась. По нему определяется устаревание |

**Почему координаты лежат здесь, а не берутся джойном к `region`.** Витрина
денормализована ровно для того, чтобы BI читал одну таблицу. Джойн к `region`
пришлось бы делать по строковому имени (`showcase_event.region` — это текст
`Калуга`, а не id), что хрупко, плюс это второй датасет в DataLens и отдельные
права на служебную таблицу. Правило: **нужно на дашборде — значит, лежит
в витрине.**

**Почему подписи, а не коды.** В `categorized_event` приоритет хранится как
`p1`, тональность как `positive` — это слой хранения. Витрина — слой
представления, она отдаёт значения, готовые к показу, чтобы в BI не пришлось
писать `CASE WHEN`. Маппинги живут в `src/bp4/constants.py` и являются
единственным источником этих подписей на весь проект.

## Как работает прогон

```
select_pending_events  →  build_showcase_row  →  upsert_showcase_events
    (crud.py)               (pipeline.py)            (crud.py)
```

Запуск: `run_bp4()` из `src/bp4/pipeline.py` — открывает свою сессию и коммитит.
Если сборку надо выполнить внутри чужой транзакции (так делает сидер) —
`sync_showcase(session)`.

### Что попадает в витрину

Событие отбирается, если выполнены **все** условия:

1. у него есть разметка (`categorized_event`);
2. его факты имеют `normalized_item.status = 'ok'`;
3. строки в витрине ещё нет **ИЛИ** `categorized_at > showcase_event.updated_at`.

Третий пункт — это инкрементальность. Витрина никогда не перезагружается
целиком (требование ТЗ): вставляются только новые события и обновляются те,
которые BP-3 переразметил после публикации. Если поправить промпт и прогнать
категоризацию заново, изменения доедут до дашборда сами.

Второй пункт не декоративный: антишум BP-2 помечает `rejected` уже
**вставленные** строки, поэтому событие может стать шумом уже после того,
как его разметили. Без этого фильтра шум просочился бы в витрину.

### Что в витрину не попадает

- отсеянные события (`normalized_item.status = 'rejected'`) — любая причина:
  чёрный домен, стоп-слово, антишум, ошибка разбора;
- неразмеченные события — пока BP-3 не создал `categorized_event`, публиковать
  нечего.

## Если в витрину добавили колонку

Инкремент отбирает события по `categorized_at > updated_at`, то есть реагирует
на **переразметку**, а не на изменение схемы. Новая колонка у уже собранных
строк останется `NULL` — прогон BP-4 их просто не заметит.

После миграции, добавляющей колонку, витрину нужно **пересобрать разово**:

```powershell
python -m core.scripts.stages.bp4    # снесёт витрину и соберёт заново
python -m core.scripts.stages.bp5    # каскад унёс алерты — вернуть
python -m core.scripts.stages.bp6    # и задачи
```

На проде то же самое делается через `DELETE FROM showcase_event` (с оглядкой
на `alert` и `action_item`) либо `UPDATE ... SET updated_at = '-infinity'` —
второе аккуратнее, оно помечает строки устаревшими, не удаляя их.

## Индексы

На `showcase_event` стоят индексы по `published_at`, `competitor`, `priority`
и `category` — под типовые фильтры дашборда: лента по датам, паспорт
конкурента, срезы по приоритетам и категориям. На `categorized_event`
проиндексирован `categorized_at` — по нему идёт отбор переразмеченных событий.

## Открытый вопрос к аналитику

**Событие, ставшее шумом после публикации, остаётся в витрине.** Сценарий:
событие попало в витрину, а на следующем прогоне антишум пометил его
`rejected(noise_limit)`. Из витрины оно уже не уйдёт.

Удалить строку нельзя: на `showcase_event` ссылаются `alert` (BP-5) и
`action_item` (BP-6) с `ondelete=RESTRICT` — удаление снесло бы историю
алертов и заведённых задач.

Возможные решения (за рамками BP-4, требуют решения аналитика):

- флаг `is_active` в витрине — строка остаётся, но BI её не показывает;
- перенести антишум так, чтобы он отрабатывал до категоризации, — тогда
  шумное событие вообще не дойдёт до BP-3.

На демо-объёме проблема не проявляется: антишум срабатывает в том же прогоне,
что и нормализация, задолго до BP-4.
