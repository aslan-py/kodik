## Context

См. `proposal.md` — Why/What Changes. Здесь — как именно вставить строку в `user` из Alembic-миграции и почему не так, как заводятся остальные справочные данные в проекте.

Текущий head — `d8be5a20d9b1` (`sync source_candidate domain unique drift`). Новая ревизия становится следующей за ним.

Модель `User` (`src/bp5/models.py`): `email` — `unique`, `password_hash` — bcrypt через `api/security.py::hash_password`/`verify_password`, `role` — enum `UserRole` (`pending`/`viewer`/`analyst`/`admin`), по умолчанию `pending`. `department_id`/`telegram_id` — nullable. `is_active` — из `ActiveMixin`, по умолчанию `true`.

Вход в `/admin` (`api/admin/users.py::UserAdmin.authenticate`) пускает только `role` из `ADMIN_LOGIN_ROLES = (admin, analyst)` и только `is_active=True`.

Существующий прецедент заливки пользователей — `core/scripts/stages/dictionaries.py::seed()` (демо-пользователи из `USERS`, пароль `DEMO_USER_PASSWORD`, роль не указывается → `pending`). Это Python-скрипт поверх ORM-сессии, не Alembic-миграция, и ни один из этих пользователей не годится для входа в админку (роль не `admin`/`analyst`).

## Goals / Non-Goals

**Goals:**
- Ровно один пользователь-администратор существует в базе сразу после `alembic upgrade head`, без ручного шага после.
- Повторное применение (или повторный `upgrade head` на базе, где строка уже есть) не создаёт дублей и не перезаписывает то, что уже могло быть изменено вручную (например, сменённый пароль).

**Non-Goals:**
- Не меняем механизм входа в админку (`UserAdmin.authenticate`) и не трогаем `ADMIN_LOGIN_ROLES`.
- Не добавляем этого пользователя в `core/scripts/stages/dictionaries.py`/`simple_dictionaries.py` — это заливка демо/тестовых данных пайплайна, инфраструктурный админ-бутстрап — отдельная забота.
- Не решаем ротацию/принудительную смену пароля при первом входе — вне рамок этого change.

## Decisions

**Данные заводятся Alembic-миграцией, а не сидер-скриптом.** Явное решение из запроса задачи. Проект до сих пор не заводил данные через миграции (все существующие ревизии — чистый DDL), справочные/демо-данные всегда идут через `core/scripts/stages/*`. Здесь это осознанно нарушается: сидер-скрипты запускаются по явной команде оператора и легко забыть выполнить при разворачивании новой среды, а наличие администратора — предпосылка для входа в систему вообще, поэтому логичнее привязать её к тому шагу разворачивания, который выполняется гарантированно (`alembic upgrade head`). _Альтернатива_ — добавить пользователя в `dictionaries.py`: отклонена, так как та заливка — опциональный шаг демо-наполнения, не гарантированно выполняемый на каждой среде (в т.ч. на будущем проде, где демо-справочники заливать не планируется).

**Вставка — идемпотентный raw SQL (`op.execute`) с `ON CONFLICT (email) DO NOTHING`, не ORM.** Тот же приём, что `_insert()` в `dictionaries.py` использует для справочников с натуральным уникальным ключом — здесь такой ключ есть (`email`). Использовать ORM-модель `User` из миграции нельзя по общему правилу Alembic: модели в коде проекта эволюционируют, а миграция должна остаться воспроизводимой с тем состоянием схемы, что было на момент её написания — поэтому пишем через `sa.table()`/`op.execute`, не импортируя `src.bp5.models.User`.

**Хэш пароля вычисляется в момент выполнения миграции через `api/security.py::hash_password`.** Тот же bcrypt/`passlib`, что и весь остальной логин — не заводим отдельный алгоритм ради миграции. Импорт прикладного кода из миграции — осознанное исключение из правила выше (модели схемы не импортируем, а вот чистую функцию хэширования — можно: она не завязана на состояние схемы и не изменится несовместимо в обозримом будущем).

**`ON CONFLICT DO NOTHING`, а не `DO UPDATE`.** Если строка с этим email уже существует (заведена вручную, пароль уже сменён), миграция не должна тихо переписать чей-то реальный пароль/роль обратно на дефолтные. Совпадает с требованием в specs/core/admin-user-seed — "существующая строка не меняется".

**Downgrade удаляет строку по email, безусловно.** Симметрично upgrade; если к моменту отката администратор с этим email — не тот, что завела миграция (кто-то мог решить оставить себе этот email под другую учётку), это редкий ручной сценарий, не защищаем от него отдельно — таблица `user` и так под контролем администратора БД.

## Risks / Trade-offs

- [Риск] **Пароль `Admin123` в открытом виде в git-истории.** Любой с доступом к репозиторию видит пароль. → Митигация: это предпром/локальный бутстрап-пароль, не итоговый; в проверке (tasks.md) — явный шаг сменить пароль через `/admin` сразу после первого входа на любой среде, где к репозиторию есть посторонний доступ.
- [Риск] **Нарушение сложившейся конвенции "миграции — только DDL".** Следующий разработчик, ищущий, где заводятся данные, ожидает найти это в `core/scripts/stages/`, а не в `alembic/versions/`. → Митигация: развёрнутый комментарий в самой миграции (аналогично `d8be5a20d9b1`) плюс явная пометка в `proposal.md`/этом файле — единственный прецедент, не создающий общий паттерн для будущих данных.
- [Компромисс] **Один захардкоженный администратор на все среды (dev/предпром/будущий прод) с одним и тем же паролем.** Приемлемо для нынешней стадии проекта (по формулировке задачи — нужен рабочий вход прямо сейчас); при появлении реального прод-контура потребуется отдельная политика (переменная окружения для пароля или полный отказ от захардкоженного администратора) — вне рамок этого change.

## Migration Plan

1. Новая ревизия Alembic, `down_revision='d8be5a20d9b1'`.
2. `upgrade()`: raw SQL `INSERT INTO user (...) VALUES (...) ON CONFLICT (email) DO NOTHING`, хэш пароля считается через `api/security.py::hash_password('Admin123')` на этапе выполнения миграции.
3. `downgrade()`: `DELETE FROM user WHERE email = 'admin@admin.ru'`.
4. Применить (`alembic upgrade head`), проверить вход в `/admin`.
