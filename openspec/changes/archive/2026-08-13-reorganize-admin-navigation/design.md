## Context

См. `proposal.md` — Why. Фактический реестр FastAdmin сейчас содержит 22 модели и формирует секции в порядке регистрации: алертинг, валидация, парсинг, данные конвейера, технический пайплайн, пользователи, витрина, план действий. `PipelineControlMarker` нужен как владелец widget actions, но собственных данных не имеет.

FastAdmin 0.10.0 поддерживает у модели только строковый `menu_section`; схема конфигурации не содержит порядка секций, описаний, CSS-классов или признака «не показывать модель в меню». Встроенное название Dashboard берётся из закрытого клиентского bundle как перевод «Панель управления». Правка `venv/site-packages` непереносима и будет потеряна при переустановке зависимостей.

## Goals / Non-Goals

**Goals:**

- сделать новую структуру меню детерминированной и проверяемой независимо от алфавитной сортировки импортов;
- сохранить техническую регистрацию pipeline marker для widget actions, скрыв только его навигационное представление;
- добавить проектное оформление и описания без форка или изменения установленного пакета FastAdmin;
- обеспечить корректную работу при client-side переходах, прямой загрузке URL, смене темы и сворачивании sidebar.

**Non-Goals:**

- переписывать весь FastAdmin frontend или менять библиотеку админки;
- менять модели БД, бизнес-логику этапов, CRUD или права;
- создавать второй уровень вложенности внутри секций;
- превращать описание раздела в длинную пользовательскую документацию.

## Decisions

### 1. Единый реестр информационной архитектуры

В проектном модуле навигации будет задан ordered-набор пяти разделов: стабильный идентификатор, отображаемое имя, короткое описание, зона оформления и список моделей в порядке показа. Тексты не дублируются между Python и JavaScript: конфигурация сериализуется в custom index HTML как `window.KODIK_ADMIN_UI`.

Целевой порядок моделей:

1. скрытый `PipelineControlMarker` — первым для формирования dashboard widgets;
2. parsing: `Competitor`, `Source`, `Trigger`, `SearchTask`;
3. references: `Region`, `BlackDomain`, `StopWord`, `TopicLimit`, `Category`, `Department`, `User`;
4. alerting: `EventType`, `Channel`, `RoutingRule`;
5. final tables: `RawItem`, `NormalizedItem`, `CategorizedEvent`, `ShowcaseEvent`, `Alert`, `ActionItem`, `SourceCandidate`.

После обычных импортов проект перестраивает insertion order глобального реестра FastAdmin и назначает итоговые `menu_section`. Альтернатива — полагаться на порядок импортов — отклонена: `workflow.py` одновременно регистрирует витрину и задачу, а между ними должен находиться alert; кроме того, автоформатер снова способен переставить импорты.

### 2. Проектный wrapper вокруг неизменённого FastAdmin ASGI app

Экспортируемый `admin_app` станет небольшим wrapper-приложением. Оно отдаёт проектный `index.html` и локальные `/ui/admin.css` и `/ui/admin.js`, а все `/api`, `/static` и остальные пути передаёт штатному FastAdmin app. Штатный JS/CSS bundle продолжает грузиться из установленного пакета.

Альтернативы отклонены:

- правка `index.min.js` в `venv` — не версионируется и исчезает после установки;
- копирование всего bundle в репозиторий — создаёт тяжёлый неотслеживаемый fork;
- только Unicode-разделители в названиях — не решают Dashboard, описания и адаптивное оформление.

### 3. UI-adapter использует стабильные ссылки, а не русские подписи

После рендера React проектный скрипт находит элементы по `href` Dashboard и model names из реестра, добавляет `data-kodik-zone`/CSS-классы, переименовывает Dashboard в «Пайплайн» и скрывает контейнер технической модели. `MutationObserver` повторяет идемпотентное применение после client-side навигации и перестройки sidebar.

Поиск по видимому русскому тексту не используется как основной селектор: перевод или изменение подписи не должно молча ломать структуру. Если ожидаемая ссылка/контейнер не найдены, скрипт оставляет штатный интерфейс рабочим и пишет одно диагностическое предупреждение в console.

### 4. Оформление строится вокруг трёх зон

CSS использует custom properties и атрибуты зон:

- pipeline — самостоятельная синяя карточка/акцент и увеличенный нижний отступ;
- settings — единый зелёный/бирюзовый акцент для трёх соседних секций, с небольшими внутренними промежутками;
- final — отдельный фиолетовый акцент и увеличенный верхний отступ.

Помимо цвета применяются отступ, тонкая рамка и типографическое состояние заголовка/active item. Цвета имеют пары для светлой и тёмной темы; при компактном sidebar фон и рамки остаются в пределах ширины, текстовые описания меню скрываются штатно, а title/tooltip сохраняется.

### 5. Описание вставляется как контекстный banner

Для Dashboard section определяется непосредственно как pipeline. На model list/detail/form страницах section определяется по model name из текущего URL или активной ссылки. Скрипт добавляет один идемпотентный banner перед основным содержимым: название раздела и 1–2 предложения.

Предлагаемые тексты:

- Пайплайн — «Запуск отдельных этапов BP-1—BP-7 или всего конвейера. Результат каждого запуска отображается на этой странице.»
- Настройки парсинга — «Конкуренты, источники, триггеры и задачи, по которым BP-1 собирает материалы.»
- Настройки справочников — «Справочники очистки и разметки данных, отделы и пользователи системы.»
- Настройки алертинга — «Типы событий, каналы доставки и правила выбора получателей уведомлений.»
- Финальные таблицы — «Результаты этапов BP-1—BP-7 в порядке прохождения данных. Большинство таблиц доступны только для просмотра.»

Banner получает `role="note"`, не перехватывает фокус и не смещает action buttons внутрь себя. На неизвестном маршруте banner не добавляется.

### 6. Backend остаётся источником прав и функций

Перемещение `UserAdmin`, `ShowcaseEventAdmin` и `ActionItemAdmin` меняет только `menu_section` и позицию. Их permission methods, base classes, fields и actions не изменяются. Pipeline marker остаётся зарегистрированным и продолжает генерировать widget actions; скрытие выполняется только после получения полной конфигурации.

## Risks / Trade-offs

- [DOM FastAdmin изменится после обновления пакета] → опираться на href/model identifiers, добавить browser-тесты и оставить fail-soft поведение; версия сейчас ограничена `>=0.10,<1.0`, поэтому обновление проверяется визуальным smoke.
- [Переупорядочивание глобального реестра использует внутренний API FastAdmin] → изолировать адаптер в одном модуле, проверять полный список 22 моделей и падать при пропавшей/лишней модели вместо тихой потери пункта.
- [MutationObserver создаст повторные элементы или лишнюю нагрузку] → debounce/idempotent data-marker и один observer на корневой контейнер.
- [Цветовые акценты окажутся слишком яркими или нечитаемыми] → умеренные design tokens, контрастная рамка/отступ как нецветовые признаки и визуальная проверка обеих тем.
- [Скрытие marker-модели случайно скроет dashboard widgets] → отдельные тесты конфигурационного API и DOM: schema marker/widget actions остаются, sidebar link отсутствует, кнопки видимы на Dashboard.

## Migration Plan

Миграция БД не требуется. Сначала вводятся реестр и перестройка menu sections/order, затем wrapper/template и UI assets, после чего добавляются unit/API/Playwright проверки. Откат возвращает прежний экспорт штатного FastAdmin app и старые `menu_section`; модели и данные не затрагиваются.
