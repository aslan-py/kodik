## Why

Заглушка этапа 1 в реестре пайплайна (`core/pipeline/registry.py`) сейчас переиспользует `core/scripts/stages/bp1.py` — тот же скрипт, что заливает ПОЛНЫЙ демо-датасет (~49 конкурентов, 100+ новостей). Это удобно для демонстрации BI, но дорого для сквозной проверки пайплайна: каждый клик «Этап 1» (или «Запустить всё») через `run_all()` доходит до BP-3, а там пять LLM-вызовов на пачку новостей и Tavily-поиск по КАЖДОМУ конкуренту (см. change `fix-bp3-pipeline-and-entrypoint`) — на полном датасете это неоправданно жжёт токены и лимиты внешних API при обычной проверке «пайплайн в принципе работает».

## What Changes

- Заводится отдельный минимальный сидер для заглушки этапа 1 — 1 конкурент, 1 `raw_item`, 2 чистые новости (доходят до `status=ok` в `normalized_item` после BP-2, без «грязного» текста — грязь тестирует BP-2, тут не нужна).
- `core/pipeline/registry.py` — заглушка этапа 1 переключается на этот новый минимальный сидер вместо `core/scripts/stages/bp1.py`.
- `core/scripts/stages/bp1.py` (полный демо-датасет, 49 конкурентов) **не меняется** и остаётся отдельной осознанной командой (`python -m core.scripts.stages.bp1`) для тех случаев, когда нужен весь объём демоданных — например, для наполнения BI.
- Никакого нового флага в `.env` не заводится — объём данных определяется тем, какую команду запустили (полный сидер вручную vs минимальная заглушка через пайплайн/админку), а не переключателем состояния.

## Capabilities

### New Capabilities
- `bp1/minimal-pipeline-stub`: заглушка этапа 1 пайплайна (в отличие от полного демо-сидера) заливает фиксированный минимальный набор — один конкурент, один снимок, две чистые новости — специально для дешёвой сквозной проверки этапов 2-7 без расхода токенов LLM и лимитов внешних API.

## Impact

- Код: новый минимальный сидер (`core/scripts/stages/bp1_stub.py` или аналогичное имя — уточнить при реализации, не путать с `bp1.py`), `core/pipeline/registry.py` (заглушка этапа 1 указывает на новую пару `clear`/`seed`).
- `core/scripts/stages/bp1.py` не изменяется.
