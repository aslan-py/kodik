## Context

См. `proposal.md` — «Why» для мотивации и разбора конкретного инцидента
(rbc.ru). Здесь фиксируется механика решения.

Сейчас `SearchUrlProber.probe()` (`search_probe.py:747-971`) перебирает
кандидатов и останавливается на **первом**, прошедшем
`looks_like_search_results` + `score_target_presence` — оба сигнала
текстовые, ни один не проверяет причинность. Селекторы адаптера на
момент пробинга ещё не существуют (пробинг предшествует
`analyze_structure`), поэтому сравнение «состава карточек» не может
опираться на структурированные поля — нужен эвристический сбор ссылок
(`_LinkCollector`, уже используется в `pagination.py` для похожей
задачи).

`_handle_quality_outcome` (`core.py:445`) знает только агрегированный
`quality_ok: bool` — `_run_quality_gate` (`core.py:393`) вычисляет
`reports` (список `QualityGateReport` по уровням) и тут же схлопывает их
в один булев флаг через `is_all_passed`, не передавая `reports` дальше.
Чтобы `_handle_quality_outcome` мог отличить «провалился именно
RELEVANCE» от «провалился SCHEMA», нужно прокинуть `reports` (или хотя
бы флаг «RELEVANCE провалился») в сигнатуру.

## Goals / Non-Goals

**Goals:**
- Кандидат поискового URL признаётся рабочим, только если его выдача
  причинно отличается от нефильтрованной базовой ленты источника.
- Когда для источника уже подтверждён рабочий URL с составом выдачи
  другого конкурента — сравнение использует и его тоже.
- Повторная деградация релевантности после успешной регистрации
  обнаруживается без ожидания ручной жалобы (как эта).
- Провал именно RELEVANCE сбрасывает и адаптер, и `probed_url` —
  остальные уровни качества сбрасывают только адаптер, как раньше.

**Non-Goals:**
- Не переписывается `looks_like_search_results`/`score_target_presence`
  сами по себе — новая проверка добавляется РЯДОМ, как дополнительный
  барьер, существующие сигналы остаются первым фильтром.
- Не гарантируется 100% отлов «сайт не фильтрует» — эвристика на основе
  overlap-порога, как и любая эвристика, имеет ложные срабатывания
  (см. Risks).
- Не вводится проверка релевантности на уровне классического RPA-контура
  (fedresurs) — там нет query-параметров поиска в этом смысле.
- Не меняется `ADAPTER_FAIL_THRESHOLD` (2) — используется тот же порог,
  что и для остальных уровней качества.

## Decisions

**1. Сравнение карточек — по множеству URL, не по хэшу всей страницы.**
Извлекаем ссылки эвристикой (`_LinkCollector`-подобный сбор, с той же
фильтрацией `_is_noise_url`/`_is_ad_redirect_url`, что уже применяется в
`pagination.py`), получаем множество URL, считаем коэффициент Жаккара
(`|A∩B| / |A∪B|`) между кандидатом и базовой лентой. Альтернатива —
сравнение `content_hash` всей страницы (дешевле) — отклонена: слишком
грубо, ложноотрицательно на страницах, которые честно вставляют «вы
искали: X» в иначе идентичную вёрстку (хэш разойдётся, а выдача
фактически не отфильтрована — обратная ошибка тоже возможна и не
ловится хэшем).

**2. Порог overlap — константа, не эвристика по домену.**
`SEARCH_PROBE_OVERLAP_THRESHOLD` (предлагается 0.7-0.8, требует
калибровки на нескольких известных источниках перед фиксацией) —
кандидат отклоняется, если совпадение с базовой лентой РАВНО ИЛИ ВЫШЕ
порога. Не делаем порог настраиваемым per-source в этой итерации — это
преждевременная сложность без данных о том, что он вообще нужен per-source.

**3. Базовая лента запрашивается один раз на весь `probe()`-вызов.**
`fetch(base_url)` без параметра — один запрос, результат переиспользуется
для сравнения со ВСЕМИ кандидатами в рамках одного вызова `probe()` (не
по одному fetch на кандидата). Итоговая стоимость: +1 запрос на вызов
`probe()`, а не +1 на каждый из до 7 кандидатов.

**4. Сравнение со «вторым конкурентом» требует хранить снимок карточек
победителя — в ОТДЕЛЬНОМ ключе кэша, не в `ProbedUrl` источника.**
`ProbedUrl` расширен полем `sample_item_urls: list[str]` (ограничено 30
ссылками, `_SAMPLE_ITEM_URLS_LIMIT`) — заполняется в `probe_async()` из
`plan.winner.result_urls` и естественно попадает в кэш через уже
существующий `set_probed_url()` (per-конкурентная запись, составной
ключ источник+хэш запроса).

Однако читать «снимок ДРУГОГО конкурента» из per-конкурентных записей
напрямую нельзя — `UnifiedCache` не поддерживает перечисление ключей по
паттерну (`get_probed_url` требует знать конкретный `search_param`).
**Найдено при реализации:** source-level ключ без `search_param`
(`_probed_url_key(source_name)`, тот же, что читает
`_preferred_param_from_registration`) уже занят другой записью —
подсказкой query-параметра, которую пишет
`SourceRegistrationService.register(probe_search=True)` при регистрации
источника. Если писать туда же результат обычного `probe_async()` (без
`search_params`), это затёрло бы подсказку параметра для будущих
холодных стартов.

Решение: отдельный ключ `bp1:probed_sample:{host}`
(`UnifiedCache.get_probed_sample_urls`/`set_probed_sample_urls`,
`core/cache.py`) — снимок карточек ПОСЛЕДНЕГО успешного пробинга любого
конкурента на источнике, независимо от per-конкурентных записей и от
записи регистрации. `AdaptiveRunner._get_or_probe_url` читает его перед
вызовом `probe_async()` и передаёт как `known_other_result_urls`; после
успешного пробинга — обновляет этим же снимком. `SourceRegistrationService`
сознательно НЕ пишет в этот ключ: её health-check идёт с `target_name=''`,
и `_evaluate()` в `probe()` не заполняет `result_urls`, если цель не
задана — писать было бы нечего.

Если снимка нет (первая регистрация источника) — сравнение идёт только с
базовой лентой (Decision 3), это осознанно слабее, но не блокирует
холодный старт.

**5. RELEVANCE — новый уровень `DataQualityGate`, не расширение
`BUSINESS`.**
Отдельный уровень (`QualityGateLevel.RELEVANCE`), не смешивается с
существующим `BUSINESS` (проверяет структуру бизнес-правил, не
смысловое соответствие). Разделение уровней даёт независимую
диагностику в логах/метриках (Шаг 20 уже собирает `quality_levels`
по уровням) — видно ИМЕННО какая проверка провалилась, не общий провал.
Порог провала: **ни один** из собранных `items` не упоминает
`competitor`/`trigger` (0 из N) — консервативный порог, не «доля ниже
X%», чтобы не давать ложных провалов на источниках с легитимно смешанной
повесткой (конкурент упомянут не в каждой новости, это нормально).

**6. `_handle_quality_outcome` получает `reports` И точный `search_param`,
не только `quality_ok`.**
Сигнатура расширяется параметром `reports: list[QualityGateReport]`
(уже вычисляется в `_run_quality_gate`, просто не передавался дальше).
Внутри — поиск отчёта уровня `RELEVANCE`, при провале ИМЕННО его (после
достижения `ADAPTER_FAIL_THRESHOLD`) — дополнительный вызов
`self._cache.clear_probed_url(source_name, search_param=...)` рядом с уже
существующим `clear_adapter(source_name)`.

**Найдено при реализации:** `clear_probed_url(source_name)` без
`search_param` чистит НЕ ТУ запись — source-level ключ занят подсказкой
параметра из регистрации (см. Decision 4), а реально проваленный URL
закэширован по составному ключу источник+хэш `search_param` конкретного
конкурента/задачи. `AdaptiveParser.parse()` этот `search_param` изначально
не получал (только уже резолвленный `url`) — пришлось прокинуть точную
строку через всю цепочку: `runner/core.py::run_task` (уже вычисляет её
через `SearchParamResolver` для пробинга) → `parse_kwargs['search_param']`
→ `bridge.py.parse()` → `AdaptiveParser.parse(search_param=...)` →
`_run_quality_gate` → `_handle_quality_outcome`. Без этого сброс был бы
no-op для реального сценария инцидента.

## Risks / Trade-offs

- **[Risk]** Overlap-порог может ложно отклонить реально рабочий
  параметр, если выдача конкурента легитимно пересекается с базовой
  лентой (конкурент — герой сегодняшней топ-новости).
  **→ Mitigation:** порог 0.7-0.8 — оставляет запас; при отклонении
  перебор просто идёт к следующему кандидату/реформулировке, не
  проваливает весь пробинг; худший случай — на один кандидат больше
  перебрано, не потеря функциональности.
- **[Risk]** +1 HTTP-запрос на каждый вызов `probe()` — на источниках с
  редкой регистрацией это не заметно, но `probe()` также вызывается
  из `AdaptiveRunner` при отсутствии кэша.
  **→ Mitigation:** пробинг и так кэшируется по паре (источник+запрос) —
  лишний fetch происходит только при первом обращении, не на каждый
  прогон.
- **[Risk]** Хранение `sample_item_urls` в `ProbedUrl` — расширение
  формата кэша, существующие закэшированные записи не будут иметь этого
  поля.
  **→ Mitigation:** поле опционально (`| None`/пустой список по
  умолчанию) — старые записи просто не участвуют в сравнении со «вторым
  конкурентом» до следующего успешного пробинга, деградации нет.
- **[Risk]** RELEVANCE — новый уровень, добавляет вызов
  `score_target_presence`-подобной проверки на каждый прогон (лёгкая,
  без LLM, но не бесплатная операция на больших списках items).
  **→ Mitigation:** линейная проверка по тексту, тот же порядок
  стоимости, что уже есть в `search_probe.py` — не LLM-вызов, не тратит
  деньги.

## Migration Plan

Поведенческое изменение, без миграции БД. Расширение `ProbedUrl`
(Decision 4) — аддитивное поле в pydantic-модели, кэшируемой в Redis как
JSON — старые записи десериализуются с полем по умолчанию, ничего не
ломается. Новый уровень `QualityGateLevel.RELEVANCE` — новое значение
enum, не переиспользует существующие. Откат — стандартный откат кода.
