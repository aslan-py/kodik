# bp1/adaptive-search-probing Specification

## Purpose

Поиск рабочего адреса выдачи по источнику: система перебирает способы
обратиться к поиску сайта (query-параметры, HTML-форма, реформулировки
запроса), чтобы адаптивный сбор и регистрация источника могли получить
адрес страницы результатов, на которой действительно есть искомая
компания, вместо угадывания одного фиксированного параметра.

## Requirements

### Requirement: Перебор поиска доступен при регистрации источника и при сборе
Проверка поискового эндпоинта источника (при регистрации, флаг
«проверить поиск») и адаптивный сбор по конкуренту SHALL успешно
выполнять перебор вариантов поиска без отказа из-за внутренней ошибки
конфигурации перебора.

#### Scenario: Регистрация источника с проверкой поиска
- **WHEN** источник регистрируется с включённой проверкой поискового
  эндпоинта
- **THEN** перебор вариантов поиска выполняется и завершается результатом
  (найден рабочий вариант или ни один не подошёл), не завершаясь ошибкой
  инициализации перебора

#### Scenario: Адаптивный сбор по задаче с конкурентом
- **WHEN** запускается адаптивный сбор по источнику, для которого ещё нет
  подсказки о рабочем параметре поиска
- **THEN** система перебирает варианты поиска и использует первый, на
  котором найден искомый конкурент

### Requirement: Найденная HTML-форма поиска отправляется тем способом, который она требует
Если на странице источника обнаружена поисковая форма с методом
отправки POST, перебор SHALL отправить её как POST-запрос с полями
формы, а не повторно запросить GET по тому же адресу. Если транспорт для
POST-отправки недоступен, этот вариант перебора SHALL быть помечен как
пропущенный, а не выполнен как GET.

#### Scenario: Форма поиска требует POST
- **WHEN** словарные query-параметры не дали выдачи, а на странице
  найдена форма поиска с методом POST
- **THEN** перебор отправляет форму POST-запросом с её полями и проверяет
  результат на наличие искомой компании

#### Scenario: POST-транспорт не подключён
- **WHEN** найдена форма поиска с методом POST, а перебору не передан
  способ выполнить POST-запрос
- **THEN** этот вариант перебора помечается пропущенным по причине
  отсутствия транспорта, и перебор переходит к следующему варианту
  (реформулировкам), не выполняя GET по адресу формы

### Requirement: Проверка «похоже на выдачу» может быть заменена вызывающей стороной
Перебор SHALL использовать переданную вызывающей стороной проверку
«похож ли ответ на страницу результатов поиска», если она передана, и
проверку по умолчанию — если нет.

#### Scenario: Вызывающая сторона не передала свою проверку
- **WHEN** перебор запущен без указания способа проверять «похоже на
  выдачу»
- **THEN** используется проверка по умолчанию, и перебор работает как
  обычно

#### Scenario: Вызывающая сторона передала свою проверку
- **WHEN** перебор запущен с указанием способа проверять «похоже на
  выдачу» (например, для источника, у которого признак пустой выдачи
  нетипичный)
- **THEN** результат каждой попытки перебора оценивается переданной
  проверкой, а не проверкой по умолчанию

### Requirement: Успешный вариант поиска обязан фильтровать выдачу, а не только содержать имя цели

Перебор SHALL считать вариант поиска (query-параметр, форма,
реформулировка) успешным только если состав результата причинно связан
со значением запроса, а не совпадает с нефильтрованной базовой лентой
источника. Присутствие имени цели где-либо в HTML SHALL NOT быть
единственным основанием для признания варианта рабочим.

#### Scenario: Кандидат отдаёт ту же ленту, что и базовый URL источника

- **WHEN** ответ на кандидата (query-параметр/форма/реформулировку)
  совпадает с содержимым базовой страницы источника (без параметра
  поиска) выше порога совпадения
- **THEN** этот кандидат SHALL NOT быть признан победителем, даже если в
  его HTML встречается имя искомой цели; перебор продолжается со
  следующим кандидатом

#### Scenario: Кандидат отдаёт состав, отличный от базовой ленты

- **WHEN** ответ на кандидата содержит имя цели и его состав карточек
  результата заметно отличается от базовой ленты источника
- **THEN** кандидат признаётся победителем как и раньше

#### Scenario: Для источника уже есть подтверждённая выдача другого конкурента

- **WHEN** идёт перебор для нового конкурента на источнике, для которого
  ранее уже был подтверждён рабочий вариант с составом выдачи другого,
  отличного конкурента
- **THEN** сравнение состава карточек SHALL использовать этот ранее
  подтверждённый состав в дополнение к базовой ленте источника

### Requirement: Выбор fetch-транспорта учитывает классификацию источника
Перебор поисковых вариантов SHALL выбирать fetch-транспорт для получения
страницы кандидата с учётом уже резолвленной классификации источника
(наличие антибота, признак SPA, рекомендованная стратегия). Если
классификация указывает, что источнику требуется деградационная стратегия
сильнее прямого HTTP-запроса, перебор SHALL использовать деградационный
fetch вместо запроса, который заведомо не получит содержательный ответ.

#### Scenario: Источник с известной антибот-защитой
- **WHEN** перебор запущен для источника, классификация которого указывает
  `has_antibot=true` (или `is_spa=true`, или рекомендованная стратегия
  строже FAST)
- **THEN** перебор использует fetch, способный пройти защиту источника
  (деградационную стратегию), а не только прямой HTTP-запрос

#### Scenario: Источник без известной защиты
- **WHEN** перебор запущен для источника без признаков антибота/SPA (или
  без классификации вовсе)
- **THEN** перебор использует прежний лёгкий fetch, поведение не меняется

### Requirement: Перебор с эскалированным fetch ограничивает число кандидатов
Когда перебор использует деградационный fetch (эскалация по
классификации), число перебираемых кандидатов SHALL быть меньше, чем при
лёгком fetch, чтобы не выполнять дорогой запрос на каждый из полного
набора вариантов подряд.

#### Scenario: Эскалированный перебор для защищённого источника
- **WHEN** перебор для источника с антибот-защитой перешёл на
  деградационный fetch
- **THEN** перебор пробует не более ограниченного приоритетного
  подмножества параметров (включая подсказку из предыдущей регистрации
  источника, если она есть), а не полный список параметров и
  реформулировок

### Requirement: Проверка поискового эндпоинта при регистрации источника учитывает защиту источника
Проверка поискового эндпоинта, выполняемая при регистрации источника
(`add-source` с включённой проверкой), SHALL использовать тот же принцип
выбора fetch-транспорта по классификации, что и перебор при боевом сборе,
— чтобы найденный на этом шаге параметр был пригоден для последующего
использования как подсказка даже для защищённых источников.

#### Scenario: Регистрация антибот-защищённого источника с проверкой поиска
- **WHEN** источник регистрируется с включённой проверкой поискового
  эндпоинта, и классификация (или результат первой попытки) указывает на
  антибот-защиту
- **THEN** проверка эндпоинта использует fetch, способный пройти защиту,
  вместо прямого HTTP-запроса, который не даст содержательного ответа

### Requirement: Вариант имени конкурента соответствует фактически использованному URL перебора
Перебор поисковых вариантов для одной задачи сбора SHALL выполняться
единожды на задачу: вариант названия конкурента (полный/без ОПФ),
извлечённый из победившей попытки перебора, SHALL соответствовать тому же
URL, который используется для последующего парсинга, а не результату
отдельного, независимого прогона перебора.

#### Scenario: Определение варианта имени и выбор URL для парсинга согласованы
- **WHEN** перебор для задачи сбора находит победивший вариант
  (параметр/форма/реформулировку)
- **THEN** URL этого победившего варианта используется и для определения
  имени конкурента при сборе новостей, и как адрес, который парсится
