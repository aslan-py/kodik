## Context

См. [proposal.md](proposal.md). `PipelineRun` и `PipelineStageRun` хранят только итоговый статус и JSON-результат. Технические записи создаются разными логгерами и доступны только в stdout контейнеров; Flower показывает состояние задач, но не объясняет бизнес-результат. В проекте уже применяется стандартный модуль `logging` и PostgreSQL.

## Goals / Non-Goals

**Goals:**

- Один источник понятной истории запусков, доступный и из админки, и через API.
- Связь каждого события с `run_id`, а при необходимости с BP-этапом и Celery task id.
- Единый контекст для stdout-логов воркеров: run id, stage, действие, итог и безопасная причина.
- Полезные сообщения для событий без ошибки: «нет новых данных», «пропущено circuit breaker», «занято другим прогоном», количества входных и выходных записей.

**Non-Goals:**

- Не заменять Flower, Sentry или централизованный технический стек наблюдаемости.
- Не транслировать stdout контейнеров в браузер и не строить терминал в админке.
- Не хранить полные отладочные payload, HTML, LLM-промпты, ключи и traceback в PostgreSQL.
- Не менять бизнес-правила BP1—BP7 или планировщик только ради журналирования.

## Decisions

### Постоянный журнал — отдельная таблица, а не JSON в `PipelineRun`

Добавить модель `PipelineRunEvent`: FK на прогон, nullable FK/номер этапа, время, уровень (`info`, `warning`, `error`), код события, короткое сообщение и ограниченный безопасный `details` JSON. Индексы: `(pipeline_run_id, created_at)` и `(created_at, level)`. Это даёт хронологию, фильтрацию и не раздувает строку `PipelineRun`.

Альтернатива — складывать массив сообщений в `PipelineRun.result`. Отклонена: массив плохо обновляется конкурентными воркерами, неудобен для общего журнала и не индексируется для фильтров.

### Единый сервис публикации событий

Ввести маленький сервис/фабрику событий, вызываемый на границах orchestration: создание прогона, публикация canvas, старт/итог этапа, финализация, watchdog/reconciler и пропуск планового слота. Сервис формирует одновременно DB-событие и структурированную запись обычного Python logging.

Альтернатива — подключить handler `logging`, который перехватывает все записи приложения. Отклонена: невозможно надёжно определить `run_id`, высок риск записать секреты и будет много нерелевантного шума.

### Сообщения и коды событий — стабильный словарь

События имеют машинный `event_code` и человекочитаемый русский `message`. Количественные показатели выбираются из уже подготовленных stage result и сохраняются в `details`; UI не должен интерпретировать произвольные traceback. Для ошибки хранится безопасная классификация и короткая причина. Технический exception с traceback остаётся в stdout через `logger.exception`.

### Админка показывает журнал как read-only модель

Зарегистрировать журнал отдельной read-only страницей в зоне «Пайплайн», с русскими названиями, фильтрами и ссылками на прогон. Существующие список прогонов и детали этапов получают ссылку/фильтр на связанные события. Для актуальных событий хватает ручного обновления страницы; live streaming не требуется на первом этапе.

### API отделяет общий журнал от детализации прогона

Добавить защищённые GET-методы для общего постраничного журнала и событий одного `run_id`, с allow-list фильтров. Ответы не содержат технические исключения сверх безопасных полей. В `PipelineRunRead` добавить ссылочное/счётное поле только при сохранении обратной совместимости схемы.

## Risks / Trade-offs

- [Журнал растёт при частом расписании] → записывать только события жизненного цикла, ограничить длину сообщений и предусмотреть настраиваемую политику хранения/очистки отдельной последующей задачей.
- [Сбой записи журнала не должен ломать конвейер] → запись события изолируется: ошибка журналирования фиксируется в stdout, но не меняет статус полезной работы этапа.
- [Дубли событий при redelivery Celery] → использовать идемпотентный ключ для уникальных событий этапа/попытки либо явно фиксировать номер попытки и исключать дубли на уровне БД.
- [Разные воркеры пишут одновременно] → короткие отдельные транзакции, индексы и отсутствие обновления единого JSON-массива.

## Migration Plan

1. Добавить таблицу журнала и миграцию без изменения текущих таблиц прогонов.
2. Развернуть код записи и UI/API; старые прогоны остаются доступными без событий.
3. После перезапуска воркеров новые прогоны начинают создавать события и расширенные stdout-логи.
4. Откат: удалить использование сервиса и экран/API; таблицу оставить безвредно либо удалить отдельной согласованной миграцией.
