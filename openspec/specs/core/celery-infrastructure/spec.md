# core/celery-infrastructure Specification

## Purpose

Единое Celery-приложение проекта, от которого наследуются фоновые задачи любого BP: общий брокер/бэкенд на Redis, общая ретрай-политика по умолчанию и Beat, готовый принимать периодические расписания.

## Requirements

### Requirement: Единое Celery-приложение для всего проекта
В проекте СУЩЕСТВУЕТ ровно одно приложение `Celery`, доступное для импорта и регистрации задач любым BP. Задача, зарегистрированная через это приложение, SHALL успешно диспатчиться через `.delay()`/`.apply_async()` при наличии рабочего брокера.

#### Scenario: Существующая задача BP-1 диспатчится
- **WHEN** `run_pipeline(mode='celery')` вызывает `.delay()` для задачи парсинга
- **THEN** вызов не завершается ошибкой импорта/отсутствия приложения, и задача попадает в очередь брокера

#### Scenario: Задача нового BP регистрируется в том же приложении
- **WHEN** код любого BP регистрирует новую фоновую задачу через общее Celery-приложение
- **THEN** задача видна тому же worker'у, что обслуживает задачи остальных BP, без создания отдельного `Celery()`-инстанса

### Requirement: Очередь задач и бизнес-данные в Redis изолированы друг от друга
Брокер и result backend Celery SHALL использовать номера БД Redis, отличные от номера БД, который занят под бизнес-данные (например, дедуп-хэши BP-1).

#### Scenario: Очистка бизнес-данных не задевает очередь
- **WHEN** данные в Redis-БД бизнес-логики (например, дедуп-хэши BP-1) очищаются или инспектируются
- **THEN** содержимое очереди/результатов Celery в своей отдельной БД не затрагивается

### Requirement: Beat готов принимать периодические расписания
Приложение SHALL включать отдельный singleton-процесс Beat с зарегистрированной периодической управляющей задачей. Управляющая задача SHALL с настраиваемым интервалом проверять эффективное cron-расписание pipeline, атомарно обрабатывать каждый наступивший слот не более одного раза и учитывать изменение runtime override без перезапуска Beat.

#### Scenario: Beat запускается с действующим расписанием
- **WHEN** singleton-процесс Beat стартует при включённом валидном расписании
- **THEN** он периодически ставит управляющую задачу в очередь, а наступивший cron-слот инициирует полный прогон pipeline

#### Scenario: Beat запускается без ошибок при пустом расписании
- **WHEN** процесс Beat стартует без runtime override, а default-расписание выключено
- **THEN** процесс и периодический dispatcher работают без ошибок, но полный pipeline не ставится в очередь

#### Scenario: Расписание выключено
- **WHEN** эффективная настройка `enabled` равна false
- **THEN** Beat продолжает работать, но управляющая задача не создаёт плановые прогоны

#### Scenario: Расписание изменено из админки
- **WHEN** администратор сохраняет новый runtime override
- **THEN** управляющая задача применяет его не позднее следующего интервала проверки без перезапуска Beat

#### Scenario: Один слот не дублируется
- **WHEN** управляющая задача повторно обрабатывает уже зарезервированный cron-слот
- **THEN** второй прогон для этого слота не создаётся

### Requirement: Ретрай-политика по умолчанию общая для всех задач
Приложение SHALL определять дефолтные параметры повторных попыток (максимум попыток, задержка, максимальный backoff), доступные любой зарегистрированной задаче без необходимости объявлять собственные константы.

#### Scenario: Новая задача BP наследует ретрай-дефолты
- **WHEN** задача любого BP регистрируется в общем приложении без явного переопределения параметров ретрая
- **THEN** к ней применяются дефолтные значения максимума попыток, задержки и backoff, определённые общим приложением

### Requirement: Pipeline использует выделенные именованные очереди
Celery SHALL маршрутизировать управляющие задачи в `pipeline.control`, ресурсоёмкие задачи BP1 в `pipeline.bp1`, а задачи BP2—BP7 в `pipeline.stages`. Развёртывание SHALL запускать worker'ы с явным списком обслуживаемых очередей.

#### Scenario: BP1 изолирован от остальных этапов
- **WHEN** поставлены задачи BP1 и последующих этапов
- **THEN** BP1 получает worker, подписанный на `pipeline.bp1`, а BP2—BP7 — worker, подписанный на `pipeline.stages`

#### Scenario: Управляющая задача не исполняет бизнес-этап
- **WHEN** диспетчер расписания или финализатор ставится в очередь
- **THEN** задача маршрутизируется в `pipeline.control`, отдельно от очередей бизнес-этапов

### Requirement: API, workers, Beat и Flower запускаются отдельными процессами
Контейнерная инфраструктура SHALL предоставлять отдельные сервисы API/uvicorn, worker'ов, singleton Beat и Flower на основе совместимого образа приложения. Запуск uvicorn SHALL NOT запускать worker, Beat или Flower внутри API-процесса.

#### Scenario: Запуск полного Compose deployment
- **WHEN** оператор запускает документированную Compose-конфигурацию
- **THEN** PostgreSQL, Redis, API, необходимые worker'ы, один Beat и Flower стартуют как отдельные наблюдаемые сервисы

#### Scenario: API перезапущен отдельно
- **WHEN** перезапускается только API-контейнер
- **THEN** worker'ы и планировщик продолжают работать независимо

#### Scenario: BP1 worker готов к браузерному парсингу
- **WHEN** BP1 запускается в контейнерном deployment
- **THEN** обслуживающий его worker имеет браузерные системные зависимости и доступ к постоянным данным, требуемым существующим BP1

### Requirement: Flower предоставляет защищённый мониторинг Celery
Flower SHALL запускаться отдельным сервисом с подключением к общему Celery app и SHALL требовать настроенную аутентификацию. Эксплуатационная документация SHALL предупреждать, что публичный доступ требует защищённого reverse proxy/TLS.

#### Scenario: Авторизованный оператор открывает Flower
- **WHEN** оператор передаёт корректные учётные данные
- **THEN** Flower показывает worker'ы, очереди и задачи deployment

#### Scenario: Неавторизованный запрос к Flower
- **WHEN** клиент не предоставляет корректные учётные данные
- **THEN** доступ к панели мониторинга отклоняется

### Requirement: Настройки выполнения задаются окружением
Интервал диспетчера, cron/timezone/enabled по умолчанию, таймаут зависшего прогона, параметры worker'ов и учётные данные Flower SHALL иметь документированные переменные окружения и безопасные значения для локального запуска, кроме секретов, которые SHALL быть заданы явно.

#### Scenario: Deployment использует env-настройки
- **WHEN** сервисы стартуют с заполненным env-файлом
- **THEN** API, worker'ы и Beat используют согласованные broker/backend и настройки pipeline

#### Scenario: Секрет Flower отсутствует
- **WHEN** production deployment запускает Flower без обязательных учётных данных
- **THEN** сервис завершается с понятной ошибкой конфигурации вместо запуска открытой панели
