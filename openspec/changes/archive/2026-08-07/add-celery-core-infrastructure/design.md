## Context

См. proposal.md - Why. Дополнительные ограничения, важные для выбора решения:

- `docker-compose.yml` сегодня содержит только сервисы на готовых образах (`postgres`, `redis`, `redis-commander`) — ни одного `build`-сервиса для самого приложения нет. Само FastAPI-приложение и все BP-скрипты (`python -m core.scripts...`) запускаются локально, не в контейнере.
- `src/bp1/runner.py::run_pipeline(mode='celery')` уже вызывает `.delay()` — то есть код, ожидающий рабочий Celery-app, существует и это единственный текущий потребитель.
- `core/config.py` уже хранит `redis_db` (используется BP-1 под дедуп-хэши) и производный `redis_url` по паттерну `property` — новые Celery-настройки следуют этому же паттерну.

## Goals / Non-Goals

**Goals:**
- Единая точка `core/celery_app.py`, от которой наследуются задачи любого BP.
- Broker/backend на Redis, с БД, изолированными от `redis_db` бизнес-логики.
- Ретрай-политика по умолчанию доступна как общий дефолт, а не константы, привязанные к BP-1.
- Beat-приложение существует и готово принимать расписания (без записей).

**Non-Goals:**
- Контейнеризация celery-worker/celery-beat/flower — см. Decisions ниже.
- Конкретные записи `beat_schedule` и обёртывание задач BP-2…BP-7 — см. proposal.md - Non-goals.

## Decisions

### Отдельные номера Redis-БД под broker и result backend
`CELERY_BROKER_DB` и `CELERY_RESULT_BACKEND_DB` — новые настройки, отдельные от `REDIS_DB`. Альтернатива (переиспользовать `redis_db` с префиксом ключей) отклонена: очередь и бизнес-данные (дедуп-хэши BP-1) должны жить в разных БД одного Redis-инстанса, чтобы `FLUSHDB`/просмотр в `redis-commander` по одной из них не задевал другую случайно.

### `celery-worker`/`celery-beat`/`flower` не идут в `docker-compose.yml` в этом изменении
Решено (не оставлено на потом): раз для приложения ещё нет `Dockerfile`/`build`-сервиса ни для чего, кроме готовых образов, заводить его только ради Celery — расширение рамок этого изменения. Вместо этого воркер/beat/flower запускаются той же локальной командой, что уже описана в README BP-1 (`celery -A core.celery_app worker`, аналогично `celery -A core.celery_app beat`, `celery -A core.celery_app flower`). Когда для приложения появится общий `Dockerfile` (отдельное изменение), туда же добавятся и эти три сервиса в `docker-compose.yml`.

### Retry-константы переезжают в `core/celery_app.py`, а не остаются в `src/bp1/constants.py`
Три константы (`CELERY_MAX_RETRIES`, `CELERY_DEFAULT_RETRY_DELAY`, `CELERY_RETRY_BACKOFF_MAX`) становятся дефолтами общего приложения — иначе каждый следующий BP, заводящий свою задачу, будет вынужден либо дублировать константы, либо тянуть зависимость на `src/bp1`, что нарушает независимость BP друг от друга.

## Risks / Trade-offs

- [Risk] Без контейнеризации воркер/beat/flower зависят от локального окружения разработчика (версии Python, установленных зависимостей) → Mitigation: команды запуска зафиксированы в README рядом с уже существующей инструкцией по API; `requirements.txt` — единственный источник версий зависимостей.
- [Risk] Пустой `beat_schedule` может быть забыт, и BP-7 «раз в 2 дня» повиснет без реального расписания → Mitigation: явно зафиксировано в Non-goals proposal.md, отслеживается отдельным будущим изменением, а не остаётся неявным пробелом.
- [Risk] BREAKING-правка `src/bp1/celery_tasks.py` (смена `@shared_task` на `app.task`) может разойтись с незакоммиченной локальной веткой автора BP-1 → Mitigation: правка согласована заранее (см. proposal.md - What Changes), внешнее поведение `run_parser_task` не меняется.

## Migration Plan

Функциональности до этого изменения не существовало (`src.celery_app` отсутствовал, `.delay()` не мог отработать) — миграции данных нет. Порядок внедрения:
1. Настройки в `core/config.py` + `.env.example`/`.env`.
2. `core/celery_app.py` с пустым `beat_schedule` и ретрай-дефолтами.
3. Переключение `src/bp1/celery_tasks.py` на импорт общего `app`, перенос трёх констант.
4. Обновление `src/bp1/README.md` (команда запуска воркера).
5. `flower` в `requirements.txt`.

Откат: изменение не трогает существующие данные/схему БД — откат равносилен ревёрту коммита.
