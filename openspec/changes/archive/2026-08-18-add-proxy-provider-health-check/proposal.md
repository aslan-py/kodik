## Why

`network/pool.py` (изменение `add-rpa-collection-proxying`) кэширует пул
прокси в Redis только при успехе — при ошибке провайдера (невалидный или
отозванный `SX_ORG_API_KEY`, исчерпанный баланс) ничего не кэшируется.
Каждый `acquire()` — то есть каждый запрос каждой RPA-стратегии по всему
конвейеру — заново пытается достучаться до заведомо сломанного
провайдера и получает 3 ретрая с экспоненциальным бэкоффом (~7с) прежде
чем деградировать до работы без прокси. При долгоживущей проблеме
(например, ключ отозван) это не роняет прогон формально, но незаметно
съедает время каждой RPA-выборки и заваливает лог одинаковыми warning —
на практике выглядит как «конвейер не работает».

## What Changes

- Перед выполнением задач сбора (`AdaptiveRunner.run_all`) — один
  реальный синхронный чек провайдера прокси (если `SX_ORG_API_KEY`
  задан): дешёвый авторизованный вызов провайдера. Не отдельная
  периодическая Celery-задача — проверка происходит один раз в начале
  каждого прогона, а не по расписанию.
- Если чек не прошёл (ключ невалиден, баланс исчерпан, провайдер
  недоступен) — ровно одна запись в лог на весь прогон («Прокси не
  работает, необходимо пополнить баланс сервиса — сбор продолжается без
  прокси») и общий Redis-маркер «провайдер недоступен», который
  `pool.acquire()` проверяет перед любым обращением к провайдеру.
- Пока маркер жив, `acquire()` в рамках того же прогона не повторяет
  обращения к провайдеру — сразу возвращает отсутствие прокси. Это
  распространяется и на классический контур `fedresurs_rpa` — он ходит
  через тот же `pool.acquire()`, отдельно ничего не дублируется.
- В `network/provider.py`: `_make_request` не ретраит HTTP 401/403 —
  аутентификационная ошибка не лечится повтором, только тратит время
  (~7с на 3 бесполезных ретрая). Ретраятся только сетевые/5xx/429-ошибки,
  как раньше.
- **Отправка реального уведомления (email/telegram) не входит в этот
  change** — только лог-заглушка. Настройки-получатели (`TEST_EMAIL`,
  `TEST_TG` из существующего блока `--- Настройки алёртов ---`)
  переиспользуются без изменений — новых настроек не заводится; в коде
  оставляется пометка, где будущая реализация подключит
  `core.mail.send_email`/`core.telegram.send_telegram`.

## Capabilities

### New Capabilities
(нет)

### Modified Capabilities
- `bp1/rpa-network-controls`: добавлена проверка провайдера прокси в
  начале прогона (не на каждый запрос) с однократным логом и
  предотвращением повторных обращений к уже известному неработоспособным
  провайдеру в рамках того же прогона.

## Impact

- `src/bp1/adaptive/integration/runner/batch.py` (`AdaptiveRunner.run_all`)
  — точка вызова чека, до диспетчеризации задач.
- `src/bp1/network/pool.py` — Redis-маркер «провайдер недоступен»,
  метод чека, однократный лог.
- `src/bp1/network/provider.py` — `_make_request` не ретраит 401/403.
- Не затрагивает: `core/mail.py`, `core/telegram.py`, Celery beat —
  реальная отправка уведомлений вне рамок этого change.
