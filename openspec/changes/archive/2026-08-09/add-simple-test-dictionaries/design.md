## Context

См. proposal.md — Why. Пользователь явно разрешил разрыв «новость должна получить приоритет П2/П3 от LLM» — новости №2/№3 отсеиваются в BP-2 и до BP-3 не доходят вовсе, это нормально (см. переписку — «ничего страшного что в третий этап не попадут»). Итоговая арифметика, подтверждённая пользователем: из 6 новостей 2 отсеиваются в BP-2 (чёрный домен, стоп-слово), из оставшихся 4 антишум отсеивает ещё 2, до BP-3 доходят ровно 2, одна из них — гарантированно П1.

## Goals / Non-Goals

**Goals:**
- Предсказуемый, воспроизводимый набор из 6 новостей, каждая с понятной ролью в тесте.
- Один скрипт (`simple_dictionaries`), после которого админку сразу можно жать «Этап 1» → «Запустить всё» и увидеть все фильтры/алертинг в деле.

**Non-Goals:**
- Не гарантируем на 100%, какая ИМЕННО из новостей №4/№5/№6 переживёт антишум (см. Risks) — определяется порядком вставки, не контролируется явно.
- Не гарантируем на 100%, что LLM всегда даст новости №1 именно категорию, маппящуюся в П1 — контент спроектирован для однозначного сигнала, но это LLM, не детерминированная функция.
- Не трогаем `Category`/`Department`/`Region` — они приходят из обычного `core/scripts/stages/dictionaries.py`, `simple_dictionaries` их не заливает и не чистит (пользователь запускает `dictionaries.py` до `simple_dictionaries`, см. проверенный порядок в proposal.md).

## Decisions

**Шесть новостей и их роли** (заменяют текущие 2 в `bp1_stub.py`):

| № | Домен | Заголовок | Роль |
|---|---|---|---|
| 1 | `test1-alert-source.ru` | «Прокуратура начала проверку «ДатаСинтез» из-за нарушений» | Однозначный сигнал категории «надзорная санкция и юридический риск» → П1. Содержит слово «прокуратура» — маркер для `event_type.keywords` (алертинг) |
| 2 | `compromat-test.ru` | «Партнёрство «ДатаСинтез» с логистическим оператором» | Домен в чёрном списке — отсеивается в BP-2, содержимое не важно |
| 3 | `test3-source.ru` | «Специальный промокод на скидку от партнёра «ДатаСинтез»» | Содержит стоп-слово «промокод» — отсеивается в BP-2 |
| 4 | `shared-site-test.ru` | «"ДатаСинтез" представила обновление продукта» | Общий домен с №5/№6 — под антишум |
| 5 | `shared-site-test.ru` | «Сотрудники «ДатаСинтез» выступили на конференции» | Общий домен с №4/№6 — под антишум |
| 6 | `shared-site-test.ru` | «"ДатаСинтез" подвела итоги квартала» | Общий домен с №4/№5 — под антишум |

**Справочники `simple_dictionaries` (все — снос + заново, при каждом запуске):**

- `Competitor` — ровно один: «ДатаСинтез».
- `Source` — ровно один: `https://newssearch.yandex.ru` (переиспользуем `SOURCE_NAME` из `dictionaries.py`, не дублируем строкой).
- `BlackDomain` — один: `compromat-test.ru` (под новость №2).
- `StopWord` — один: `phrase='промокод'`, `type=stop_word` (под новость №3; по образцу из `BP2_README.md`, где «промокод» уже приведён как типовой пример).
- `TopicLimit` — один: `scope=media, max_count=1, window=run`. Именно `max_count=1`, не 2: чтобы из трёх новостей с одним доменом (№4/5/6) отсеялись ДВЕ, а не одна (подтверждено пользователем: «две новости по антишуму»).
- `Channel` — два: `email`, `telegram`.
- `EventType` — один: `keywords=['прокуратура']` (ловит новость №1). Имя — по образцу существующего в демо-данных BP-5 (`'судебный/надзорный риск'`), не изобретаем новую формулировку.
- `User` — один тестовый получатель (не пересекается с демо-пользователями `dictionaries.py`, которых заодно и не трогаем — `simple_dictionaries` управляет только «своими» справочниками из списка выше). Email/telegram_id — заглушки для структуры БД: реальная адресация в проде управляется `settings.true_alerting`/`TEST_EMAIL`/`TEST_TG` (см. `BP5_README.md`), это уже задокументировано и пользователь сам это упомянул («буду использовать настройку в env»).
- `RoutingRule` — две строки: (EventType, П1) → (User, channel=email, mode=instant) и (EventType, П1) → (User, channel=telegram, mode=instant). `mode=instant` обязателен — только он реально пытается отправиться (см. `BP5_README.md`, `digest` остаётся `queued`).

**Почему `simple_dictionaries` не трогает `Category`/`Department`/`Region`.** Они не в списке, который явно перечислил пользователь, и нужны раньше по цепочке (BP-3 резолвит категорию/отдел из LLM-ответа по этим справочникам) — их логично оставить за обычным `dictionaries.py`, а не дублировать здесь. Порядок использования (полная очистка → `dictionaries.py` → `simple_dictionaries` → пайплайн) зафиксирован в proposal.md по словам пользователя.

**Очистка перед заливкой.** По образцу `dictionaries.py::clear()` — сначала `clear_from(session, PIPELINE_ORDER[-1])` (сносит весь пайплайн, иначе FK RESTRICT не даст удалить конкурента/источник, на которые ссылается `search_task`), затем прямой `delete()` по каждой из управляемых таблиц.

## Risks / Trade-offs

- [Риск] **Какая из новостей №4/№5/№6 переживёт антишум — не гарантировано явно.** `reject_over_limit` (BP-2, `antinoise.py`) ранжирует строки `ROW_NUMBER() OVER (PARTITION BY media_domain ORDER BY created_at DESC)`, а `created_at` у всех трёх выставляется ОДНИМ И ТЕМ ЖЕ значением при массовой вставке (SQLAlchemy bulk insert — тот же эффект, что уже наблюдался при разборе алертинга ранее в проекте: одинаковый timestamp с точностью до микросекунды на весь батч). При равных `created_at` Postgres разрешает неоднозначность по физическому/сканирующему порядку — на практике устойчиво в пределах одного `INSERT`, но не гарантировано спецификацией SQL. → Митигация: не критично для теста («какая именно выживет — неважно», только их МЕСТО важно), задача 6.x — проверить вручную, какая уцелела, и просто зафиксировать это в докстринге модуля по факту.
- [Риск] **LLM может не дать новости №1 категорию, маппящуюся строго в П1.** Контент спроектирован максимально однозначно («прокуратура», «проверка», «нарушения» — прямое попадание в описание категории «надзорная санкция и юридический риск» из `BP3_README.md`), но 100% гарантии нет — это реальный вызов LLM. → Митигация: если на практике придёт другая категория/приоритет, значение маркер-слова в `EventType.keywords` не изменится (оно совпадает с заголовком новости №1, не с приоритетом), так что при ручной проверке достаточно свериться с фактическим приоритетом события и, если он не П1, поправить `RoutingRule.priority` вручную через админку — код менять не придётся.
- [Риск] **`simple_dictionaries` полностью сносит `Competitor`/`Source`.** Если в БД к моменту запуска есть другие конкуренты/источники (не только «ДатаСинтез»/yandex) — они и все данные пайплайна на них будут снесены каскадно. → Митигация: это явно то, что просил пользователь («строго одного конкурента», «строго один источник»), задокументировано в докстринге скрипта как предупреждение.
