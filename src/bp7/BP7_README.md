# BP-7: расширение источников — очередь кандидатов и перенос в `source`

BP-7 отвечает за пополнение справочника `source` новыми источниками без
правки кода. В этой итерации реализована таблица кандидатов и логика
переноса по порогу `score`. Агент, который сам ищет кандидатов в интернете
(веб-поиск + LLM-оценка), и периодический запуск через Celery Beat —
следующие итерации (см. «Осознанно не реализовано» ниже).

---

## `source_candidate` — очередь кандидатов

| Поле | Тип | Описание |
|------|-----|---------|
| `id` | int | Первичный ключ |
| `domain` | string, unique, not null | Найденный домен-кандидат. UNIQUE — не предлагать дважды |
| `competitor_id` | FK → `competitor`, nullable | По какому конкуренту/запросу нашли |
| `url` | string, nullable | Url найденного кандидата к парсингу |
| `score` | numeric(3,2), nullable | Оценка релевантности от LLM, 0.00–1.00 |
| `status` | enum, not null, default `new` | `new` → `promoted`. Индексирован (`ix_source_candidate_status`) — отбор на перенос идёт по индексу, без JOIN/NOT EXISTS с `source` |
| `is_active` | bool, not null, default true | `false` — снять кандидата с рассмотрения, не удаляя строку |
| `created_at` | datetime | Когда кандидат добавлен |

`url`, `competitor_id`, `score` — nullable: заполняющий агент ещё не
написан, поля должны просто существовать в таблице для ручного/будущего
наполнения.

**Зачем `status`, а не просто сверка с `source` на лету.** При росте
`source_candidate` проверка «есть ли уже такой `domain` в `source`»
(JOIN/`NOT EXISTS` на каждый прогон) стала бы всё дороже. `status`
проставляется в момент переноса и отбор идёт `WHERE status = 'new'` — по
индексу, без сканирования уже обработанных строк.

## Порог переноса

Хранится в конфиге приложения, не в БД и не в коде:

```
# .env
SOURCE_CANDIDATE_SCORE_THRESHOLD=0.5
```

`core.config.settings.source_candidate_score_threshold` (по умолчанию `0.5`).
Поменять порог — правка `.env`, без деплоя новой логики и без миграций.

## Логика переноса

`src/bp7/pipeline.py::SourceCandidatePromoter` — класс с методами:

- `get_threshold()` — текущий порог из конфига;
- `select_promotable(threshold)` — активные (`is_active=true`) кандидаты со
  `status='new'` и `score` строго больше порога;
- `promote()` — весь прогон: порог → отбор → запись в `source`
  (`name=candidate.domain`, `is_active=true`) через
  `INSERT ... ON CONFLICT DO NOTHING` по `source.name` → у ВСЕХ отобранных
  кандидатов проставляется `status='promoted'`. Два уровня защиты от
  дублей: `status='new'` не даёт повторно ОТОБРАТЬ кандидата (главный
  механизм, дешёвый — по индексу), `ON CONFLICT DO NOTHING` по `source.name`
  подстрахует, если в `source` такое имя уже оказалось не через этот перенос.

После переноса ничего вручную заводить в `search_task` не нужно. Ближайший
реальный прогон BP-1 автоматически создаст задачи без поискового слова по
новому источнику для всех активных конкурентов и сразу выполнит их обход.

Логика собрана в класс (а не в свободные функции, как `run_bp4()`/`run_bp5()`)
специально, чтобы её методы позже обернуть декоратором Celery без
переписывания — когда в проекте появится общая настройка очередей
(расписание «раз в 2 дня» — следующая итерация).

## Как запустить вручную для теста

Прямой запуск как самостоятельный скрипт (открывает свою сессию, коммитит):

```bash
python -m src.bp7.pipeline
```
Печатает сводку: `{'threshold': 0.5, 'checked': N, 'promoted': M}`.

Программный вызов (например, внутри теста или другого скрипта):

```python
from core.database import AsyncSessionLocal
from src.bp7.pipeline import SourceCandidatePromoter

async with AsyncSessionLocal() as session:
    summary = await SourceCandidatePromoter(session).promote()
    await session.commit()
    print(summary)
```

Чтобы проверить перенос вручную — вставьте пару строк в `source_candidate`
(например, через `psql`/DBeaver) с разным `score` (выше и ниже порога;
`status` по умолчанию `new`) и запустите `python -m src.bp7.pipeline`:
в `source` должна появиться только строка с `score` выше порога, а её
`status` в `source_candidate` — смениться на `promoted`. Повторный запуск
даст `checked: 0` для уже перенесённого кандидата — status='new' у него
больше нет, повторно он не отбирается.

## Осознанно не реализовано

- **Агент расширения источников.** Поиск кандидатов в живом интернете и их
  LLM-оценка (заполнение `source_candidate`) — отдельная задача, таблица
  сейчас наполняется вручную/другим скриптом.
- **Celery Beat расписание («раз в 2 дня»).** `run_bp7_promotion()` вызывается
  напрямую, как `run_bp4()`/`run_bp5()` — Celery-обвязки в проекте пока нет
  ни у одного BP (см. `src/bp5/BP5_README.md`, «Осознанно не реализовано»).
- **API для порога.** Порог правится через `.env`
  (`SOURCE_CANDIDATE_SCORE_THRESHOLD`), не через эндпоинт — вынесение в API
  отложено на будущую итерацию.
