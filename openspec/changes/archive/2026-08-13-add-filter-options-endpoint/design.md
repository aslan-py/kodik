## Context

См. `proposal.md` — Why. Текущий `GET /showcase` фильтрует по строковым `category`, `region`, `priority`, `competitor`, `department`, причём эти отображаемые значения уже денормализованы в `showcase_event`. `GET /action-items` принимает `department_id`, `status`, `task`, `assigned_user_id`, `showcase_event_id`, но не принимает запрошенные фронтом `deadline` и `priority`. Приоритет задачи не хранится в `action_item`: он берётся из связанного `showcase_event.priority`.

Плоское объединение двух предложенных JSON-объектов создаёт конфликт типов: showcase использует строковый `department`, а action-items — числовой `department_id`. Кроме того, массив имён под ключом `assigned_user_id` не позволяет фронту отправить настоящий ID. Поэтому один HTTP-запрос сохраняется, но ответ делится на две предметные секции.

## Goals / Non-Goals

**Goals:**

- дать фронтенду один запрос для инициализации фильтров обоих экранов;
- возвращать значения в форме, которую можно без обратного поиска передать существующим и новым query-параметрам;
- отражать актуальные данные, а не весь объём административных справочников;
- не раскрывать viewer сведения о задачах чужих отделов;
- сохранить детерминированный контракт и покрыть его endpoint-тестами.

**Non-Goals:**

- реализовывать зависимые фасетные варианты, меняющиеся от уже выбранных фильтров;
- локализовать даты или enum-статусы на сервере;
- добавлять кэш до появления измеренной проблемы производительности;
- менять существующую модель ролей или область видимости списка задач.

## Decisions

### 1. Один endpoint, но вложенные секции

Контракт ответа:

```json
{
  "showcase": {
    "category": ["Логистика"],
    "region": ["Москва"],
    "priority": ["П1", "П2", "П3", "П4"],
    "competitor": ["Ozon"],
    "department": ["Коммерческий"]
  },
  "action_items": {
    "status": ["open", "in_progress", "done"],
    "deadline": ["2026-02-19"],
    "priority": ["П1"],
    "assigned_user_id": [{"value": 17, "label": "Анастасия Иванова"}],
    "department_id": [{"value": 3, "label": "Коммерческий"}]
  }
}
```

Ключи совпадают с query-параметрами списочных endpoint, что уменьшает преобразования на фронте. Альтернатива с плоским объектом отклонена из-за разных типов отделов и невозможности независимо развивать два экрана.

### 2. Значения из данных и enum разделяются явно

Showcase category/region/competitor/department берутся как `DISTINCT` непустые значения `showcase_event`, поэтому фильтр не предлагает значения без результатов. Showcase priority берётся из единственного отображаемого mapping приоритетов и доступен полностью даже на пустой витрине.

Action status берётся из `ActionStatus` полностью. Deadline, priority, assigned user и department берутся только из существующих доступных задач: для priority выполняется join с `showcase_event`, для подписей ID — join с `user` и `department`. Это не скрывает старую задачу только потому, что связанный пользователь позже стал неактивным.

Альтернатива — собирать всё из master-справочников. Она отклонена: витрина хранит готовые строки, которые могут отражать историческое значение, а не текущее имя справочника; фильтр обязан совпадать с реально фильтруемой колонкой.

### 3. Viewer scope применяется в самих action-запросах

Общая база запросов action options ограничивается `ActionItem.department_id == current_user.department_id` для viewer. Analyst/admin не получают это условие. Если у viewer нет отдела, data-derived массивы action-items пусты, а enum-статусы остаются доступны.

Фильтрация не выполняется после загрузки в Python: ограничение на уровне SQL не переносит чужие значения из БД в прикладной слой и масштабируется предсказуемо.

### 4. Новые фильтры action-items проходят через всю цепочку

В endpoint, service и CRUD добавляются `deadline: date | None` и `priority: str | None`. Deadline сравнивается с `ActionItem.deadline`, priority требует join `ActionItem.showcase_event_id == ShowcaseEvent.id` и сравнивается с `ShowcaseEvent.priority`. Join применяется только когда нужен priority, чтобы не усложнять обычный список.

Все условия продолжают накапливаться в одном statement и объединяться AND. Для viewer service по-прежнему принудительно заменяет любой `department_id` на собственный отдел.

### 5. Новый слой следует текущему API-разделению

Добавляются отдельные schema, CRUD, service и тонкий endpoint-модуль для filter options; router регистрируется в `api/routers.py` с отдельным тегом. Общая схема `IdLabelOption(value: int, label: str)` используется для ID-backed вариантов. Endpoint принимает `ViewerDep`, чтобы pending не получил доступ, а service получает текущего пользователя для scope.

Прямое размещение SQL в endpoint отклонено: оно нарушило бы существующее разделение `endpoint → service → CRUD` и усложнило бы модульные тесты.

### 6. Формат дат остаётся машинным

Deadline сериализуется стандартной Pydantic date-схемой как `YYYY-MM-DD`, совпадая с форматом query-параметра FastAPI. Формат `19.02.2016` из примера является отображением и формируется фронтом; передача его обратно в текущий date query привела бы к `422`.

## Risks / Trade-offs

- [Несколько DISTINCT-запросов увеличивают число обращений к БД] → выбирать только одну колонку, использовать существующие индексы где доступны и измерить endpoint до введения кэша.
- [Список сроков или исполнителей со временем станет большим] → текущий контракт возвращает все применимые значения; при измеренном росте добавить поиск/пагинацию отдельным change, не обрезать ответ молча.
- [Исторические строки showcase могут содержать нестандартный приоритет] → статический showcase-набор остаётся каноническим, action priority включает только значения, распознаваемые порядком `П1`—`П4`; аномалии выявляются тестом данных и не становятся случайными UI-опциями.
- [Параллельный change проверки API фиксирует 90 операций] → при совместном применении добавить `GET /filter-options` в manifest и ожидать 91 операцию.
- [Viewer может передать чужой department_id вместе с другими фильтрами] → действующее принудительное ограничение своим отделом остаётся последним словом service-слоя.

## Migration Plan

Миграция БД не требуется. Сначала расширяется фильтрация action-items и её тесты, затем добавляются слои filter options и router. После этого обновляются OpenAPI/API-документация и manifest активного endpoint-verification change, если он уже применён. Откат удаляет новый route и два новых необязательных query-параметра; существующие клиенты не затрагиваются.
