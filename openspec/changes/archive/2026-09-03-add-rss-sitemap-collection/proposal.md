## Why

`src/bp1/adaptive/` умеет ровно одно — адаптироваться к разметке страницы
(лестница деградации `FAST → CRAWL4AI → BROWSER → WAYBACK → STEALTH →
HITL`, LLM подбирает CSS-селекторы). Для источников, которые
`SourceClassifier` уже распознаёт как `SourceType.NEWS` (основная часть
«агрегатор СМИ» из `ABOUT_PROJECT/TZ.md`, раздел 4), это часто избыточно
дорогой путь: значительная доля новостных сайтов публикует RSS/Atom-фид
и/или `sitemap.xml` — стабильный, официально предназначенный для
машинного чтения интерфейс, который не требует ни браузера, ни обхода
антибота, ни LLM для подбора селекторов, и не ломается при каждой смене
вёрстки сайта. Сейчас этот путь никак не используется: обнаружение фида
нигде не пробуется, `SourceType.NEWS` влияет только на оценку сложности,
не на выбор стратегии сбора.

## What Changes

- Новый шаг обнаружения фида для источников `SourceType.NEWS`: проба
  конвенциональных путей (`/rss`, `/feed`, `/atom.xml`, `/sitemap.xml` и
  т.п.) + разбор `<link rel="alternate" type="application/rss+xml|
  application/atom+xml">` в `<head>` уже полученного HTML — до
  HTML-лестницы деградации, не вместо неё.
- Прямое извлечение материалов из найденного RSS/Atom в `ParsedItem[]`
  (`title`/`link`/`pubDate`/`description` → `title`/`url`/`published_at`/
  `text`) — без LLM и без подбора селекторов.
- `sitemap.xml` как источник URL-кандидатов, когда RSS/Atom не найден:
  список статей передаётся в уже существующий deep-fetch
  (`_extract_article_text`), не в новый экстрактор.
- Найденный URL фида/sitemap кэшируется на источник (`UnifiedCache`, тот
  же TTL/паттерн, что у адаптеров) — не передискавери на каждый прогон.
- Самокоррекция: повторные отказы фида (404, невалидный XML, пусто)
  сбрасывают кэш и откатывают источник на обычную HTML-лестницу — фид не
  блокирует сбор, если перестал работать.
- Материалы из фида проходят тот же шаг relevance-ranking
  (`BP1_RELEVANCE_MODE`), что и материалы с HTML-страницы — фид отдаёт
  весь поток сайта, не выборку под конкретного конкурента, поэтому
  оценка релевантности обязательна, а не опциональна.
- Новая зависимость: `feedparser` (разбор RSS/Atom; `sitemap.xml` —
  обычный XML, отдельная библиотека не нужна).

## Capabilities

### New Capabilities
- `bp1/rss-sitemap-collection`: обнаружение и использование RSS/Atom-фида
  и `sitemap.xml` как альтернативного, более дешёвого источника
  материалов для новостных источников BP-1, с откатом на существующую
  HTML-лестницу деградации при отсутствии/отказе фида.

### Modified Capabilities
(нет — `bp1/adaptive-collection-run` описывает поведение прогона на
уровне результата (обработка активных задач, дедуп, устойчивость к
отказу источника), не то, какая именно стратегия добывает контент; её
сценарии не меняются, RSS/sitemap — ещё один способ получить контент
внутри уже описанного контракта)

## Impact

- `src/bp1/adaptive/strategies/orchestrator.py`,
  `src/bp1/adaptive/strategies/engines.py` — новая стратегия/шаг перед
  `FAST` в лестнице деградации, применяется только при
  `SourceType.NEWS`.
- `src/bp1/adaptive/strategies/classifier.py` — `SourceType.NEWS` начинает
  влиять не только на оценку сложности, но и на выбор стратегии.
- `src/bp1/adaptive/core/cache.py` (`UnifiedCache`) — новый вид кэшируемой
  записи (URL фида/sitemap на источник) по образцу кэша адаптера.
- `src/bp1/adaptive/processing/_llm/` — маршрут релевантности переиспользуется
  без изменений (материалы из фида проходят через тот же `score_relevance`).
- `requirements.txt` — новая зависимость `feedparser`.
- Не затрагивает: `SourceType.REGISTRY`/`API`/`SPA`/`UNKNOWN`,
  классический контур `fedresurs_rpa`, BP-2…BP-7.
