## Context

См. `proposal.md` — Why. Инвентаризация через фактическую OpenAPI-схему обнаружила 90 операций: 5 auth, 4 users, 3 showcase, 4 action-items, 5 search-tasks, 59 операций справочников и 10 read-only операций данных конвейера. Импорт приложения и генерация OpenAPI проходят успешно.

Текущий `pytest tests/api -q` даёт `62 passed`, однако поиск по тестам не находит HTTP-клиента или вызовов маршрутов: проверяются нижние слои, но не регистрация роутеров, FastAPI dependencies, разбор запроса и сериализация ответа. Безопасный smoke всех 90 операций без токена и с пустыми телами дал 0 ответов `5xx`; это проверяет только защитный внешний контур, но не успешные авторизованные ветви.

Тесты используют реальную PostgreSQL из `settings.database_url`. Сервисы API вызывают `commit`, поэтому существующая autouse-фикстура заменяет commit на no-op и общий `session` откатывается после теста. Новые HTTP-тесты должны использовать именно эту сессию через dependency override, иначе запрос создаст самостоятельную сессию и сможет оставить данные в БД.

## Goals / Non-Goals

**Goals:**

- получить явное подтверждение для каждой опубликованной операции, а не только покрытие фабрики роутеров;
- проверять реальные FastAPI request/response, dependency injection и response-model validation;
- сделать ролевую матрицу и ожидаемые коды машиночитаемыми;
- находить и точечно исправлять реальные несовпадения между кодом, OpenAPI и описанным контрактом;
- гарантировать отсутствие сетевых отправок и утечки тестовых данных.

**Non-Goals:**

- проводить нагрузочное тестирование или проверять боевые SMTP/Telegram/Redis;
- тестировать визуальное поведение React-интерфейса FastAdmin;
- менять URL, роли или бизнес-правила только ради упрощения тестов;
- исправлять поведение пайплайнов BP-1—BP-6 вне их HTTP-обвязки.

## Decisions

### 1. Вести декларативный manifest всех HTTP-операций

Тестовый manifest будет хранить метод, шаблон пути, публичность, разрешённые роли, ожидаемый успешный код и тип сценария. Отдельный тест сравнит manifest с `app.openapi()['paths']` в обе стороны: исчезнувший и новый незадекларированный endpoint одинаково требуют осознанного обновления контракта. Уникальность `operationId` проверяется там же.

Альтернатива — считать покрытием только вызов generic-фабрики. Она отклонена: можно забыть подключить готовый router, назначить неверный prefix или повредить один конкретный schema/dependency, а фабричный тест останется зелёным.

### 2. Использовать асинхронный ASGI-клиент и dependency overrides

HTTP-запросы выполняются непосредственно против ASGI-приложения без запуска порта. Dependency получения сессии переопределяется генератором, возвращающим общую откатываемую `session`; её `commit` остаётся no-op. Dependency текущего пользователя переопределяется для параметризованной ролевой матрицы, а несколько выделенных auth-тестов проходят настоящий JWT-путь от логина до защищённого endpoint.

Это предпочтительнее синхронного `TestClient`: текущий пробный прогон выдаёт предупреждение о его устаревающей httpx-интеграции, а основной стек и фикстуры проекта уже асинхронные.

### 3. Разделить общие контрактные и предметные endpoint-тесты

Общий набор параметризованно проверяет все 90 операций: регистрацию, отсутствие `5xx`, доступ без токена и отказ запрещённым ролям. Успешные сценарии группируются по одинаковой семантике:

- generic CRUD справочников — таблица из 12 ресурсов с отдельным ожиданием отсутствия DELETE у `region` и публичного GET у `department`;
- read-only данные — пять семейств list/detail;
- search-tasks и source-candidates — собственные фильтры и ограничения;
- auth/users, showcase и action-items — отдельные сценарии из-за ролевой и транзакционной бизнес-логики.

Каждая запись manifest должна иметь хотя бы один успешный HTTP-вызов. Общая проверка будет сообщать непокрытые записи, чтобы «все эндпоинты» не превратилось в выборочное покрытие.

### 4. Создавать минимальные связанные данные через фабрики

Фикстуры создают уникально именованные отделы, пользователей всех ролей и минимальные цепочки моделей для BP-1—BP-6. Списочные тесты проверяют наличие созданной строки и действие фильтра, а не точное количество строк: это сохраняет устойчивость на заполненной локальной БД. Detail/update/delete работают только с идентификаторами строк текущего теста.

Для проверки независимости набор дополнительно прогоняется на чистой временной БД после миграций. Временная БД создаётся и удаляется только командой проверки с явным уникальным именем.

### 5. Мокировать только внешние границы

Почтовая отправка при сбросе пароля и другие доступные из API сетевые вызовы заменяются `AsyncMock` на точке использования. CRUD, сервисы, JWT, схемы ответа и SQLAlchemy остаются настоящими. Для негативного теста провайдера мок выбрасывает контролируемое исключение, чтобы проверить HTTP-контракт ошибки.

### 6. Исправлять только подтверждённые контрактные дефекты

Если endpoint-тест падает, сначала классифицируется источник: неверное ожидание manifest, дефект тестовых данных, ошибка OpenAPI-документации либо production-дефект. Код приложения меняется только в последнем или документальном случае. Публичный путь, метод или политика доступа не меняются скрытно; такое расхождение сначала отражается в spec.

## Risks / Trade-offs

- [90 успешных сценариев создают объёмный тестовый набор] → использовать параметризацию и общие фабрики, сохраняя отдельный идентификатор теста для каждой операции.
- [Dependency override может остаться в глобальном приложении и повлиять на соседний тест] → фикстура клиента очищает overrides в `finally` после каждого теста.
- [Сервисный `commit` сможет записать данные, если HTTP-клиент получит другую сессию] → проверять идентичность внедрённой сессии, оставлять commit no-op и добавлять тест отсутствия строки после rollback.
- [Заполненная рабочая БД может влиять на списки и уникальность] → уникальные значения, проверки по id/включению, плюс повторный прогон на чистой временной БД.
- [Исправление найденного дефекта способно изменить контракт] → совместимые исправления выполняются сразу; несовместимое изменение требует обновления proposal/spec и согласования до реализации.

## Migration Plan

Миграция данных не планируется. Сначала добавляются manifest, клиент и фикстуры, затем контрактные и предметные тесты по группам. После каждого подтверждённого дефекта выполняется минимальное исправление и повторный целевой прогон. Завершение требует `pytest tests/api`, прогона на чистой временной БД, полного `pytest` и статических проверок. Откат удаляет новые тесты и точечные совместимые исправления; рабочая схема и данные остаются без изменений.
