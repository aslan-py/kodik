## Why

Сбор данных начинается не с источника и не с конкурента, а с задачи сбора (`search_task`) — строки, связывающей их пару. Создавать такие строки автоматически в системе некому: их заводит только человек через админку либо сидеры на тестовых данных. Из-за этого цепочка автоматизации обрывается на последнем шаге.

Ярче всего это видно на агенте расширения источников. BP-3 находит новый домен и кладёт его в очередь кандидатов, BP-7 сверяет оценку с порогом и переносит кандидата в справочник источников — и на этом останавливается. Задача сбора по новому источнику не создаётся, поэтому парсинг по нему не начнётся никогда: следующий прогон снова пройдёт ровно по тем же задачам, что и предыдущий. Система умеет сама находить и добавлять источники, но не умеет начать ими пользоваться.

То же происходит при обычной работе со справочниками: аналитик добавил конкурента через админку — по нему ничего не собирается, пока он вручную не заведёт задачи на каждый источник. Число задач при этом растёт как произведение, и держать его в голове невозможно.

## What Changes

- **Перед началом сбора выполняется синхронизация покрытия**: для каждой пары «активный источник + активный конкурент», для которой задачи сбора ещё нет, задача создаётся. Существующие задачи не изменяются.
- **Создаются только задачи без поискового слова** — «парсим источник в лоб». Задачи с поисковым словом остаются целиком ручными: это узкая настройка, которую автоматика не может вывести из справочников.
- **Отключение пары выполняется деактивацией задачи, а не её удалением.** Деактивированная задача считается существующей и заново не создаётся. Удалённая — будет создана снова при следующей синхронизации; это поведение фиксируется в документации явно, потому что оно неочевидно.
- **Результат синхронизации виден в сводке прогона** — сколько задач создано, сколько уже было. Без этого рост числа задач остаётся незаметным до момента, когда прогон становится подозрительно долгим.
- **Синхронизация доступна и отдельно от сбора** — чтобы можно было посмотреть, что получится, до запуска парсинга.

## Capabilities

### New Capabilities
- `bp1/search-task-coverage`: поддержание полноты покрытия задачами сбора — каждая активная пара «источник + конкурент» имеет задачу, без ручного заведения; ручные решения об исключении пар при этом сохраняются.

### Modified Capabilities
_нет_

## Impact

- Код: новый модуль синхронизации покрытия в `src/bp1/`; вызов из `src/bp1/pipeline.py::run_bp1()` перед обходом источников; строка в `core/scripts/SCRIPTS_README.md`.
- БД: миграций нет. Используются существующие ограничения `search_task` — обычное ограничение уникальности и частичный уникальный индекс для задач без поискового слова, которые уже гарантируют отсутствие дублей.
- Объём данных: число задач сбора становится произведением числа активных источников на число активных конкурентов. На демо-справочниках это заметная величина — см. design.md, Risks.
- Замыкает цепочку BP-3 → BP-7 → сбор: найденный агентом источник начинает парситься со следующего прогона без участия человека.
- Порядок: после `connect-real-bp1-parsing` — синхронизация встраивается в точку входа реального сбора, которой до той задачи не существует.
