## Why

ТЗ требует алертинга по приоритетам П1 и П2. Реализовано это через справочник типов значимых событий: правило маршрутизации обязательно указывает тип, тип ловится вхождением ключевого слова в заголовок события. Решение гибче требования ТЗ — порог значимости живёт в справочнике, а не в коде, — но при этом строго уже: базовый сценарий «слать все события приоритета П1 независимо от текста заголовка» выразить нельзя.

На практике это означает пропущенные алерты. Событие получило от LLM приоритет П1 — то есть система признала его требующим немедленной реакции, — но если в его заголовке не нашлось ни одного ключевого слова из справочника, детектор молча пропускает его: `event_type_id` не определился, событие не сматчилось, ни одной строки алерта не создаётся. Заголовки живых новостей формулируются как угодно, а список ключевых слов конечен, поэтому дыра не теоретическая. Особенно заметно это станет после перехода на реальный сбор: сейчас заголовки синтетические и подогнаны под справочник.

## What Changes

- **Правило маршрутизации может не указывать тип события.** Тип становится необязательным полем: правило без типа срабатывает на любое событие подходящего приоритета, без проверки заголовка. Правило с типом работает как раньше.
- **Детектор перестаёт отбрасывать события без совпадения по ключевым словам.** Событие, для которого тип не определился, проверяется на наличие правил, заданных только приоритетом; если такие есть — алерты создаются.
- **Журнал алертов допускает запись без типа события** — когда алерт создан правилом, заданным только приоритетом, и тип при этом не распознан.
- **Разрешается наложение правил.** Если на одно событие срабатывают и правило по типу, и правило по приоритету с одним и тем же получателем и каналом, доставка выполняется один раз — существующее ограничение уникальности в журнале это уже гарантирует, но выбор оставляемой записи не должен зависеть от случайного порядка вставки.
- **Миграция БД**: поле типа события в правиле маршрутизации и в журнале алертов становится необязательным; правила уникальности пересматриваются с учётом того, что в Postgres `NULL` не равен `NULL`.

## Capabilities

### New Capabilities
- `bp5/alert-routing`: правила определения того, кому и по какому событию отправляется алерт. Спеки на маршрутизацию BP-5 до сих пор не было — она заводится здесь и описывает оба вида правил: по типу события и только по приоритету.

### Modified Capabilities
_нет_

## Impact

- Код: `src/bp5/models.py` (необязательный тип в правиле и журнале), `src/bp5/crud.py` (загрузка правил, группировка), `src/bp5/pipeline.py` (поиск правил, сборка строк алерта), `api/schemas/routing_rule.py`, `api/admin/alerting.py`.
- БД: миграция Alembic — снятие NOT NULL с двух полей, пересмотр ограничений уникальности правила маршрутизации. Существующие данные не теряются: все нынешние правила указывают тип и продолжают работать без изменений.
- Справочники: `core/scripts/stages/dictionaries.py` и `simple_dictionaries.py` — при желании дополняются примером правила, заданного только приоритетом.
- Документация: `src/bp5/BP5_README.md` — раздел про порог значимости описывает оба вида правил.
- Совместимость: правила, заведённые ранее, работают как прежде; новая возможность добавляется, существующее поведение не меняется.
- Не зависит от задач по BP-1 — может выполняться в любой момент.
