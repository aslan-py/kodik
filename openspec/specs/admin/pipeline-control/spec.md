# admin/pipeline-control Specification

## Purpose

Запуск этапов конвейера (по отдельности, все подряд, с пересборкой для этапа 2) прямо из уже существующей административной панели — без необходимости открывать терминал.

## Requirements

### Requirement: Кнопка запуска этапа в админке
Для каждого из 7 этапов конвейера админ-панель SHALL предоставлять отдельный элемент управления, который создаёт асинхронный прогон ровно этого этапа. Интерфейс SHALL сразу показывать принятый `run_id` и ссылку на состояние, не удерживая HTTP-запрос до завершения этапа.

#### Scenario: Успешный запуск этапа из админки
- **WHEN** пользователь нажимает элемент управления конкретного этапа при свободном pipeline
- **THEN** создаётся прогон этого этапа, пользователь видит `run_id` со статусом `queued`, а итог позднее отображается в истории

#### Scenario: Этап отклонён по предусловию
- **WHEN** поставленный этап не может выполниться из-за отсутствия данных предыдущего слоя
- **THEN** история прогона показывает терминальную ошибку с той же понятной причиной, что диагностический CLI

#### Scenario: Pipeline занят
- **WHEN** пользователь нажимает запуск этапа во время другого активного прогона
- **THEN** новая задача не создаётся, а интерфейс показывает конфликт и ссылку на активный прогон

### Requirement: Кнопка запуска всего конвейера
Админ-панель SHALL предоставлять отдельный элемент управления, который асинхронно запускает все 7 этапов подряд с поведением «сбой бизнес-логики одного не прерывает остальные». Интерфейс SHALL сразу показывать принятый `run_id`, а постоянная история SHALL отображать итоговую сводку по каждому этапу.

#### Scenario: Запуск всего конвейера из админки
- **WHEN** пользователь нажимает «запустить весь конвейер» при свободном pipeline
- **THEN** создаётся полный прогон в статусе `queued`, а BP1—BP7 позднее выполняются по порядку

#### Scenario: Один этап полного прогона завершился ошибкой
- **WHEN** один из этапов возвращает ожидаемую ошибку
- **THEN** интерфейс показывает ошибку этого этапа, статусы последующих этапов и итоговый статус `partial_failed`

### Requirement: Переключатель пересборки у этапа, который её поддерживает
Рядом с элементом управления этапа, поддерживающего режим пересборки, админ-панель SHALL предоставлять переключатель, включающий этот режим для конкретного запуска.

#### Scenario: Запуск с включённой пересборкой
- **WHEN** пользователь включает переключатель пересборки и нажимает элемент управления этапа
- **THEN** этот этап выполняется в режиме пересборки (уже обработанные данные пересматриваются новыми правилами, без повторного сбора исходных)

#### Scenario: Запуск без пересборки
- **WHEN** пользователь нажимает элемент управления этапа, не включая переключатель пересборки
- **THEN** этап выполняется в обычном режиме, как и раньше

### Requirement: Переключатель выбора реализации у этапа с несколькими реализациями
Рядом с элементом управления этапа, у которого есть и настоящая реализация, и заглушка, админ-панель SHALL предоставлять переключатель выбора реализации для конкретного запуска. Положение переключателя по умолчанию SHALL соответствовать настройке приложения, чтобы нажатие кнопки без изменения переключателя давало то же поведение, что запуск этапа из CLI или по расписанию.

#### Scenario: Запуск с переключателем в положении по умолчанию
- **WHEN** пользователь нажимает элемент управления этапа, не трогая переключатель реализации
- **THEN** выполняется реализация, заданная настройкой приложения, и пользователю показывается результат прогона

#### Scenario: Разовый выбор другой реализации
- **WHEN** пользователь переводит переключатель реализации в положение, отличное от настройки, и нажимает элемент управления этапа
- **THEN** выполняется выбранная реализация, а настройка приложения остаётся прежней и следующий запуск из CLI или по расписанию снова использует её

#### Scenario: Результат показывает, какая реализация отработала
- **WHEN** этап с несколькими реализациями выполнен из админки
- **THEN** в показанном результате видно, была выполнена заглушка или настоящая реализация

### Requirement: Экран пайплайна управляет расписанием
Экран пайплайна SHALL показывать эффективные `enabled`, cron и timezone, источник каждого значения, рассчитанное время следующего запуска и SHALL позволять уполномоченному администратору сохранить override или сбросить его к `.env`.

#### Scenario: Администратор меняет время запуска
- **WHEN** администратор сохраняет валидные cron и timezone
- **THEN** экран показывает новые эффективные значения, источник `admin` и пересчитанное время следующего запуска

#### Scenario: Администратор сбрасывает настройки
- **WHEN** администратор нажимает сброс к настройкам окружения
- **THEN** override удаляется, а экран показывает значения из `.env` с источником `env`

#### Scenario: Невалидный cron введён в форме
- **WHEN** администратор сохраняет невалидное cron-выражение
- **THEN** форма показывает понятную ошибку и не изменяет действующее расписание

### Requirement: Экран пайплайна показывает последние прогоны
Экран пайплайна SHALL показывать последние ручные и плановые прогоны с источником, статусом, временем и переходом к деталям BP1—BP7.

#### Scenario: Просмотр выполняющегося прогона
- **WHEN** пользователь открывает экран при активном прогоне
- **THEN** он видит текущий этап, общий статус и обновляемые статусы этапов

#### Scenario: Просмотр завершённого прогона
- **WHEN** пользователь открывает детали завершённого прогона
- **THEN** он видит упорядоченную сводку результатов и ошибок всех относящихся к прогону этапов
