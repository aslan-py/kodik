## Purpose

Предоставляет фронтенду единый актуальный набор значений для фильтрации витрины и плана действий с корректными идентификаторами и учётом прав пользователя.

## ADDED Requirements

### Requirement: Единый endpoint возвращает варианты для двух экранов
Система SHALL предоставлять защищённый `GET /filter-options`, доступный ролям `viewer`, `analyst` и `admin`. Ответ SHALL содержать отдельные объекты `showcase` и `action_items`, чтобы одноимённые поля с разными типами не смешивались.

#### Scenario: Разрешённый пользователь получает все секции
- **WHEN** пользователь с ролью `viewer`, `analyst` или `admin` вызывает `GET /filter-options` с валидным токеном
- **THEN** сервер возвращает `200` и обе секции `showcase` и `action_items`

#### Scenario: Endpoint вызван без подходящей роли
- **WHEN** endpoint вызывает клиент без токена либо пользователь с ролью `pending`
- **THEN** сервер возвращает соответственно `401` либо `403` и не раскрывает варианты фильтров

### Requirement: Секция showcase соответствует параметрам витрины
Объект `showcase` SHALL содержать массивы `category`, `region`, `priority`, `competitor` и `department`. Значения, кроме `priority`, SHALL состоять из уникальных непустых значений фактической витрины; `priority` SHALL содержать полный набор отображаемых значений `П1`, `П2`, `П3`, `П4` в этом порядке.

#### Scenario: В витрине есть повторяющиеся и пустые значения
- **WHEN** несколько событий имеют одинаковую категорию или регион, а часть событий содержит `null` в необязательном поле
- **THEN** каждое непустое значение появляется в соответствующем массиве один раз, а `null` и пустые строки отсутствуют

#### Scenario: Витрина пока пуста
- **WHEN** в витрине нет событий
- **THEN** массивы значений из данных пусты, а `priority` по-прежнему содержит `П1`, `П2`, `П3`, `П4`

### Requirement: Секция action-items сохраняет значения идентификаторов
Объект `action_items` SHALL содержать `status`, `deadline`, `priority`, `assigned_user_id` и `department_id`. `assigned_user_id` и `department_id` SHALL быть массивами объектов `{value: integer, label: string}`; остальные поля SHALL быть массивами строк, непосредственно пригодных для передачи в одноимённые query-параметры.

#### Scenario: Задача назначена пользователю и отделу
- **WHEN** доступная пользователю задача имеет назначенного сотрудника и ответственный отдел
- **THEN** ответ содержит ID сотрудника и отдела в `value` и их читаемые имена в `label`, без подмены ID именем

#### Scenario: Задача имеет срок
- **WHEN** доступная задача имеет непустой deadline
- **THEN** `deadline` содержит эту дату один раз в ISO-формате `YYYY-MM-DD`

#### Scenario: Варианты статуса
- **WHEN** клиент получает варианты action-items
- **THEN** `status` содержит все допустимые значения `open`, `in_progress`, `done` в порядке рабочего процесса

### Requirement: Варианты action-items соблюдают область видимости
Для роли `viewer` значения `deadline`, `priority`, `assigned_user_id` и `department_id` SHALL вычисляться только из задач собственного отдела пользователя. Для ролей `analyst` и `admin` они SHALL вычисляться из всех задач. Полные enum-значения `status` от наличия строк не зависят.

#### Scenario: Viewer не видит варианты чужого отдела
- **WHEN** viewer получает варианты, а задачи другого отдела содержат уникального исполнителя, срок или приоритет
- **THEN** эти значения отсутствуют в секции `action_items`

#### Scenario: Analyst получает общие варианты
- **WHEN** analyst получает варианты при наличии задач в нескольких отделах
- **THEN** секция `action_items` содержит варианты из всех отделов

### Requirement: Все выданные варианты action-items можно применить
`GET /action-items` SHALL принимать дополнительные необязательные параметры `deadline` и `priority` вместе с существующими фильтрами. `deadline` SHALL точно совпадать со сроком задачи, а `priority` SHALL точно совпадать с отображаемым приоритетом связанного события витрины. Все переданные фильтры SHALL объединяться условием AND и сохранять действующее ограничение viewer своим отделом.

#### Scenario: Фильтрация задач по deadline
- **WHEN** разрешённый пользователь передаёт дату из `action_items.deadline` в `GET /action-items?deadline=YYYY-MM-DD`
- **THEN** сервер возвращает только видимые задачи с точно таким сроком

#### Scenario: Фильтрация задач по приоритету события
- **WHEN** разрешённый пользователь передаёт значение из `action_items.priority` в `GET /action-items?priority=П1`
- **THEN** сервер возвращает только видимые задачи, связанные с событиями витрины указанного приоритета

#### Scenario: Комбинация новых и существующих фильтров
- **WHEN** пользователь одновременно передаёт `priority`, `deadline`, `status` и `department_id`
- **THEN** сервер возвращает только задачи, удовлетворяющие всем переданным условиям и ролевой области видимости

### Requirement: Порядок вариантов детерминирован
Обычные строковые варианты SHALL сортироваться по значению без учёта регистра, варианты `{value, label}` SHALL сортироваться по `label` без учёта регистра, сроки SHALL сортироваться по возрастанию, статусы SHALL следовать порядку `open`, `in_progress`, `done`, а приоритеты SHALL следовать порядку `П1`, `П2`, `П3`, `П4` с пропуском отсутствующих data-derived значений.

#### Scenario: Повторный запрос без изменения данных
- **WHEN** клиент дважды вызывает `GET /filter-options`, а данные между запросами не меняются
- **THEN** массивы вариантов возвращаются в одинаковом порядке
