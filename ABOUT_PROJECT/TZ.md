# Техническое задание

## Система автоматизированной конкурентной разведки

*Описание бизнес-процессов и дорожная карта реализации*

| Назначение документа | Формализация целевых бизнес-процессов системы конкурентной разведки и план их реализации |
|---|---|
| Состав | Раздел I — бизнес-процессы (BP-1…BP-7); Раздел II — дорожная карта (Этапы 0–3) |
| Целевой результат | Автоматический цикл: сбор → категоризация → витрина → BI-дашборд с алертами, без участия аналитика |
| Длительность | ≈ |
| Ключевое ограничение | Развёртывание web/сервер: установка ПО на рабочие места пользователей не требуется |

## 1. Контекст и цель

### 1.1. Процесс «как есть» (AS-IS)

Мониторинг конкурентов выполняется вручную. Аналитик получает новостной поток из агрегатора СМИ, дополняет его данными из открытых источников, вручную объединяет и устраняет дубли, размечает события (категория, приоритет, тональность, регион), перепроверяет факты по 10–15 источникам и переносит результат в таблицу Excel. Далее он рассылает выводы коллегам либо публикует их в витрине.

**AS-IS: Агрегатор СМИ + ручной поиск → ручное объединение → ручная категоризация в Excel → ручная перепроверка → рассылка**

**Проблемы:** процесс не масштабируется на весь реестр конкурентов; результат зависит от занятости одного специалиста; события обнаруживаются с задержкой; аналитик занят рутиной вместо интерпретации.

### 1.2. Процесс «как должно быть» (TO-BE)

Система выполняет весь цикл самостоятельно по расписанию. Аналитик выходит из рутинного цикла и переключается на интерпретацию и принятие решений; за ним сохраняются контроль качества разметки и возможность перепроверки по исходным данным.

**TO-BE: Автосбор по триггерам → очистка и дедупликация → LLM-категоризация → витрина → BI-дашборд + алерты → действие**

### 1.3. Цель и метрики

- **Цель.** Перевести разовый анализ конкурентов в непрерывно обновляемый процесс и исключить ручной труд из цикла сбора и категоризации.
- **Ценность.** Своевременная реакция на события у конкурентов: юридические риски, тендеры, новые клиенты и объекты, расширение и уход с рынка.
- **Метрики (согласуются):** полнота покрытия реестра конкурентов; доля событий, найденных автоматически; отсутствие пропущенных значимых событий; время «событие → алерт»; доля разметки, совпавшей с эталоном.

## 2. Роли и участники процессов

| Роль | Участие в процессах | Процессы |
|---|---|---|
| Система (автоматически) | Сбор, очистка, дедупликация, категоризация, запись в витрину, детект событий, рассылка алертов | BP-1 … BP-5 |
| Аналитик | Владелец правил категоризации; выборочный контроль качества, перепроверка по исходникам, интерпретация | BP-3, BP-6 |
| Отделы-получатели | Принимают алерты и задачи по своей зоне (юридическая, тендерная, коммерческая, PR) | BP-5, BP-6 |
| Руководитель | Получает сводную аналитику и алерты высокого приоритета, принимает решения | BP-6 |
| Администратор системы | Реестр конкурентов и источников, расписание, доступы | BP-7 |

**РАЗДЕЛ I. БИЗНЕС-ПРОЦЕССЫ**

Каждый процесс описан по схеме: назначение → триггер → вход → шаги → выход → правила и требования.

## BP-1 · Сбор данных из источников

**Назначение:** Автоматическое получение сведений о конкурентах из внешних источников по заданным триггерам.

| Параметр | Значение |
|---|---|
| Триггер | Наступление времени по расписанию (заданный интервал) либо ручной запуск администратором. |
| Вход | Реестр конкурентов; наборы триггеров (наименования, ключевые упоминания, темы); перечень подключённых источников. |
| Выход | Массив сырых материалов с атрибутами источника, сохранённый в хранилище исходных данных. |

**Шаги процесса**

- Система формирует поисковые запросы по триггерам для каждого источника.
- Выполняется обращение к источникам: агрегатор СМИ (первичный поток), новостной поиск, вакансии, судебные и арбитражные реестры, закупки, социальные сети и мессенджеры (в т. ч. перепубликации), реестры юридических лиц и финансовой отчётности.
- Полученные материалы сохраняются в исходном виде (сырьё) с указанием источника, ссылки и времени получения.
- Фиксируется статус выгрузки по каждому источнику; при сбое запускается повтор и формируется техническое уведомление.
**Правила и требования**

- Источники делятся по типу доступа: открытые и бесплатные API; условно-бесплатные API с лимитами; источники, доступные только через RPA-парсинг; источники по платной лицензии.
- Для источников с RPA-доступом применяются прокси (не с корпоративных IP-адресов), ротация User-Agent и задержки между запросами.
- Исходные материалы хранятся для последующей перепроверки; глубина хранения задаётся регламентом.
- Инкрементальность: повторно полученные материалы сверяются по контрольной сумме и помечаются как новые, изменённые или без изменений.

## BP-2 · Очистка, дедупликация и фильтрация шума

**Назначение:** Приведение сырых материалов к единому виду и отсечение дублей и нерелевантного контента до этапа категоризации.

| Параметр | Значение |
|---|---|
| Триггер | Появление новых материалов в хранилище исходных данных (выход BP-1). |
| Вход | Массив сырых материалов. |
| Выход | Очищенный, дедуплицированный поток событий, готовый к категоризации. |

**Шаги процесса**

- Нормализация: извлечение текста, приведение форматов даты, региона и наименования источника к справочникам.
- Дедупликация: склейка повторов одного события (перепечатки в разных СМИ) по заголовку, ссылке и содержанию.
- Фильтрация по чёрным спискам доменов (заказные и компрометирующие ресурсы исключаются полностью).
- Отсечение нерелевантного контента по стоп-темам и по ложным срабатываниям ключевых слов.
- Ограничение инфраструктурного шума: единичный объект не должен занимать непропорциональную долю выборки; применяются лимиты по темам.
**Правила и требования**

- Правила фильтрации выносятся в настраиваемые справочники и изменяются без доработки кода.
- Отсеянные материалы не удаляются, а помечаются статусом — для возможности разбора и настройки правил.

## BP-3 · Категоризация событий

**Назначение:** Автоматическая разметка каждого события по правилам, эквивалентным текущей ручной методике аналитика.

| Параметр | Значение |
|---|---|
| Триггер | Поступление очищенного события (выход BP-2). |
| Вход | Очищенное событие; эталонные правила разметки; справочники значений. |
| Выход | Событие с полным набором атрибутов разметки. |

**Шаги процесса**

- Языковая модель анализирует событие и присваивает атрибуты разметки.
- Определяется приоритет по четырёхуровневой шкале (см. правила).
- Определяются категория события, тональность, регион, затрагиваемый конкурент или объект.
- Формируются требуемое действие и срок реакции; определяется ответственный отдел.
- Событие с полной разметкой передаётся в витрину (BP-4).
**Правила и требования**

- **Шкала приоритетов:** П1 — реагировать немедленно (юридический или репутационный риск, прямая угроза позициям), срок 48 часов; П2 — отслеживать (активность конкурента, требует мониторинга), срок 1 неделя; П3 — к сведению (фоновая активность); П4 — игнорировать (шум, нерелевантный контент).
- **Атрибуты события:** дата · заголовок · источник · регион · конкурент/объект · приоритет · категория · тональность · медиа-метрики (охват, заметность, индекс, вовлечённость) · требуемое действие · срок · ответственный отдел · комментарий.
- **Категории событий:** надзорная санкция и юридический риск; репутационный риск; PR-активность конкурента; системная проблема (возможность для входа); признание качества и конкурсы; косвенное упоминание; информационный шум.
- **Контроль качества:** разметка валидируется против эталонного набора; расхождения возвращаются в правила категоризации.

## BP-4 · Хранение и витрина данных

**Назначение:** Накопление размеченных событий в структуре, пригодной для аналитики и визуализации.

| Параметр | Значение |
|---|---|
| Триггер | Поступление размеченного события (выход BP-3). |
| Вход | Размеченные события; исходные материалы. |
| Выход | Актуальная витрина данных, доступная BI-системе по прямому подключению. |

**Шаги процесса**

- Событие записывается в витрину — плоскую аналитическую таблицу с полным набором атрибутов.
- Исходный материал сохраняется в хранилище сырья со ссылкой из витрины (возможность перепроверки).
- Обновляются профили конкурентов: агрегаты по активности, регионам, приоритетам и категориям.
- Витрина публикуется как источник данных для BI-слоя.
**Правила и требования**

- Витрина ведётся в СУБД; запись выполняется инкрементально, без полной перезагрузки.
- Из любой строки витрины доступен переход к исходному материалу.
- Структура витрины фиксируется до начала разработки BI-слоя (контракт данных).

## BP-5 · Обнаружение событий и алертинг

**Назначение:** Своевременное уведомление ответственных о значимых событиях у конкурентов.

| Параметр | Значение |
|---|---|
| Триггер | Появление в витрине события, удовлетворяющего правилам детектора. |
| Вход | Витрина событий; правила детектора; матрица маршрутизации по отделам. |
| Выход | Отправленный алерт и задача с ответственным отделом и сроком. |

**Шаги процесса**

- Детектор проверяет событие на соответствие типам значимых событий: судебный или надзорный риск; выигранный тендер; крупный контракт; новый клиент, объект или регион; активный наём; расширение; слияние или поглощение; закрытие объекта.
- При срабатывании формируется алерт с указанием приоритета и требуемого действия.
- Алерт направляется в согласованные каналы (мессенджер, электронная почта, отметка в дашборде).
- Алерт маршрутизируется на ответственный отдел согласно матрице маршрутизации.
**Правила и требования**

- Приоритет П1 доставляется незамедлительно; П2 — в составе регулярной сводки.
- Набор типов событий и матрица маршрутизации настраиваются без доработки кода.

## BP-6 · Аналитика и принятие решений

**Назначение:** Предоставление пользователям готовой аналитической картины рынка и конкурентов.

| Параметр | Значение |
|---|---|
| Триггер | Обновление витрины; обращение пользователя к дашборду; поступление алерта. |
| Вход | Витрина данных; профили конкурентов; входящие алерты. |
| Выход | Принятые решения и отработанные задачи; актуальная картина рынка. |

**Шаги процесса**

- Пользователь открывает BI-дашборд: карта рынка по регионам, паспорт конкурента, лента событий по приоритетам.
- Аналитик при необходимости проваливается в исходный материал для перепроверки факта.
- По событиям приоритета П1–П2 формируется план действий: задача → ответственный отдел → срок → ожидаемый результат → статус.
- Отделы отрабатывают задачи; статус отражается в системе.
**Правила и требования**

- Доступ к данным разграничивается по ролям (права вплоть до уровня строк).
- Дашборды доступны через веб-интерфейс; установка ПО на рабочие места пользователей не требуется.

## BP-7 · Сопровождение и расширение системы

**Назначение:** Поддержание актуальности реестров, источников и правил без остановки работы системы.

| Параметр | Значение |
|---|---|
| Триггер | Появление нового конкурента, источника или изменение правил разметки; сбой источника. |
| Вход | Реестр конкурентов; перечень источников; правила категоризации и фильтрации. |
| Выход | Актуальные реестры и правила; расширенный перечень источников. |

**Шаги процесса**

- Администратор добавляет нового конкурента или триггер в реестр — система включает его в следующий цикл сбора.
- Агент расширения источников автоматически формирует поисковые запросы, находит новые публично доступные источники и перепубликации и предлагает их к добавлению.
- Новый источник проходит модерацию и подключается к сбору.
- Правила категоризации и фильтрации корректируются по результатам контроля качества.
- При сбое источника формируется техническое уведомление; сбор по остальным источникам продолжается.
**Правила и требования**

- Добавление конкурента или источника не требует доработки кода.
- Агент предлагает источники, но подключение выполняется после модерации.
- Отказ одного источника не останавливает конвейер.

## 3. Нефункциональные требования

- **Автономность.** Полный цикл выполняется по расписанию без участия человека; самообновление данных.
- **Развёртывание.** Веб/серверная архитектура; на рабочих местах пользователей ПО не устанавливается.
- **Отказоустойчивость сбора.** Повторы при сбоях, уведомления о недоступности источников, отказ одного источника не блокирует остальные.
- **Прозрачность.** От любого показателя доступен переход к исходному материалу.
- **Настраиваемость.** Реестры, триггеры, правила фильтрации и маршрутизации изменяются через справочники.
- **Разграничение доступа.** Ролевая модель доступа к данным и дашбордам.
- **Регламент обработки.** Целевой уровень: не менее 95% источников обработано к заданному времени суток.
- **Юридическая чистота.** Используются официальные API и публично доступные данные; лицензионные источники — при наличии лицензии у Заказчика.

## 4. Источники: классификация по типу доступа

Объём работ по интеграции определяется не числом конкурентов, а числом источников: один источник — одна интеграция.

| Тип доступа | Сложность | Состав |
|---|---|---|
| Открытый / бесплатный API | Низкая | Вакансии; реестры юридических лиц; сведения о доменах; социальные сети и мессенджеры (по токену); государственные закупки |
| Условно-бесплатный API | Низкая — средняя | Поисковые сервисы по СМИ (лимиты на количество запросов в сутки) |
| Только RPA-парсинг | Высокая | Судебные и арбитражные реестры; сайты конкурентов; реестры интеллектуальной собственности (требуются прокси, обход защиты, эмуляция действий пользователя) |
| Платная лицензия | Зависит от лицензии | Агрегатор СМИ; коммерческие системы проверки контрагентов и финансовой отчётности |

**Примечание.** Часть источников, доступных только через RPA (арбитраж, интеллектуальная собственность), может быть заменена официальными API коммерческих систем проверки контрагентов — при наличии соответствующей лицензии у Заказчика. Это сокращает объём и хрупкость RPA-интеграций.

| Этап 1 | Работающая разведка на одном источнике: BP-1 → BP-2 → BP-3 → BP-4 → дашборд |  |  |  |

### Этап 0 — Готовая основа

**Срок:**

**Работающий слой:** Инфраструктура развёрнута, правила категоризации согласованы — система готова принимать и размечать данные.

- Настроены инфраструктура, конвейер обработки и модель данных (структура витрины).
- Зафиксированы реестр конкурентов, триггеры, перечень источников и таксономия приоритетов П1–П4.
- Сформированы и проверены на эталоне правила категоризации.
**Процессы этапа:** Проектирование BP-1 … BP-4; полное определение BP-3.

### Этап 1 — Работающая разведка на одном источнике (демо)

**Срок:**

**Работающий слой:** Полный цикл по одному источнику работает вживую — от сбора до дашборда.

- Автоматический сбор по триггерам; очистка и дедупликация.
- Категоризация по приоритетам П1–П4 с атрибутами события.
- Запись в витрину и отображение в BI-дашборде: карточка конкурента, лента событий, регион на карте.
- **Точка контроля:** результат оценивается на эталонном наборе до расширения на полный объём.
**Процессы этапа:** BP-1, BP-2, BP-3, BP-4 — на ограниченном контуре (один источник).

### Этап 2 — Полное покрытие сбора и алертинг

**Срок:**

**Работающий слой:** Система мониторит весь реестр конкурентов по всем источникам, фильтрует шум и рассылает алерты.

- Подключены все согласованные источники (по классификации раздела 4).
- Работает полная фильтрация шума: дубли, чёрные списки, стоп-темы, лимиты.
- Витрина в СУБД и хранение исходных данных; детектор событий и алерты в согласованные каналы.
- Маршрутизация задач по ответственным отделам.
**Процессы этапа:** BP-1, BP-2 — полный контур; BP-4, BP-5 — в промышленной эксплуатации.

### Этап 3 — Полный самостоятельный продукт

**Срок:**

**Работающий слой:** Система работает автономно, с полной аналитикой; аналитик выведен из рутинного цикла.

- Автосбор по расписанию без ручного запуска.
- Агент самостоятельно находит и предлагает новые публично доступные источники.
- Полный BI: карта рынка, паспорт конкурента, ролевая модель доступа.
- Приёмочное тестирование на полном объёме, обучение команды, передача в эксплуатацию.
**Процессы этапа:** BP-6, BP-7; полный цикл BP-1 … BP-7 в автономном режиме.
