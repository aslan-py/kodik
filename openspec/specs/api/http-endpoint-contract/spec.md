# api/http-endpoint-contract Specification

## Purpose

Определяет проверяемый HTTP-контракт FastAPI-приложения: опубликованные маршруты, права доступа, успешные ответы и предсказуемые клиентские ошибки для всех API-семейств.

## Requirements

### Requirement: Все заявленные HTTP-операции доступны в приложении
Приложение SHALL регистрировать каждую заявленную операцию API с её методом и путём, а OpenAPI-схема SHALL содержать уникальное описание каждой операции. Swagger UI, ReDoc и смонтированная веб-админка SHALL быть доступны по документированным путям.

#### Scenario: Получение OpenAPI-схемы
- **WHEN** клиент запрашивает `/openapi.json`
- **THEN** сервер возвращает успешный ответ со всеми зарегистрированными операциями и без повторяющихся идентификаторов операций

#### Scenario: Открытие документации и админки
- **WHEN** клиент открывает `/docs`, `/redoc` или `/admin`
- **THEN** сервер возвращает страницу либо документированный редирект на страницу соответствующего интерфейса без внутренней ошибки

### Requirement: Доступ соответствует ролевой политике
Каждая операция SHALL соблюдать заявленную политику доступа для публичного клиента и ролей `pending`, `viewer`, `analyst` и `admin`. Отсутствующий или недействительный токен SHALL давать `401`, а аутентифицированная роль без необходимых полномочий SHALL получать `403`, кроме явно документированных случаев сокрытия чужого объекта через `404`.

#### Scenario: Публичная операция без токена
- **WHEN** клиент без токена вызывает публичную операцию авторизации, чтения отделов или публичной документации
- **THEN** запрос обрабатывается без требования JWT

#### Scenario: Защищённая операция без токена
- **WHEN** клиент без токена вызывает защищённую операцию
- **THEN** сервер возвращает `401` в стандартном формате ошибки и не выполняет целевое действие

#### Scenario: Роль не имеет полномочий
- **WHEN** аутентифицированный пользователь вызывает операцию, недоступную его роли
- **THEN** сервер возвращает предусмотренный политикой `403` или маскирующий чужой объект `404` и не изменяет данные

#### Scenario: Роль имеет полномочия
- **WHEN** аутентифицированный пользователь с разрешённой ролью вызывает операцию с корректными данными
- **THEN** сервер выполняет действие и возвращает документированный успешный код

### Requirement: Каждая операция возвращает ответ заявленной схемы
Для корректного запроса каждая операция SHALL возвращать документированный HTTP-код и тело, соответствующее своей OpenAPI-схеме. Это требование SHALL охватывать авторизацию, пользователей, витрину, план действий, задачи поиска, справочники и read-only данные этапов конвейера.

#### Scenario: Успешное чтение списка и объекта
- **WHEN** разрешённый клиент запрашивает список с поддерживаемыми фильтрами или существующий объект по идентификатору
- **THEN** сервер возвращает `200`, тело заявленной схемы и данные, соответствующие фильтрам и области видимости пользователя

#### Scenario: Успешное создание
- **WHEN** разрешённый клиент отправляет корректное тело в операцию создания
- **THEN** сервер возвращает документированный код создания и созданный объект заявленной схемы

#### Scenario: Успешное частичное обновление
- **WHEN** разрешённый клиент отправляет допустимый непустой набор изменяемых полей существующего объекта
- **THEN** сервер возвращает `200`, изменяет только переданные поля и возвращает обновлённый объект заявленной схемы

#### Scenario: Мягкое удаление справочника
- **WHEN** разрешённый клиент удаляет существующий элемент справочника, поддерживающего удаление
- **THEN** сервер возвращает `200`, оставляет строку в хранилище и переводит её в неактивное состояние

### Requirement: Ошибочные запросы завершаются предсказуемо
API SHALL отклонять неверное тело, параметры, отсутствующие объекты и нарушения уникальности документированными ответами `4xx`. Покрытые валидные и ошибочные клиентские сценарии SHALL NOT завершаться необработанным `5xx`.

#### Scenario: Невалидное тело или параметр
- **WHEN** клиент передаёт тело или параметр, не соответствующий схеме операции
- **THEN** сервер возвращает `422` со стандартным описанием ошибок валидации и не изменяет данные

#### Scenario: Объект не существует
- **WHEN** разрешённый клиент запрашивает или изменяет отсутствующий объект
- **THEN** сервер возвращает документированный `404` без внутренней ошибки

#### Scenario: Нарушение уникальности или связности
- **WHEN** разрешённый клиент создаёт или изменяет данные с документированным конфликтом уникальности либо связности
- **THEN** сервер возвращает `409`, сохраняет прежнее согласованное состояние и не раскрывает внутреннюю ошибку БД

### Requirement: Внешние побочные эффекты контролируются
Операции API, способные отправлять сообщения во внешние системы, SHALL выполнять отправку только в предусмотренном сценарием случае, а сбой внешнего провайдера SHALL обрабатываться согласно документированному контракту без неконтролируемого изменения данных.

#### Scenario: Запрос сброса пароля существующего пользователя
- **WHEN** клиент запрашивает сброс пароля для существующего активного email
- **THEN** сервер создаёт действующий одноразовый код и инициирует ровно одно сообщение на адрес этого пользователя

#### Scenario: Запрос сброса для неизвестного email
- **WHEN** клиент запрашивает сброс пароля для email, которого нет в системе
- **THEN** сервер возвращает тот же публичный ответ, что и для существующего email, но не инициирует отправку сообщения
