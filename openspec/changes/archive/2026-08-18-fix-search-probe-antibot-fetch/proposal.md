## Why

Перебор поисковых параметров (`SearchUrlProber`) всегда получает страницу
через голый HTTP-запрос (`urllib`), даже когда классификация источника уже
известна и говорит, что сайт защищён антиботом и требует браузерную
стратегию. Для таких источников (пример: `rbc.ru`, QRATOR) пробер не
получает валидного ответа ни на один параметр перебора — весь перебор
проваливается и система падает в наивный fallback-шаблон `/search?q=`,
независимо от того, какой параметр реально понимает сайт (для `rbc.ru` это
`query=`). Источник с уже подтверждённой антибот-защитой каждый раз
собирается по заведомо неверному URL: выдача не фильтруется по конкуренту,
в витрину попадают нерелевантные материалы вместо новостей о конкуренте.

## What Changes

- Перебор поисковых параметров получает доступ к уже резолвленной
  классификации источника (`has_antibot`/`is_spa`/`recommended_strategy`) и
  может эскалировать fetch-транспорт до `AgenticOrchestrator
  .fetch_with_degradation` для источников, которым голый HTTP-запрос
  заведомо не подходит — вместо того чтобы всегда использовать один и тот
  же fetch независимо от источника.
- Для источников, требующих эскалации, число перебираемых кандидатов
  сокращается (дорогой fetch не гоняется по всем ~13 вариантам подряд —
  только по приоритетным: подсказка из регистрации источника + 2-3 самых
  частых параметра).
- Проверка поискового эндпоинта при регистрации источника (`add-source`)
  тоже получает эскалацию — рабочий параметр для антибот-защищённого
  источника определяется один раз при регистрации и переиспользуется всеми
  конкурентами на этом источнике через уже существующий механизм
  `prefer_param`.
- Устраняется дублирующий вызов перебора поисковых параметров для одной и
  той же задачи сбора: сейчас `probe()` выполняется дважды с разными
  результатами (один раз — только для определения варианта имени
  конкурента, второй — для реального URL парсинга), что позволяет двум
  прогонам разойтись во мнениях о том, какой параметр рабочий.

## Capabilities

### Modified Capabilities

- `bp1/adaptive-search-probing`: перебор вариантов поиска должен учитывать
  классификацию источника при выборе fetch-транспорта для получения
  страницы кандидата, а не всегда использовать один и тот же
  HTTP-запрос независимо от того, что известно об источнике.

## Impact

- `src/bp1/adaptive/integration/search_probe.py` — `SearchUrlProber`, выбор
  fetch-транспорта и число перебираемых кандидатов.
- `src/bp1/adaptive/integration/runner/core.py`,
  `src/bp1/adaptive/integration/runner/probing.py` — `AdaptiveRunner`:
  передача классификации в пробер, устранение дублирующего вызова
  `probe()`.
- `src/bp1/adaptive/integration/sources.py` —
  `SourceRegistrationService.probe_search_endpoint`.
- `tests/bp1/adaptive/test_search_probe.py`,
  `tests/bp1/adaptive/test_runner_source_aware.py` — тесты на
  антибот-сценарий перебора.
