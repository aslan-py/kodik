## Context

См. proposal.md — Why. Два варианта обсуждались: флаг в `.env` (например, `BP1_LOW_VARIANT`), переключающий объём внутри существующего `core/scripts/stages/bp1.py`, либо отдельный, всегда-минимальный сидер, не связанный с полным демо-скриптом.

## Goals / Non-Goals

**Goals:**
- Заглушка этапа 1 в пайплайне всегда дешёвая, без ручных переключателей.
- Полный демо-датасет остаётся доступным как есть, без риска случайно получить не тот объём.

**Non-Goals:**
- Не трогаем `core/scripts/stages/bp1.py` и его датасет (`news_data.py`, `SNAPSHOTS`) — они не источник данных для нового стаба, только вдохновение по структуре (`item()`, `make_raw_data()`).

## Decisions

**Отдельный минимальный сидер, не флаг.** Сравнение вариантов:

| | Флаг `BP1_LOW_VARIANT` | Отдельный минимальный стаб (выбрано) |
|---|---|---|
| Риск | Одна и та же команда `python -m core.scripts.stages.bp1` даёт разный результат в зависимости от невидимого состояния `.env` — легко случайно засеять не тот объём | Команда сама по себе определяет объём, переключать нечего |
| Согласованность | Единственный такой условный сидер в проекте | Уже так устроены заглушки BP-6/BP-7 (`core/scripts/stages/bp6.py`/`bp7.py`) — маленький целевой сидер, отдельный от «полного» |
| Сложность | Нужно ветвить генерацию внутри уже сложного `bp1.py`, обходя `assert`-проверку полноты сценариев | Новый файл на порядок проще: 1 конкурент, 2 новости, без «грязного» текста (грязь тестирует BP-2, тут не нужна) |

Решение принято по итогам обсуждения с пользователем (не техническое требование, а выбор архитектуры).

**Источник двух новостей.** `News.is_clean` (`core/scripts/stages/news_data.py`) уже помечает, какие строки CSV проходят фильтры BP-2 без отсева — берём любые 2 таких `id` для одного конкурента напрямую из существующего `news_dataset.csv`, не выдумываем новый контент. Конкретные `id`/конкурент фиксируются при реализации (`tasks.md`).

## Risks / Trade-offs

- [Риск] Два места с похожей, но не идентичной логикой генерации `raw_item`/`SearchTask` (полный `bp1.py` и новый минимальный стаб) → Митигация: минимальный стаб держим предельно простым (без «грязного» текста, без сценариев тай-брейка/дублей), не пытаемся переиспользовать сложную логику `bp1.py` — дублирование тут дешевле связанности с датасетом, рассчитанным на другую задачу (демонстрация фильтров BP-2).
