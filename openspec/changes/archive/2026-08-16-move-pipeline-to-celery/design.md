## Context

См. `proposal.md` — Why. В проекте уже есть единый Celery app с Redis broker/result backend и один BP1 task, но task autodiscovery не настроен, Beat пуст, а API/админка вызывают синхронный `core.pipeline.runner`. Runner и registry уже определяют порядок BP1—BP7 и правило продолжения после ошибки. Docker Compose сейчас поднимает только инфраструктурные PostgreSQL/Redis-сервисы; образ приложения и процессы API/Celery отсутствуют.

BP1 использует браузерный парсинг и локальные данные, поэтому его worker имеет иные ресурсные и системные требования, чем BP2—BP7. Состояние выполнения нельзя строить только на Celery result backend: оно должно переживать очистку Redis и быть доступно API с предметными статусами.

## Goals / Non-Goals

**Goals:**

- Сделать очередь единственным production-путём запуска из API, админки, Beat и обычного CLI.
- Сохранить нынешний порядок этапов и существующие реализации, добавив над ними надёжную оркестрацию и наблюдаемость.
- Применять изменения расписания из админки без перезапуска Beat и иметь однозначный fallback к `.env`.
- Разделить ресурсоёмкий BP1, остальные этапы и управляющие задачи по очередям и процессам.
- Обеспечить воспроизводимый локальный/серверный запуск всей инфраструктуры через Compose.

**Non-Goals:**

- Переписывать бизнес-алгоритмы BP1—BP7 или менять их порядок.
- Делать этапы одного полного прогона параллельными.
- Запускать несколько pipeline одновременно, даже если они относятся к разным этапам.
- Использовать Flower как источник предметной истории или как публичную пользовательскую панель.
- Заменять PostgreSQL/Redis либо внедрять внешний workflow engine.

## Decisions

### 1. Uvicorn, worker, Beat и Flower — отдельные процессы

Один образ приложения используется несколькими Compose-сервисами: `api`, `celery-worker`, `celery-worker-bp1`, `celery-beat`, `flower`. Uvicorn только принимает HTTP-запросы и ставит задачи; он не порождает Celery-процессы. Beat запускается ровно в одном экземпляре. BP1-образ/слой содержит браузер и системные зависимости Playwright и получает существующий постоянный volume данных BP1.

Альтернатива — запускать worker/Beat вместе с uvicorn — отклонена: жизненные циклы, масштабирование и healthchecks смешиваются, рестарт API способен прервать задачи, а несколько API-реплик дублируют scheduler. Встраивание Beat во worker также не используется в production.

### 2. Три именованные очереди и два типа worker'ов

Маршрутизация фиксируется явно:

- `pipeline.control`: dispatcher расписания, финализатор, errback/watchdog;
- `pipeline.bp1`: wrapper BP1 и существующие BP1 parser tasks;
- `pipeline.stages`: wrappers BP2—BP7.

Общий worker подписывается на `pipeline.control,pipeline.stages`, BP1 worker — на `pipeline.bp1`. Для тяжёлых задач используются ограниченная concurrency, `worker_prefetch_multiplier=1`, late acknowledgement и ограниченные soft/hard time limits. JSON остаётся форматом сериализации.

Альтернатива — одна default queue — проще, но долгий BP1 может занять все слоты и задержать финализацию/расписание. Отдельный worker на каждый BP пока избыточен; маршруты позволяют добавить его позднее.

### 3. PostgreSQL — источник истины о прогоне

Добавляются `PipelineRun`, `PipelineStageRun` и singleton `PipelineSchedule`.

`PipelineRun` хранит идентификатор, тип (`single`/`all`), выбранный этап, источник (`admin`/`api`/`cli`/`beat`), инициатора, снимок параметров, root task id, запланированный слот, статус, сводный результат/ошибку и timestamps. Статусы: `queued`, `running`, терминальные `succeeded`, `partial_failed`, `failed`, `rejected`, `stale`.

`PipelineStageRun` уникален по `(pipeline_run_id, stage)`, хранит Celery task id, статус, число попыток, выбранную реализацию/stub, результат/ошибку и timestamps. Для полного запуска семь строк создаются заранее, чтобы API сразу показывал весь план.

`PipelineSchedule` хранит nullable override для enabled/cron/timezone, `last_scheduled_for`, автора и время изменения. Эффективное значение вычисляется по каждому полю как `DB override ?? env default`.

Celery result backend остаётся диагностическим механизмом Celery, но API читает состояние из PostgreSQL. Альтернатива — AsyncResult/Redis как история — отклонена из-за TTL/очистки, слабого предметного контракта и невозможности надёжно связать этапы.

### 4. Глобальная блокировка активного прогона обеспечивается БД

У `PipelineRun` есть nullable `active_slot`: для `queued`/`running` он равен константе `1`, для терминальных статусов — NULL; уникальный индекс разрешает только одну ненулевую строку. Создание прогона и захват slot выполняются одной транзакцией. Конфликт возвращает существующий активный `run_id`; Beat записывает пропущенный занятый слот без создания исполняемой цепочки.

Финализатор освобождает slot. Периодический watchdog переводит прогон в `stale`, если heartbeat/изменение этапа старше `PIPELINE_STALE_TIMEOUT_SECONDS`, после проверки Celery state. Это предотвращает вечную блокировку после убийства worker'а.

Альтернатива — Redis lock — отклонена как второй источник истины с риском истечения lock во время долгого BP1. PostgreSQL advisory lock неудобен для lock, который должен переживать разные транзакции и процессы.

### 5. Полный прогон строится как chain из устойчивых wrapper-задач

Для одиночного запуска ставится один stage wrapper и финализатор. Для полного — Celery `chain` из BP1…BP7 и финализатора. Wrapper открывает собственную DB-сессию, атомарно переводит этап в `running`, вызывает существующий `run_stage`, сохраняет результат и возвращает компактный envelope следующему wrapper'у.

Ожидаемые ошибки бизнес-логики и предусловий wrapper перехватывает, сохраняет как `failed` и **возвращает** failure envelope. Он не выбрасывает исключение, поэтому chain продолжает следующие этапы. Необработанная инфраструктурная ошибка использует ограниченный retry; после исчерпания срабатывает errback/watchdog и прогон становится `failed`/`stale`. Ни одна Celery-задача не вызывает синхронный `.get()` другой задачи.

Повторно доставленный wrapper сначала блокирует свою stage-row и при терминальном статусе возвращает сохранённый envelope без повторного вызова бизнес-кода. Это даёт дедупликацию на уровне orchestration; бизнес-идемпотентность самих BP остаётся дополнительной защитой.

Альтернатива — один большой task с последовательным прямым runner — не даёт маршрутизации BP1, отдельных task ids и прозрачности по этапам. Chord/group не подходят, потому что порядок строгий и параллелизм запрещён.

### 6. Beat вызывает частый dispatcher, а cron хранится как эффективная настройка

В `beat_schedule` находится одна статическая запись dispatcher с интервалом `PIPELINE_SCHEDULE_POLL_SECONDS` (по умолчанию 30 секунд). Dispatcher читает effective enabled/cron/timezone, вычисляет последний наступивший cron slot и внутри транзакции блокирует singleton schedule-row. Если slot новее `last_scheduled_for`, он сначала резервируется, затем предпринимается создание полного прогона.

Значения `.env` (`PIPELINE_SCHEDULE_ENABLED`, `PIPELINE_SCHEDULE_CRON`, `PIPELINE_SCHEDULE_TIMEZONE`) — defaults. Nullable DB override меняется API/админкой и подхватывается на следующем poll без рестарта. Сброс удаляет override. API одинаковым вычислителем возвращает источник каждого поля и `next_run_at`.

Альтернатива — динамически переписывать `app.conf.beat_schedule` — требует рестарта/специального scheduler backend. Отдельная crontab-запись на каждое изменение также усложняет дедупликацию. Polling dispatcher прост и достаточно точен для pipeline с минутной гранулярностью cron.

### 7. API и админка работают через общий orchestration service

Общий сервис валидирует параметры, атомарно создаёт run rows и публикует canvas после commit. Если publish не удался, run переводится в `failed`, slot освобождается, а клиент получает наблюдаемый `run_id` с ошибкой. Production CLI вызывает тот же сервис и печатает `run_id`; прямой `runner` остаётся доступен только через явно названный диагностический режим.

HTTP-контракт:

- `POST /pipeline/runs` — полный прогон, HTTP 202;
- `POST /pipeline/stages/{stage}/runs` — один этап, HTTP 202;
- `GET /pipeline/runs` и `GET /pipeline/runs/{run_id}` — история/детали;
- `GET /pipeline/schedule` и `PATCH /pipeline/schedule` — эффективное расписание и override/reset.

Просмотр разрешён ролям чтения, запуск и PATCH — текущим управляющим ролям admin/analyst. Админ-кнопки возвращают run id, а экран Pipeline Dashboard показывает schedule card и последние прогоны. Это дополняет change `reorganize-admin-navigation`: новый блок размещается на том же верхнем экране, не создавая второй раздел Pipeline.

### 8. Flower — отдельный защищённый operational service

Flower запускается командой общего Celery app в отдельном Compose-сервисе, использует basic auth из обязательных env secrets и healthcheck. Порт по умолчанию предназначен для локального/внутреннего доступа; для внешней публикации документация требует reverse proxy с TLS и дополнительным контролем доступа. Предметные результаты остаются в приложении, Flower нужен для worker/queue/task telemetry.

## Risks / Trade-offs

- [Публикация в broker происходит после DB commit и может упасть] → run переводится в `failed`, slot освобождается; периодический reconciler может повторно публиковать только явно `queued` записи без task id.
- [Worker погиб после бизнес-записи, но до обновления stage status] → wrapper и BP должны опираться на идемпотентные ключи; повторная доставка сверяет stage-row, watchdog помечает неразрешимый прогон.
- [Ожидаемая ошибка ошибочно классифицирована как инфраструктурная] → ввести типизированные ошибки preflight/business/transient и тестировать retry-матрицу.
- [Долгий BP1 задерживает расписание] → отдельная очередь/worker, глобальная блокировка и явная запись пропущенного слота; автоматического накопления backlog нет.
- [Cron/timezone дают неоднозначность на переходах DST] → хранить UTC timestamps слотов, рассчитывать cron в указанной IANA timezone и дедуплицировать по UTC slot.
- [Flower раскрывает аргументы задач] → не передавать секреты в task arguments, включить auth, не публиковать сервис напрямую в интернет.
- [Два Beat-процесса случайно запущены] → Compose задаёт одну реплику, а транзакционное резервирование slot остаётся второй линией защиты.

## Migration Plan

1. Добавить модели, enum'ы и Alembic-миграцию; заполнить singleton schedule-row без override.
2. Расширить config/`.env.example`, зарегистрировать tasks/routes и покрыть wrapper'ы unit-тестами в eager mode.
3. Добавить orchestration service и history API, оставив старые синхронные точки входа временно доступными только для диагностики.
4. Перевести админку и production CLI на постановку в очередь; проверить конфликт активного прогона и сохранение результатов всех BP.
5. Добавить Dockerfile/Compose-сервисы и запустить smoke test: manual single, manual all с ошибкой среднего этапа, scheduled run, runtime schedule override, worker restart, Flower auth.
6. После подтверждения отключить любой неявный production-доступ к прямому runner и включить Beat.

Rollback: сначала выключить schedule через DB/env, дождаться или вручную завершить активный прогон, остановить Beat/workers/Flower и вернуть прежние entrypoints. Новые таблицы можно оставить без влияния на бизнес-данные; откат миграции выполнять отдельно только после сохранения требуемой истории.
