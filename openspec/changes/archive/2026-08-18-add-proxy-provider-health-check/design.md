## Context

См. `proposal.md` — Why. Технический контекст:

- `network/pool.py::_get_pool()` кэширует пул в Redis только при успехе
  (`if self.redis is not None and addresses:`) — при ошибке провайдера
  ничего не пишется, `_select_pool()` заново выполняется на каждый
  `acquire()`.
- `network/provider.py::_make_request` ретраит любой `httpx.HTTPError`
  одинаково — включая 401/403, для которых повтор бессмысленен по
  определению (ключ либо валиден, либо нет).
- `AdaptiveRunner.run_all(session, redis_client, task_ids=None)`
  (`integration/runner/batch.py`) — единая точка входа пакетного сбора:
  уже вызывает `self._bind_redis(redis_client)` до диспетчеризации
  задач, то есть `self._proxy_pool.redis` на этот момент уже привязан.
  Естественная точка «начала прогона».
- Классический контур `fedresurs_rpa` получает прокси через
  `AdaptiveRunner._get_parser_for_source` → тот же `self._proxy_pool.
  acquire()`, что и adaptive-стратегии — общее состояние работает для
  обоих контуров без дублирования.
- `core.mail.send_email`/`core.telegram.send_telegram` — уже существующие
  общие транспорты (не привязаны к BP-5 структурно, только по факту
  единственного текущего вызывающего кода), `settings.test_email`/
  `settings.test_tg` — уже существующие настройки песочницы алертов.

## Goals / Non-Goals

**Goals:**
- Один реальный чек провайдера в начале прогона, не по расписанию.
- Один лог на весь прогон при неработоспособности провайдера, а не
  warning на каждый запрос.
- В рамках прогона с уже обнаруженной проблемой — ноль дополнительных
  обращений к провайдеру.
- Быстрый fail для аутентификационных ошибок (401/403) — без ретраев.

**Non-Goals:**
- Реальная отправка email/telegram — только заглушка-лог с пометкой, где
  будущая реализация подключит `core.mail`/`core.telegram`.
- Новые настройки получателя — переиспользуются `TEST_EMAIL`/`TEST_TG`.
- Периодическая (Celery beat) проверка вне прогона сбора.
- Изменение поведения cooldown конкретного адреса по источнику (уже
  реализовано в `add-rpa-collection-proxying`, не трогается).

## Decisions

### D1 — Redis-маркер вместо in-process флага
Общий Redis-ключ (например, `bp1:proxy:provider_down`), не привязанный к
источнику (в отличие от cooldown адреса — тот уже per-source). Провайдер
и ключ — один общий ресурс на весь конвейер, поломка касается всех
источников одинаково. Redis выбран, а не in-process флаг на экземпляре
`ProxyPool`, потому что `ProxyPool` создаётся отдельно в
`AgenticOrchestrator` и в `AdaptiveRunner` — без Redis это состояние не
шарилось бы между двумя контурами.

**Альтернатива (отклонена):** in-process переменная. Отклонено —
`ProxyPool` не синглтон, состояние не увидят оба потребителя.

### D2 — Проверка привязана к `run_all`, не к отдельной задаче
Чек выполняется синхронно в начале `AdaptiveRunner.run_all`, до цикла по
задачам — не отдельная Celery beat задача. Проще: не нужна новая
запись в `beat_schedule`/`core/celery_app.py::include`, не нужен
отдельный TTL подавления повторных уведомлений (частота чека и так
ограничена частотой запуска `run_all`, обычно раз в сутки по
`PIPELINE_SCHEDULE_CRON`). Ограничение: если `run_all` вызывается не
через штатное расписание, а часто вручную/тестово — чек будет выполняться
чаще; это осознанно принимается, т.к. чек дешёвый (один HTTP-запрос) и
проблема должна быть видна сразу, а не молчать до следующего окна beat.

### D3 — Заглушка вместо реальной отправки
Только лог + Redis-маркер. Причина — явное решение пользователя в
обсуждении (see conversation): реальная интеграция с `core.mail`/
`core.telegram` требует решить вопрос реального получателя (не
`TEST_EMAIL`/`TEST_TG`, которые семантически — песочница для тестирования
BP-5-алертов), это отдельное решение вне рамок этого change. В коде
рядом с логом — комментарий-указатель на будущую реализацию через
`settings.test_email`/`settings.test_tg`, чтобы не искать заново, куда
их подставлять.

### D4 — Не ретраить 401/403 в `provider.py`
`_make_request` проверяет статус HTTP-ошибки до входа в ветку ретрая:
401/403 — сразу `raise`, остальные `httpx.HTTPError` (5xx, 429, сетевые/
таймаут) — ретраятся как раньше (3 попытки, бэкофф 1/2/4с). Основание:
аутентификационная ошибка детерминирована — либо ключ верный, либо нет,
повтор того же запроса результат не изменит.

## Risks / Trade-offs

- **[Риск]** Ложное определение «провайдер сломан» на разовом сетевом
  сбое во время чека (не связанном с ключом/балансом) → на весь прогон
  RPA-стратегии останутся без прокси, хотя провайдер на самом деле
  доступен → **Митигация**: чек — не единственная линия защиты, каждый
  `acquire()` внутри прогона просто использует маркер, не проверяет
  заново; но следующий прогон (`run_all`) чекает заново, ложное
  срабатывание не наследуется дальше одного прогона.
- **[Риск]** Заглушка вместо реального уведомления означает, что
  проблему увидит только тот, кто читает логи — если никто не смотрит,
  проблема (например, реально пустой баланс) может оставаться
  незамеченной долго → **Митигация**: осознанно принято пользователем
  (D3), реальная нотификация — следующий шаг, не в рамках этого change.
