## Context

См. `proposal.md` — «Why» для мотивации. Механика двух независимых потерь:

1. **Уровень листинга.** `_extract_by_selectors()`
   (`processing/parser/selectors.py`) извлекает `published_at`/`region`/
   `media_name` не хуже, чем `url`/`title` — но `_page_items()`
   (`processing/parser/pagination.py:76-146`) возвращает наружу только
   `list[tuple[title, url_abs, url_rel]]` (докстринг на строке 83-84).
   Всё остальное, что вернул `_extract_by_selectors()` для того же
   элемента, недостижимо для вызывающего кода.
2. **LLM-вызовы, результат которых уходит только в `extra`.**
   `RelevanceFilter.apply()` → `AIAgent.score_relevance()`
   (`relevance.py:69`, `agent.py:102`, `RELEVANCE_PROMPT`) размечает каждую
   новость полем `relevance`. `_enrich_news()` → `AIAgent.enrich_event()`
   (`core.py:859-893`, `agent.py:234`, `ENRICHMENT_PROMPT`) вызывается по
   одному разу на новость с текстом и реально извлекает `published_at`
   (ISO 8601), `author`, `keywords`, `summary`, `mentioned_company`,
   `mentioned_inn`, `sentiment`. Оба результата попадают в `entry['relevance']`/
   `entry['ex_enrichment']` — а `bridge.py:140` при промоушене в `ParsedItem`
   пишет `extra={}` безусловно. Результат обоих вызовов гарантированно
   недостижим — деньги на LLM потрачены, данные никуда не идут.

Прямым решением зафиксировано: `extra` для новостей всегда `{}` (не меняем),
`meta.items_count`/`meta.empty_reason` остаются (добавлены коллегой
сознательно, коммит `a137289`, не меняем), раздел `metrics` уже не
сериализуется (коммит `9fb12e8`, код не меняем). Значит `enrich_event` как
источник `published_at` тоже теряет смысл: даже если бы его результат не
выбрасывался, класть его было бы некуда (`extra={}` остаётся), а нужное
поле (`published_at`) должно приходить из прямого извлечения, не из LLM.

## Goals / Non-Goals

**Goals:**
- Значения `published_at`/`region`/`media_name`, уже извлечённые адаптером
  на уровне листинга, доходят до персистентного `ParsedItem` без повторного
  парсинга DOM и без обращения к LLM на каждый элемент.
- `media_name` промотированной новости не подменяется URL/именем источника,
  когда реальное имя публикатора не найдено — остаётся `null`.
- LLM-вызовы, чей единственный потребитель — `extra` (`score_relevance`,
  `enrich_event`), и их промпты/конфигурация удаляются из кодовой базы, а не
  просто выключаются дефолтом (чтобы не могли случайно снова включиться).

**Non-Goals:**
- Не меняется `extra={}` для промотированных новостей — подтверждённое
  решение, вне рамок.
- Не меняется `meta` (`items_count`/`empty_reason` остаются) — подтверждённое
  решение, вне рамок.
- Не меняется код вокруг `metrics`/`ParsedResponse.metrics` — уже не
  сериализуется (`exclude=True`), отдельного действия не требует.
- Не трогается классический RPA-контур (`fedresurs_rpa/parser.py`).
- Не добавляется новая логика извлечения/новые селекторы — только прокладка
  пути для уже вычисляемых значений и удаление неиспользуемого LLM-пути.
- Не переписывается парсинг/нормализация `region` в id справочника —
  обязанность BP-2 по ТЗ.

## Decisions

**1. Расширить возвращаемое значение `_page_items()`.**
Сейчас `list[tuple[title, url_abs, url_rel]]`. Функция возвращает уже
извлечённые `published_at`/`region`/`media_name` вместе с `title`/`url` за
один проход. Альтернатива — заново вызывать `_extract_by_selectors()` в
`_collect_news_with_pagination()` — отклонена: дублирует разбор HTML и
рискует разойтись с тем, что уже нашёл `_page_items()` для того же
элемента.

**2. Прокинуть поля через `_run_extraction_cascade()` под `ex_`-префиксом.**
По аналогии с `ex_title`/`ex_url`/`ex_text` — добавляются
`ex_published_at`/`ex_region`/`ex_media_name` (только когда листинг их
реально дал; иначе ключ отсутствует).

**3. Промоушен в `bridge.py` — без LLM-фолбэка:**
```
published_at = entry.get('ex_published_at')  # или None
region       = entry.get('ex_region')
media_name   = entry.get('ex_media_name')
```
Никакого обращения к `ex_enrichment` (его больше не существует) и никакого
`base_media_name = raw_item.get('media_name')` (текущий URL-фолбэк,
`bridge.py:113,133`) — убирается. `media_name` служебного элемента «страница
поиска» (`_make_search_page_item`, `pagination.py:168`) не трогается — это
отдельный контракт, не событие.

**4. Удалить, а не выключить дефолтом.**
`RelevanceFilter`, `AIAgent.score_relevance`/`_score_relevance_batch`/
`enrich_event`, `RELEVANCE_PROMPT`/`ENRICHMENT_PROMPT` и связанные настройки
(`bp1_relevance_mode`, `bp1_relevance_threshold`, `bp1_enrichment_enabled`)
удаляются из кода. Отклонённая альтернатива — оставить код, но выставить
дефолты в `off`/`False`: отклонена, т.к. не устраняет риск случайного
повторного включения и оставляет мёртвый, вводящий в заблуждение код (два
неиспользуемых промпта, класс-фильтр без потребителей).
`AdaptiveParser.__init__` (`processing/parser/core.py:95-101`) лишается
`self._relevance`/`self._enrichment_enabled`; `_assemble_items` — блока
`filtered_news = await self._relevance.apply(...)` и вызова
`_enrich_news(...)`.

## Risks / Trade-offs

- **[Risk]** Селекторы листинга могут быть у части адаптеров неточными
  (LLM ошиблась при `analyze_structure`) — прокидывание может принести
  видимо «грязные» значения `region`/`media_name` в сырьё.
  **→ Mitigation:** это ровно то, что адаптер и так заявляет как извлечённое
  для `url`/`title` — новой неточности не добавляется; по ТЗ нормализация и
  контроль качества этих полей — задача BP-2.
- **[Risk]** Смена возвращаемого типа `_page_items()` затрагивает
  существующие тесты (`test_page_items_*`, `test_parser.py`), которые сейчас
  распаковывают ровно 2-3 элемента кортежа.
  **→ Mitigation:** обновить эти тесты явно в рамках задач; логика подбора
  совпадений (`_find_row_scope`, разворачивание контейнера-списка) не
  меняется.
- **[Risk]** Удаление `RelevanceFilter`/`enrich_event` — откат уже
  реализованного и протестированного функционала (Шаги 14/15/22 прежнего
  плана рефакторинга bp1).
  **→ Mitigation:** явное, осознанное решение пользователя, подтверждённое
  трижды в разговоре; соответствующие тесты (`test_llm.py` батчинг
  relevance, `test_parser.py` enrichment) удаляются вместе с кодом, а не
  остаются падать.
- **[Risk]** Без `enrich_event` `published_at` для статей без листинговой
  разметки останется `null` чаще, чем при старом поведении (когда LLM хотя
  бы иногда его находил из текста).
  **→ Mitigation:** осознанный компромисс пользователя — точность через
  прямое извлечение важнее полноты через LLM-домысливание; `null` — честный
  сигнал «не извлекли», а не выдуманное значение.

## Migration Plan

Изменение поведенческое, без миграции данных. Уже сохранённые
`raw_item.raw_data` не переписываются задним числом — новое поведение
действует только для новых прогонов сбора после выката. Откат —
стандартный откат кода; удаление конфиг-настроек `bp1_relevance_mode`/
`bp1_relevance_threshold`/`bp1_enrichment_enabled` не требует миграции БД
(это поля `Settings`, не колонки).
