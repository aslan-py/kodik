## Context

См. `proposal.md` — Why/What Changes. Технический контекст, важный для
решений ниже:

- `AdaptiveParser.parse()` (`adaptive/processing/parser/core.py`) — точка,
  где решается, откуда взять контент для источника, ДО обращения к
  `AgenticOrchestrator.fetch_with_degradation()`; `_assemble_items` уже
  собирает `items` в форме `[{..., extra: {news: [...]}}]`, которую можно
  заполнить и в обход HTML-лестницы (см. D4).
- `SourceClassifier._detect_source_type` уже возвращает
  `SourceType.NEWS` по маркерам в URL/имени (`classifier.py`), а
  `UnifiedCache` уже хранит классификацию и адаптер на источник в Redis с
  TTL и паттерном самокоррекции при повторных провалах (`AdapterState.
  fail_count`, Шаг 21 `REFACTORING_PLAN.md`, порог 2, а не 1 — разовый
  сбой не должен сбрасывать рабочий кэш).
- Постраничное извлечение статьи (`_extract_article_text`,
  `adaptive/processing/parser/`) уже существует и умеет доставать
  заголовок/текст/дату по произвольному URL — нужен как есть, не заново.
- BP-2 уже размечает материалы по вхождению строки без LLM (чёрные
  списки/стоп-слова, `ABOUT.md`) — прецедент для D6: LLM в этом проекте
  используется для семантической неоднозначности (BP-3), не для проверки
  вхождения имени.
- В зависимостях уже есть `httpx` (сетевые запросы) и `beautifulsoup4`
  (может парсить XML через `lxml`-парсер, уже используется в HTML-пути) —
  RSS/Atom, в отличие от произвольного HTML, имеет строгий формат, для
  него нужен специализированный парсер, а не эвристики `HtmlCleaner`.

## Goals / Non-Goals

**Goals:**
- Обнаружение и использование RSS/Atom как более дешёвой альтернативы
  HTML-лестнице для источников `SourceType.NEWS`.
- `sitemap.xml` как источник URL-кандидатов, когда фида нет — переиспользуя
  существующий deep-fetch статьи, не новый экстрактор.
- Безопасный откат: отсутствие/отказ фида не блокирует и не портит сбор,
  источник всегда может собираться через существующую HTML-лестницу.
- Материалы фида размечаются по совпадению с именем конкурента до того,
  как попасть в сводку сбора — никакого отдельного «доверенного» потока
  без разметки под конкретного конкурента.

**Non-Goals:**
- Не реализуется нечёткое/алиасное сопоставление имени конкурента
  (сокращения, транслитерация, синонимы) — `Competitor` не хранит алиасы
  (`src/bp1/models.py`), совпадение только по точному (после нормализации)
  вхождению полного `name`, тот же класс ограничения, что уже принят для
  `dedup_key` в BP-2.
- Не реализуется обнаружение приватных JSON-API через перехват сетевого
  трафика браузера (network sniffing/XHR-reverse-engineering) — отдельная,
  более сложная возможность, см. «Отложено на будущее» ниже.
- Не реализуется проба конвенций REST/OpenAPI/GraphQL-интроспекции —
  туда же, см. ниже.
- Не реализуется LLM-инференс JSON-путей для произвольных API-ответов —
  туда же, см. ниже.
- Не меняется поведение для `SourceType.REGISTRY`/`API`/`SPA`/`UNKNOWN` —
  только `NEWS`.
- Не вводится полнотекстовый поиск по фиду под конкретного
  конкурента/триггер — фид всегда отдаёт общий поток сайта, фильтрация
  по конкуренту/триггеру остаётся за relevance-ranking и BP-2, как и для
  HTML-пути.
- Не меняется классический контур `fedresurs_rpa` — там нет источников
  типа `NEWS`.

## Decisions

### D1 — Обнаружение фида: конвенциональные пути + `<link rel="alternate">`, без LLM
Два дешёвых, детерминированных способа, без обращения к LLM:
1. Проба фиксированного списка путей (`/rss`, `/rss.xml`, `/feed`,
   `/feed.xml`, `/atom.xml`, `/sitemap.xml`, `/sitemap_index.xml`) —
   лёгкие GET-запросы, тот же приём, что уже применяет `SearchUrlProber`
   для поисковых эндпоинтов (перебор кандидатов до первого валидного).
2. Если HTML источника на этот момент уже получен любой стратегией
   (переиспользуем «бесплатный» HTML, как это уже сделано для
   классификации в Шаге 9 `REFACTORING_PLAN.md`) — разбор `<link
   rel="alternate" type="application/rss+xml"|"application/atom+xml">` в
   `<head>`. Это самодекларация сайта, приоритетнее угаданного пути,
   пробуется первым, если HTML уже есть.

**Альтернатива (отклонена):** LLM определяет, есть ли у сайта фид, по
содержимому HTML. Отклонено: обнаружение фида — задача с детерминированным
ответом (путь либо отвечает валидным XML, либо нет), тратить LLM-вызов на
то, что решается пробой путей, не оправдано ни стоимостью, ни задержкой.

### D2 — RSS/Atom: `feedparser`, новая зависимость
`feedparser` — де-факто стандартная библиотека для RSS/Atom в Python:
устойчива к невалидному/нестрогому XML (частая ситуация у реальных
сайтов), нормализует различия RSS 1.0/2.0/Atom в единый интерфейс
(`entry.title`/`entry.link`/`entry.published`/`entry.summary`). Прямое
сопоставление полей `feedparser`-записи в существующую структуру
результата (`title`/`url`/`published_at`/`text`) — без LLM, без
CSS-селекторов.

**Альтернатива (отклонена):** парсить RSS/Atom вручную через
`beautifulsoup4` с XML-парсером, как уже делается для HTML. Отклонено:
RSS/Atom — два разных, местами неточно соблюдаемых на практике XML-формата
(разные схемы дат, вложенность, namespace) — `feedparser` уже решил эти
проблемы, самостоятельная реализация дублирует известную библиотеку без
причины.

### D3 — `sitemap.xml`: список URL, не самостоятельный источник материалов
`sitemap.xml` (в отличие от RSS/Atom) не несёт заголовка/текста/даты —
только список URL. Поэтому он не заменяет HTML-лестницу целиком, а
подаёт кандидатов в уже существующий deep-fetch статьи
(`_extract_article_text`), который и так вызывается для каждой найденной
ссылки на HTML-пути. Разбор `sitemap.xml`/`sitemap_index.xml`
(вложенные sitemap) — простой XML, без внешней зависимости
(`beautifulsoup4` с XML-парсером, как в остальном адаптивном контуре).

**Альтернатива (отклонена):** пропустить `sitemap.xml` в этой версии,
ограничиться только RSS/Atom. Отклонено: часть источников из ТЗ (раздел
4, «агрегатор СМИ», «сайты конкурентов») не публикует RSS, но публикует
sitemap для SEO — исключение сразу сужает выигрыш от изменения без
весомой причины, а переиспользование deep-fetch делает эту часть дешёвой
в реализации.

### D4 — Точка встраивания: ранний выход в начале `AdaptiveParser.parse()`, не таблица стратегий `AgenticOrchestrator`
**Пересмотрено при реализации.** Первоначальный вариант (фид как строка в
`_ALLOWED_STRATEGIES_TABLE`, наравне с `FAST`/`BROWSER`/...) технически не
реализуем: `_DEGRADATION_ORDER` — это способы получить контент с ОДНОГО и
того же `url` (конкурентно-специфичная страница поиска), возвращающие
`StrategyResult.data: str` — сырой HTML для последующего CSS/LLM-разбора.
Фид живёт на **другом** URL (корень домена источника, не зависит от
конкурента) и сразу отдаёт структурированные записи, а не HTML для
разбора — в форму `StrategyResult` он не укладывается ни по адресу
запроса, ни по форме результата.

Правильная точка — ранний выход в начале `AdaptiveParser.parse()`, до
`_resolve_start_strategy`/`fetch_with_degradation`: если источник —
`SourceType.NEWS` и обнаружен рабочий фид, `parse()` возвращает
`AdaptiveParseResult` сразу, HTML-лестница для этого вызова не
запускается. Materialы собираются в ТОЙ ЖЕ форме, что уже производит
`_assemble_items` (`items = [{..., extra: {news: [{ex_title, ex_url,
ex_text, ex_method, ...}]}}]`, `ex_method='rss'`/`'sitemap'` вместо
`'css'`/`'llm'`) — поэтому `bridge.py` и всё, что стоит после `parse()`
по конвейеру, не меняется вообще, совместимость по форме данных, а не по
коду.

**Альтернатива (отклонена):** вынести решение уровнем выше —
в `AdaptiveBridgeParser`/`AdaptiveRunner`, до вызова `AdaptiveParser.parse()`
(тот же уровень ответственности, что уже несут `SearchUrlProber`/
`SearchParamResolver`). Архитектурно чище, но `_deep_fetch`/
`_extract_article_text` (нужны sitemap-фолбэку) и `self._relevance` —
приватные методы конкретного экземпляра `AdaptiveParser`, наружу не
вынесены. Перенос точки принятия решения без переноса этой механики
означал бы либо создавать `AdaptiveParser` из вызывающего слоя и всё
равно лезть в его приватные методы (не проще варианта с ранним выходом),
либо предварительно выносить `_deep_fetch` в переиспользуемый компонент —
самостоятельный рефакторинг, не входящий в объём этого изменения (см.
Non-Goals).

**Альтернатива (отклонена):** обнаружение фида как предварительный шаг в
`AdaptiveRunner`, до вызова `AdaptiveParser`. Отклонено по той же причине,
что и выше: `AdaptiveRunner` не должен получать вторую копию логики
оркестрации стратегий (см. обоснование Шага 9 `REFACTORING_PLAN.md`), а
без переноса deep-fetch/relevance это единственный практичный вариант
всё равно сводится к вызову `AdaptiveParser` изнутри.

### D5 — Два разных кэша: обнаружение (URL) и материалы (распарсенные items)
**Расширено при реализации.** Изначально планировался один кэш — URL
найденного фида/sitemap. Обнаружилось: фид — ресурс уровня **источника**,
а `parse()` вызывается на каждую пару конкурент×источник (`SearchTask`).
При 10 активных конкурентах на источник без дополнительной меры
получилось бы 10 независимых походов за одним и тем же фидом в рамках
одного прогона — различался бы только шаг разметки релевантности после.
Решение — два кэша в `UnifiedCache` (Redis, паттерн `BP1_*_TTL_SECONDS`),
оба ключуются по источнику, не по паре конкурент×источник:

1. **Кэш обнаружения** (`bp1_feed_cache_ttl_seconds`, длинный TTL, по
   аналогии с кэшем адаптера/классификации — 7 дней): URL найденного
   фида/sitemap, либо явная отметка «фида нет» — чтобы не пере-пробовать
   конвенциональные пути на источнике без фида при каждом прогоне.
2. **Кэш материалов** (`bp1_feed_items_cache_ttl_seconds`, короткий TTL,
   порядка интервала прогона сбора): уже распарсенные записи фида. Первый
   `parse()` источника с фидом (любой конкурент) скачивает и парсит фид
   один раз, следующие `parse()` того же источника в пределах TTL берут
   материалы из кэша и тратят только дешёвый шаг разметки релевантности
   (D6) под своего конкурента.

Гонка при параллельном `run_all()` (Шаг 17 `REFACTORING_PLAN.md`) —
несколько конкурентов одного источника одновременно промахнутся по кэшу
материалов и оба сходят за фидом — не устраняется отдельным механизмом
(семафор/лок): тот же класс «cache miss stampede», что уже есть у кэша
адаптера/классификации, отдельной защиты для них тоже не заводили.

Порог самокоррекции кэша обнаружения — по аналогии с
`ADAPTER_FAIL_THRESHOLD=2` (Шаг 21): один случайный сбой (сайт временно
недоступен) не должен сразу выбрасывать рабочий фид из кэша, только
повторный подряд отказ.

### D6 — Разметка релевантности конкуренту: строковое совпадение по имени, без LLM
**Пересмотрено при реализации.** Изначально планировалось переиспользовать
`AIAgent.score_relevance`/`BP1_RELEVANCE_MODE` как есть — то же, что уже
применяется к материалам HTML-пути. При ближайшем рассмотрении: HTML-путь
получает контент уже с поисковой страницы сайта (запрос построен под
конкретного конкурента) — там LLM уточняет ранжирование среди частично
предотобранного. Фид не предотбирает ничего — там LLM пришлось бы решать
исключительно вопрос «встречается ли имя конкурента в тексте», а это не
семантическая задача. Проект уже решил этот класс задач в BP-2 без LLM
(`ABOUT.md`: «ИИ в BP-2 не нужен — правила дешёвые, прозрачные... Семантику
("Бегемот" компания vs животное) добивает LLM в BP-3») — LLM оправдан
только там, где есть неоднозначность смысла, а не там, где вопрос
сводится к вхождению строки.

Решение: материалы из фида размечаются строковым совпадением
нормализованного имени конкурента (`competitor.name`, тот же `norm()` —
lowercase, без пунктуации, схлопнутые пробелы — что уже применяется для
`dedup_key` в BP-2, `ABOUT.md`) в заголовке+тексте записи, без обращения
к LLM. `AIAgent.score_relevance` для материалов фида не вызывается.

Явный недостаток (принимается, не решается в этом изменении, по аналогии
с уже принятым в BP-2 для `dedup_key`): `Competitor` не хранит алиасы
(`src/bp1/models.py` — только `name`/`inn`), поэтому вариации написания,
сокращения и транслитерация имени конкурента совпадение не поймают —
только точное (после нормализации) вхождение полного `name`. Семантическую
неоднозначность (омонимы, косвенные упоминания) по-прежнему решает BP-3,
как и для HTML-пути — фид ничего не меняет в этом разделении.

## Risks / Trade-offs

- **[Риск]** Некоторые сайты отдают фид с намеренной задержкой публикации
  относительно самого сайта (кэш CDN на `/rss`) → **Митигация**: не
  критично для конкурентной разведки (не HFT), фид всё равно опрашивается
  на каждом плановом прогоне BP-1, задержка не больше интервала между
  прогонами.
- **[Риск]** `feedparser` — давно не обновлявшаяся, но стабильная
  библиотека (в экосистеме Python это норма для формата, не менявшегося
  много лет) → **Митигация**: изолирована в одной точке сопоставления
  полей, замена при необходимости не затронет остальной код.
- **[Риск]** Sitemap большого сайта может содержать тысячи URL, не все
  релевантны свежему сбору → **Митигация**: тот же лимит
  `BP1_MAX_NEWS_PER_SOURCE`, что уже ограничивает HTML-путь, применяется и
  здесь; приоритет — записи с `<lastmod>` ближе к текущей дате, если
  sitemap их указывает.
- **[Риск]** Ложноположительное обнаружение фида (путь отвечает 200, но
  это не RSS/Atom/sitemap, а, например, HTML-заглушка 404) →
  **Митигация**: валидация по факту разбора (`feedparser.bozo`/пустой
  список записей/невалидный XML), а не по одному факту HTTP 200 —
  невалидный ответ не кэшируется как успех.

## Migration Plan

1. Добавить `feedparser` в `requirements.txt`.
2. Реализовать обнаружение (конвенциональные пути + `<link
   rel="alternate">`) как отдельную чистую функцию, без побочных эффектов —
   тестируется без сети на фикстурах.
3. Реализовать сопоставление полей RSS/Atom → материалы (`feedparser`) и
   разбор `sitemap.xml`/`sitemap_index.xml` → список URL; строковую
   разметку релевантности конкуренту (D6, без LLM).
4. Подключить как ранний выход в начале `AdaptiveParser.parse()` для
   `SourceType.NEWS` (D4), с использованием существующего
   `_deep_fetch`/`_extract_article_text` для sitemap-кандидатов.
5. Добавить оба кэша в `UnifiedCache` (обнаружение + материалы, D5) —
   счётчик отказов кэша обнаружения по образцу `AdapterState.fail_count`.
6. Прогнать полный набор тестов `tests/bp1/` — обнаружение/отсутствие
   фида не должно менять поведение источников без фида (нулевая
   регрессия HTML-пути).
7. Откат — на любом шаге: без обнаруженного фида поведение источника не
   отличается от текущего (лестница деградации как есть), флаг фичи не
   нужен — это уже деградация по построению (см. `specs/`, «Отсутствие
   фида не считается отказом источника»).

## Отложено на будущее

Не входит в это изменение, зафиксировано для следующих отдельных
изменений (обсуждалось при исследовании темы «охват источников для
адаптивного поиска»):

- **Перехват сетевого трафика (network sniffing / XHR-reverse-engineering).**
  Headless-браузер уже используется (`BROWSER`/`STEALTH`-стратегии) —
  можно слушать `page.on('response')`, находить JSON-ответы, похожие на
  список объектов, запоминать URL-шаблон и на следующих прогонах обращаться
  к найденному API напрямую через `httpx`, минуя браузер. Не тривиально:
  нужны эвристики фильтрации трафика и, вероятно, LLM для распознавания
  «это тот самый эндпоинт со списком материалов».
- **Проба конвенций REST/OpenAPI/GraphQL.** Тот же принцип, что уже
  применён к поисковым эндпоинтам в `SearchUrlProber` — перебор известных
  путей (`/api/v1/`, `wp-json/`, `swagger.json`, `/graphql`
  интроспекция), но для обнаружения API вообще, не конкретно поиска.
- **LLM определяет JSON-путь в произвольном API-ответе.** Прямой аналог
  того, как сейчас `AdaptiveParser` определяет CSS-селекторы по HTML —
  тот же кэш/самокоррекция, только промпт и выход другие (JSON pointer
  вместо CSS-селектора). Имеет смысл только после того, как появится
  источник кандидат-эндпоинтов (перехват трафика или проба конвенций
  выше) — сам по себе бесполезен.
