## Context

См. proposal.md - Why. Дополнительные факты, важные для решения:

- Реальные точки входа уже существуют и не меняются: `src/bp2/pipeline.py::run_bp2()`, `src/bp4/pipeline.py::run_bp4()`, `src/bp5/pipeline.py::run_bp5()`, `src/bp7/pipeline.py::run_bp7_promotion()` — все `async def -> dict`, без CLI/транспортных забот внутри.
- `core/scripts/stages/cascade.py` уже описывает порядок зависимостей слоёв (`PIPELINE_ORDER`: `ActionItem → Alert → ShowcaseEvent → CategorizedEvent → NormalizedItem → RawItem → SearchTask`) и умеет считать строки (`count_rows`) и каскадно чистить (`clear_from`). Демо-сидеры `bp1.py`/`bp6.py` уже парные: `__main__` каждого вызывает `run_stage(title, clear, seed)` — чистит свой слой и слои ниже, потом сеет заново. Это не побочная деталь: `seed()` сам по себе НЕ идемпотентен (аддитивная вставка), повторный вызов без предварительной очистки задвоит строки или упадёт на unique-констрейнтах.
- Скрипта, заполняющего `source_candidate` кандидатами, в проекте нет вообще (см. proposal.md - What Changes, подтверждено `grep`) — `BP7_README.md` прямо называет это нереализованным.
- `core/` в проекте — зона стабильной инфраструктуры, от которой зависят `api/`, `src/bpN/`, админка (`config.py`, `database.py`, `redis_client.py`, `celery_app.py`, `telegram.py`, `mail.py`). `core/scripts/` — противоположная по смыслу зона: одноразовые dev-инструменты (`seed_all.py`, `clear_data.py`, демо-сидеры), не предназначенные для импорта из `api/`/админки.
- Раннер в этом изменении — только ручной (CLI). Подключение к API и FastAdmin — заявленные следующие шаги (см. proposal.md - Non-goals), но уже сейчас формируют требование: реестр этапов должен быть местом, которое одинаково удобно дёргать и из CLI, и позже из API-хендлера/admin-action, без переписывания.

## Goals / Non-Goals

**Goals:**
- Одна карта `{номер этапа → как проверить готовность → что запустить}`, не дублирующая бизнес-логику — только ссылки на существующие функции/заглушки.
- Preflight переиспользует уже существующую модель зависимостей (`PIPELINE_ORDER`), а не заводит собственную.
- `run_all()` не останавливается на первом сбое — прогоняет все 7 этапов, чтобы за один запуск было видно полное состояние конвейера.

**Non-Goals:**
- Транспортная независимость (Celery/API/admin-action) — реестр к этому готов по форме (async-функции, дескрипторы с метаданными), но подключение — не предмет этого изменения.
- Идемпотентность/аккуратная инкрементальность заглушек 1/6/7 при повторных запусках сверх уже принятого паттерна clear+seed — не изобретаем новый механизм, переиспользуем существующий.

## Decisions

### Реестр живёт в `core/pipeline/`, а не в `core/scripts/`
`core/scripts/` по конвенции проекта — одноразовые dev-скрипты, не импортируемые извне (см. Context). Реестр же — именно то, что позже будет дёргать и API, и FastAdmin, и CLI, то есть стабильная инфраструктура по роли, ближе к `core/celery_app.py`, чем к `seed_all.py`. Альтернатива (`core/scripts/run_pipeline.py`, рядом с сидерами) отклонена — смешала бы «переживёт релиз» с «можно снести завтра».

### Реестр — только ссылки, не реализация
Каждая запись `STAGES[n]` — номер, заголовок, флаг `is_stub`, ссылка на функцию предусловия (или `None`), ссылка на функцию запуска. Ни одной строчки бизнес-логики внутри `core/pipeline/` — весь код продолжает жить в `src/bpN/pipeline.py` (реальные этапы) и `core/scripts/stages/*.py` (заглушки). Когда придёт финальный код для этапа 1/6/7, меняется одна ссылка в реестре — форма не переписывается.

### Preflight переиспользует `cascade.PIPELINE_ORDER`, отдельная ветка для этапа 7
Для этапов 2–6 предусловие = «в таблице слоя N−1 из `PIPELINE_ORDER` есть хотя бы одна строка», проверяется через уже существующий `count_rows()`. Для этапа 7 (перенос `source_candidate → source`) зависимость независимая — не часть общей цепочки `PIPELINE_ORDER` — и пустая очередь кандидатов НЕ является ошибкой (тот же смысл, что и сегодняшний легитимный ответ `run_bp7_promotion()`: `{checked: 0}`). Отдельная, а не универсальная, preflight-функция для этого этапа — так как семантика «пусто = не ошибка» отличается от остальных этапов («пусто = ошибка, останови»).

### Заглушки этапов 1/6/7 вызывают ту же пару clear()+seed(), что и `run_stage()` из `cascade.py`, а не голый `seed()`
Раз `seed()` аддитивен и не идемпотентен (см. Context), заглушечная запись реестра для этапов 1 и 6 оборачивает `clear_from(...) → seed(...)` — то же самое, что сегодня делает блок `if __name__ == '__main__': run_stage(...)` в `bp1.py`/`bp6.py`, просто вызванное из реестра, а не из отдельного процесса. Новый `core/scripts/stages/bp7.py` пишется по тому же контракту (`clear`/`seed` пара) с самого начала, для единообразия с 1 и 6.

### Этап 3 подключается к реальному коду сейчас, извлечённому в новый `src/bp3/pipeline.py::run_bp3()`
Логика уже работает (по словам пользователя, «правки будут», не «кода нет»), поэтому не откладываем в заглушку. Но встраивать в реестр текущий `main.py` напрямую нельзя — это скрипт с `if __name__ == '__main__'`, не импортируемая функция, и над ним сейчас активно работает коллега. Решение: извлечь тонкую обёртку `run_bp3() -> dict` в новый файл (по контракту `run_bp2`/`run_bp4`/`run_bp5`), собирающую тот же `Pipeline([...])`, что и `main.py`; сам `main.py` не трогаем и не удаляем — коллега продолжает им пользоваться для ручной отладки. Когда структура BP-3 изменится, правится только `run_bp3()`, реестр — нет. Без специального dual-mode (`direct`/`celery`), как у BP-1 — по прямому запросу пользователя не переусложнять, здесь такой развилки не требуется.

### `run_all()` не прерывается на первом сбое
Каждый этап оборачивается в собственный `try/except` внутри цикла 1→7; исключение или ошибка preflight одного этапа не мешает попытке следующего. В конце — единая сводка по всем семи. Осознанное следствие: если, например, этап 4 упал, у этапов 5/6 preflight тоже покажет «нет данных» в той же сводке — это ожидаемо, не задваивает информацию, а показывает полную картину каскада за один прогон.

## Risks / Trade-offs

- [Risk] `run_bp3()`, извлечённый из `main.py`, разойдётся со следующей правкой коллеги в BP-3 → Mitigation: `main.py` не тронут, изменения коллеги в `src/bp3/modules/*` подхватятся автоматически (обёртка их только импортирует); обновить придётся только список модулей в `run_bp3()`, если коллега поменяет их набор/порядок — локальная правка одного файла.
- [Risk] Заглушка этапа 7 (новый демо-сидер `source_candidate`) может разойтись с реальной схемой, когда появится агент поиска кандидатов → Mitigation: заглушка пишет только через модель `SourceCandidate` из `src/bp7/models.py`, а не через свою параллельную структуру — если схема не меняется, замена заглушки на реального агента не потребует правок в реестре.
- [Risk] `run_all()`, продолжающий работу после сбоя, может маскировать root cause за экраном каскадных «нет данных» на нижних этапах → Mitigation: сводка explicitно показывает ПЕРВОПРИЧИНУ (реальная ошибка этапа 4) отдельно от последующих «нет данных» — это разные типы записей в сводке, не смешиваются в один текст.

## Migration Plan

Новая функциональность, ничего не заменяет — данные/схема БД не затронуты, миграций нет. Порядок реализации:
1. `src/bp3/pipeline.py::run_bp3()` — извлечение из `main.py`.
2. `core/scripts/stages/bp7.py` — новая заглушка `source_candidate` (clear/seed пара).
3. `core/pipeline/registry.py` — карта `STAGES` на все 7 этапов.
4. `core/pipeline/runner.py` — `run_stage(n)`, `run_all()`.
5. `core/pipeline/cli.py` — минимальный CLI.
6. Ручная проверка: каждый этап по отдельности, затем `run_all()` целиком на пустой и на частично заполненной БД.

Откат — ревёрт коммита, существующий код (`run_bp2`/`run_bp4`/`run_bp5`/`run_bp7_promotion`/сидеры) не менялся.
