# Система автоматического мониторинга конкурентов

Данная часть реализует модульный пайплайн на базе LLM (через OpenRouter, в будущем произойдет замена) для анализа новостей о конкурентах. Система загружает новости из базы данных, категоризирует их по заданным типам событий, назначает приоритеты и ответственные отделы, определяет тональность влияния на компанию и генерирует комментарии с рекомендациями по действиям.

---

### Архитектура пайплайна

```plaintext
┌─────────────────────┐
│  База данных         │
│  (новости, категории, │
│   отделы)            │
└──────────┬──────────┘
           │
           ▼
┌──────────────────────────────────────────────────────┐
│  InputDataModule                                    │
│  - загружает новости (id + текст), список категорий │
│    с описаниями, список отделов с зонами            │
│    ответственности                                   │
│  - сохраняет в ctx.news, ctx.manual_cat,            │
│    ctx.manual_dept                                  │
└──────────────────────────┬───────────────────────────┘
                           │
                           ▼
┌──────────────────────────────────────────────────────┐
│  CategorizedModule (LLM)                            │
│  - принимает ctx.news и ctx.manual_cat              │
│  - для каждой новости LLM определяет категорию из   │
│    списка, переданного в промпт (или null, если     │
│    невозможно)                                      │
│  - результат: ctx.category_news (id, text,          │
│    category)                                        │
└──────────────────────────┬───────────────────────────┘
                           │
                           ▼
┌──────────────────────────────────────────────────────┐
│  ActionPlanningModule (правила)                    │
│  - на основе категории назначает:                   │
│    * приоритет (П1–П4)                              │
│    * срок действия (например, «48 часов»)           │
│    * ответственный отдел (из списка отделов)        │
│  - правила заданы словарём, но могут быть           │
│    переопределены                                   │
│  - сохраняет ctx.priority, ctx.deadline,            │
│    ctx.department                                   │
└──────────────────────────┬───────────────────────────┘
                           │
                           ▼
┌──────────────────────────────────────────────────────┐
│  ToneAnalysisModule (LLM)                           │
│  - определяет тональность каждой новости с точки    │
│    зрения влияния на нашу компанию:                 │
│    "Позитивная", "Негативная", "Тревожная",         │
│    "Нейтральная", "Нерелевантно"                    │
│  - результат: ctx.tone_of_news (id, tone)           │
└──────────────────────────┬───────────────────────────┘
                           │
                           ▼
┌──────────────────────────────────────────────────────┐
│  CommentActionModule (LLM)                         │
│  - использует все предыдущие данные (текст,         │
│    категория, приоритет, дедлайн, отдел, тональность)│
│  - генерирует для каждой новости:                   │
│    * краткий комментарий (что произошло, почему     │
│      важно)                                         │
│    * рекомендацию по действию для компании          │
│  - сохраняет ctx.comments и ctx.actions             │
└──────────────────────────┬───────────────────────────┘
                           │
                           ▼
┌──────────────────────────────────────────────────────┐
│  SaveResultsModule                                  │
│  - сохраняет все результаты работы                  │
│ предыдущих модулей (категоризация, приоритезация,   │
│  тональность, комментарии, действия, определение    │
│ сроков реагирования)  в реляционную базу данных     │
└──────────────────────────┬───────────────────────────┘
```

## Категории событий и ответственные отделы

Это закрытый список из ТЗ — **разработчик заводит его на старте**, при разворачивании проекта.
Аналитику заполнять его самостоятельно не нужно (в отличие от справочников BP-2 —
`black_domain`/`stop_word`, которые начинают пустыми). Список хранится в базе данных и
динамически подгружается в LLM-промпты — редактировать записи (добавление/удаление/правка
описаний) можно без изменения кода, но это правка уже заведённого списка, а не обязательный шаг
первоначальной настройки.

### Таблица категорий событий

| Название категории | Описание |
|--------------------|----------|
| **Надзорная санкция и юридический риск** | Любое действие госорганов (проверка, предписание, штраф, иск, блокировка сервисов) или судебное разбирательство, которое создаёт материальные финансовые потери или угрозу остановки/изменения бизнес-модели конкурента. |
| **Репутационный риск** | Информационный инцидент, который не имеет прямого юридического или финансового исчисления на данный момент, но снижает доверие стейкхолдеров (клиентов, партнёров, инвесторов) к бренду, угрожая будущему оттоку аудитории. |
| **PR-активность конкурента** | Целенаправленные публичные действия конкурента по формированию позитивного имиджа, не связанные с выходом нового продукта. Это «продажа воздуха»: спикерство на форумах, спонсорство, ESG-отчёты, наймы звёздных менеджеров. |
| **Системная проблема (возможность для входа)** | Повторяющиеся (2+ раза за период) жалобы клиентов или экспертов на функциональные/технические сбои или неудобство сервиса конкурента, которые он **не может или не хочет** исправить. |
| **Признание качества и конкурсы** | Объективная фиксация успеха через внешние авторитетные источники (например, рейтинги агентств), победа в отраслевых премиях, получение патентов, положительная экспертиза от лидеров мнений. |
| **Косвенное упоминание** | Новость, где конкурент не является главным субъектом (упоминается в одном абзаце или списке), но контекст важен для понимания трендов (например, упоминание в законе, отчёте ЦБ, в новости о партнёре конкурента). |
| **Информационный шум** | Фоновые, малозначимые новости без конкретики и последствий. Перепечатки старых материалов, формальные отчёты по GAAP/МСФО (без отклонений), смена второстепенных менеджеров средней руки, общие слова о «цифровизации». |

### Таблица ответственных отделов

| Отдел | Зона ответственности |
|-------|-----------------------|
| **Юристы** | Держат санкции и иски. |
| **PR** | Держат имиджевые риски и активность конкурентов в медиа. |
| **Аналитика** | Держит рыночные возможности (системные сбои) и тренды (косвенные упоминания). |
| **Маркетинг** | Держит успехи конкурентов (признание) и корректирует свою коммуникацию. |

**Важно**: список уже заведён разработчиком и готов к работе — трогать его при первичной настройке не нужно. Если состав или описания категорий/отделов понадобится отредактировать позже, система автоматически подхватит новые значения при следующем запуске. Это позволяет гибко настраивать классификацию без изменения кода.

### Распределение на приоритеты (П1, П2, П3, П4), сроки реагирования и ответственные отделы происходит по следующей логике:

```bash
ACTION_RULES = {
    "надзорная санкция и юридический риск": ("П1", "срок 48 часов", "Юристы"),
    "репутационный риск": ("П1", "срок 48 часов", "PR"),
    "pr-активность конкурента": ("П2", "срок 1 неделя", "PR"),
    "системная проблема (возможность для входа)": ("П2", "срок 1 неделя", "Аналитика"),
    "признание качества и конкурсы": ("П3", "отслеживать", "Маркетинг"),
    "косвенное упоминание": ("П3", "отслеживать", "Аналитика"),
    "информационный шум": ("П4", "игнорировать", None),
}
```

### Влиять на результаты работы llm в некоторой степени можно с помощью редактирования промптов

*Работа модуля `CategorizedModule` регламинтируется с помощью следующего промпта:*
```bash
Ты эксперт-аналитик по оценке новостей.

Исходные данные:
- Список новостей (id и text): {news_json}
- Категории и их описания: {cat_json}

Задача: отнести КАЖДУЮ новость к одной из указанных категорий.
Используй только названия категорий из списка. Не домысливай.
Если категорию определить невозможно — укажи null в поле category.
Верни ровно {len_news} элементов в items — по одному на каждую новость.
Сохраняй id и text из входных данных без изменений.
```

*Работа модуля `ToneAnalysisModule` регламинтируется с помощью следующего промпта:*
```bash
Ты эксперт-аналитик по оценке новостей.
Дан список новостей о наших конкурентах (Компания N): {news_json}

Для каждой новости определи её влияние исключительно на нашу компанию.
Используй ТОЛЬКО одну из категорий:
- "Позитивная" — конкурент слабеет (убытки, отток, проигрыш в судах, скандалы)
- "Негативная" — конкурент усиливается (инвестиции, тендеры, прорывные технологии)
- "Тревожная" — макроугроза для всей ниши (законы, проверки, нестабильность рынка)
- "Нейтральная" — рутинные действия без изменения расстановки сил
- "Нерелевантно" — бытовые/личные новости без отношения к конкуренции

Верни ровно {len_news} элементов в items — по одному на каждую новость.
```

*Работа модуля `CommentActionModule` регламинтируется с помощью следующего промпта:*
```bash
Ты бизнес-аналитик. Для каждой новости из списка сформируй:
1. Краткий комментарий — что произошло и почему это важно.
2. Рекомендацию по действию — что делать компании в ответ.

Данные: {enriched_news_json}

Верни ровно {len_news} элементов в items — по одному на каждую новость.
```

## Требования

- Python 3.10+
- API-ключ [OpenRouter](https://openrouter.ai/)

## Установка

1. Клонируйте репозиторий и перейдите в каталог проекта.

2. Создайте и активируйте виртуальное окружение:

```bash
python -m venv env
# Windows (PowerShell)
env\Scripts\Activate.ps1
# Linux / macOS
source env/bin/activate
```

3. Установите зависимости:

```bash
pip install -r requirements.txt
```

4. Создайте файл `.env` в корне проекта:

```env
OPENROUTER_API_KEY=ваш_ключ_openrouter
```

## Запуск

```bash
python main.py
```

Скрипт последовательно выполнит все модули пайплайна и выведет в консоль:

- категоризированные новости (`category_news`);
- назначенные приоритеты (`priority`);
- сроки (`deadline`);
- ответственные отделы (`department`);
- тональность (`tone_of_news`);
- комментарии (`comments`) и рекомендации (`actions`).

## Повторный запуск

Конвейер можно запускать сколько угодно раз — уже обработанные новости повторно через LLM
не гоняются, токены на них не тратятся:

- В выборку (`src/bp3/fetch_data.py::fetch_data`) попадают только `normalized_item` со
  `status='ok'`, у которых ЕЩЁ НЕТ строки в `categorized_event`. Как только новость
  категоризирована и сохранена, при следующих запусках она из выборки исчезает — дублей в
  `categorized_event` не возникает (там `UNIQUE` на `normalized_item_id`).
- Если статус `normalized_item` меняется на `ok` задним числом (например, после переразбора в
  BP-2 из-за снятого стоп-слова), такая новость сама попадёт в ближайший запуск BP-3 — это
  срабатывает автоматически, отдельного флага «пересобрать» не требуется.
- За один прогон обрабатывается не более 10 новых событий (`limit(10)` в `fetch_data`). Если
  необработанных накопилось больше, потребуется запустить конвейер повторно — это не
  пересборка уже готового, а просто добор остатка из очереди.

## Контекст пайплайна

Данные передаются между модулями через объект `ProjectContext`:

| Поле | Описание |
|------|----------|
| `news` | Список новостей с `id` и `text` (загружается из БД) |
| `manual_cat` | Список категорий и их описаний из БД |
| `manual_dept` | Список отделов и их зон ответственности из БД |
| `category_news` | Результат категоризации: каждая новость с присвоенной категорией |
| `priority` | Приоритет для каждой новости (П1–П4) |
| `deadline` | Срок действия для каждой новости |
| `department` | Ответственный отдел для каждой новости |
| `tone_of_news` | Тональность новости относительно влияния на компанию |
| `comments` | Краткий комментарий по каждой новости |
| `actions` | Рекомендация по действию |

## Настройка

**Модель LLM** — в `src/bp3/config.py`:

- провайдер: OpenRouter (`https://openrouter.ai/api/v1`);
- модель по умолчанию: `openai/gpt-4o-mini`;
- `temperature=0`, ответ в формате JSON.

**Промпты** — хранятся в `src/bp3/prompts/*.txt`. Их можно редактировать без изменения кода модулей

## Расширение пайплайна

Каждый модуль наследует `BaseModule` (или `LLMModule` для шагов с LLM) и реализует метод `process(ctx) -> ctx`. Чтобы добавить новый шаг:

1. Создайте класс модуля в `src/bp3/modules/`.
2. При необходимости добавьте промпт в `src/bp3/prompts/`.
3. Зарегистрируйте модуль в списке `Pipeline([...])` в `main.py`.

Порядок модулей в списке определяет порядок выполнения.
