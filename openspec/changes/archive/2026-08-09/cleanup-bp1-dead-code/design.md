## Goals / Non-Goals

**Goals:**
- Убрать код, который заведомо никто не вызывает, вместе со всеми его хвостами (реэкспорты, тесты, упоминания в документации).
- Довести до конца начатый перевод `adaptive/` на `core.config.settings`.

**Non-Goals:**
- Не рефакторим работающий код `adaptive/` — только удаляем неиспользуемое и правим доступ к конфигурации.
- Не решаем судьбу источников из `core/data/source.csv`, под которые нет адаптеров: они обрабатываются универсальным парсером, отдельные адаптеры — вопрос будущих итераций.
- Не наводим порядок в `.env`/`.env.example` и не выносим новые параметры в настройки — это `centralize-parsing-settings`.

## Decisions

**Удаляем целыми папками, а не файлами.** У `kad_arbitr_rpa` и пустых заготовок нет частично полезного содержимого: либо сборщик подключён к `ParserFactory` и работает, либо это мёртвый вес. Половинчатое удаление оставило бы битые импорты внутри самих папок.

**Порядок: сначала хвосты, потом сам код.** Для MCP-сервера — сначала убрать реэкспорты из `adaptive/__init__.py` и удалить тест, затем сам файл. Обратный порядок ломает импорт пакета `adaptive` на время работы, из-за чего перестают запускаться остальные тесты и не видно, что ещё зацепило.

**Каждый шаг удаления проверяется прогоном тестов, а не только линтером.** У `adaptive/` 15 файлов тестов; `ruff` поймает неиспользуемый импорт, но не поймает падение на импорте удалённого модуля внутри функции (в проекте такие отложенные импорты есть — например, `ParserFactory` внутри `AdaptiveRunner._get_parser_for_source`). Прогон тестов — единственная надёжная проверка.

**Ключи LLM для BP-1 становятся отдельными полями `Settings`, а не переиспользуют существующие.** У проекта уже три независимых набора LLM-доступов: `openrouter_api_key` (BP-3), `deepseek_token` (BP-6), и `LLM_API_KEY`/`OPENAI_API_KEY` (BP-1 adaptive). Сводить их в одно поле в рамках задачи о чистке нельзя — это смена конфигурационного контракта, к тому же провайдеры разные. Здесь только переносим чтение из `os.getenv` в `Settings` как есть; консолидация дублей (`OPENAI_API_KEY` vs `LLM_API_KEY`, `DEEPSEEK_API_KEY` vs `DEEPSEEK_TOKEN`) — задача `centralize-parsing-settings`.

**Самописный разбор `.env` в `processing/llm.py` удаляется полностью, а не «оставляется на всякий случай».** Он существует ровно потому, что модуль читал `os.getenv` и не мог рассчитывать на загруженное окружение. После перехода на `settings` (pydantic-settings сам читает `.env`) он становится вторым, конкурирующим механизмом чтения того же файла — источником расхождений, которые крайне неприятно отлаживать.

## Risks / Trade-offs

- [Риск] **Файл может использоваться не импортом, а чтением по пути** — как `core/data/*.csv`, которые чуть не попали под удаление по результатам поиска импортов. → Митигация: перед удалением каждого объекта искать его имя по всему репозиторию как строку (включая `.md`, `.yml`, `.toml`, `.txt`), а не только как модуль Python.
- [Риск] **Отложенные импорты внутри функций не видны линтеру.** В `adaptive/` есть импорты в теле методов (`from src.bp1.parsers import ParserFactory` внутри `_get_parser_for_source`) — удаление модуля проявится только при вызове этой ветки. → Митигация: прогон тестов после каждого шага; удаление делать пошагово, а не одним коммитом.
- [Риск] **Удаляемый код может понадобиться позже** — например, `kad_arbitr_rpa` при возврате к теме судебных дел. → Митигация: код остаётся в истории git и восстанавливается по имени файла; это дешевле, чем носить 2.9 МБ неработающего кода и объяснять его каждому новому разработчику.
- [Компромисс] **`fedresurs_rpa` остаётся, хотя это тоже специализированный RPA-сборщик под один источник.** В отличие от остальных он подключён к `ParserFactory` и вызывается из `AdaptiveRunner`, то есть участвует в работе. Пересмотр его судьбы — вопрос после того, как станет видно, справляется ли универсальный парсер с `fedresurs.ru` сам.
