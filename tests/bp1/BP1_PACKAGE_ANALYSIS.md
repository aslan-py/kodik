## 1. Назначение пакета

`bp1` — первый слой ETL-конвейера системы конкурентной разведки. Собирает
сырые данные о конкурентах из внешних источников (госреестры, новости,
job-board и т.д.) и сохраняет их в Bronze Layer (`raw_storage`, `RawItem`)
для дальнейшей обработки в BP-2..BP-7.

Состоит из двух контуров:

1. **Классический** — фиксированные RPA-парсеры (`FedresursAdapter`),
   единый контракт `BaseParser`/`ParserFactory`, персистентность
   (`storage.py`), оркестрация (`runner.py`, `celery_tasks.py`).
2. **Адаптивный (`adaptive/`)** — универсальный движок без ручной настройки
   под источник: классифицирует сайт, выбирает стратегию обхода защиты,
   через LLM извлекает CSS-селекторы, кэширует адаптеры, контролирует
   качество. Это основной механизм для всех источников, кроме
   fedresurs.ru (см. `README.md` строки 5-13).

## 3. Поток выполнения (end-to-end)

```
SearchTask (БД, is_active) → AdaptiveRunner.run_task()
  1. get_search_task_config()               — competitor/source/trigger/inn/is_active×3
  2. SourceClassifier.classify()             — БЕЗ html/headers (см. 4.1 — ключевая проблема)
  3. SearchParamResolver.resolve()            — ИНН для госреестров, иначе имя конкурента
  4. проверка missing_inn / circuit breaker   — пропуск бессмысленных запросов
  5. SearchUrlProber / кэш / fallback-шаблон  — построение search URL
  6. ParserFactory (спец. RPA) ИЛИ AdaptiveBridgeParser → AdaptiveParser.parse():
       a. UnifiedCache.get_adapter()                    — кэш селекторов (Redis, TTL 7д)
       b. UnifiedCache.get_classification() + AIAgent.choose_strategy()  — стартовая стратегия
       c. AgenticOrchestrator.fetch_with_degradation()   — FAST→CRAWL4AI→BROWSER→WAYBACK→STEALTH→HITL
       d. LLMClient.analyze_structure() (если адаптера нет) — извлечение CSS-селекторов
       e. _collect_news_with_pagination() → _deep_fetch()  — полный текст статей (CSS→readability→LLM→сниппет)
       f. RelevanceFilter.apply() (опционально)          — фильтр/ранжирование по релевантности
       g. DataQualityGate.validate_all()                 — 5 уровней + карантин
  7. RawDataService.persist() / persist_error()  — хэш → Redis dedup → HTML/JSON на диск → RawItem
```

Это устойчивый к сбоям, многоуровневый дизайн: почти каждый шаг имеет
эвристический fallback при недоступности LLM/Redis/сети. Но именно в
глубине этой цепочки (шаги 2, 6b, 6d) находятся главные риски для
показателя стабильности сбора — см. раздел 4.

## 4. Адаптивный сбор данных — глубокий разбор

### 4.1 Категоризация сайтов (`SourceClassifier`, `strategies/classifier.py`)

**Как работает сейчас.** `SourceClassifier.classify()` (строки 179-247)
определяет:
- `source_type` — по ключевым словам в URL/имени: `api.` → API,
  домен из `_REGISTRY_DOMAINS` (6 гос. доменов) → REGISTRY, подстроки
  `news/ria/lenta/tass/rbc/interfax` → NEWS, иначе `UNKNOWN`.
- `has_antibot` / `has_captcha` / `is_spa` — по маркерам в `headers`/`html`
  (`_ANTIBOT_MARKERS`, `_CAPTCHA_MARKERS`, `_SPA_MARKERS`), с фолбэком на
  жёстко зашитый словарь `_KNOWN_SOURCES` (**всего 6 записей**:
  fedresurs.ru, kad.arbitr.ru, zakupki.gov.ru, nalog.ru, egrul.nalog.ru,
  fips.ru).
- `complexity_score` и `recommended_strategy` — детерминированная формула
  (`_compute_complexity`, `_pick_strategy`).

Есть более мощный метод — `classify_extended()` (строки 400-450), который
детализирует `SiteType` (20 типов: news/job_board/marketplace/e_commerce/
classifieds/…) по schema.org-разметке, Open Graph, корзине, ключевым
словам на русском («вакансия», «объявлени», «отзыв»). А в
`processing/llm.py` есть **ещё более точный** `LLMClient.classify_with_llm()`,
который использует промпт `SITE_CLASSIFICATION_PROMPT_V2` (20 типов сайта,
подтип страницы, 11 бизнес-признаков, фреймворки, сложность 0.0-1.0) —
самый детальный инструмент категоризации во всём пакете.

**Ключевая находка: AI-категоризация не используется в боевом конвейере.**
Проверено через поиск по всему `src/bp1/`:
`classify_with_llm` и `classify_extended` **не вызываются** ни из
`AdaptiveRunner.run_task()` (integration/runner.py:406-418, использует
только базовый `SourceClassifier.classify()`), ни из
`SourceRegistrationService.classify()` (integration/sources.py:310-316,
тоже базовый `classify()`), ни из `AdaptiveParser`, ни из `adaptive/cli.py`.
Единственные упоминания — README и ручной smoke-тест `llm_test.py`.
Промпт `SITE_CLASSIFICATION_PROMPT_V2` в бою **никогда не отправляется в
LLM** — это мёртвый код с точки зрения продакшена.

**Практическое следствие.** Категоризация нового/неизвестного источника
в бою — это:
1. Проверка 4 хардкод-подстрок в URL/имени (api./news-домены/6 реестров).
2. При провале — `SourceType.UNKNOWN`, `complexity=0.0`,
   `recommended_strategy=FAST`.

Более того, `AdaptiveRunner.run_task()` вызывает `classify()`
**без `headers` и `html`** (integration/runner.py:408-411: передаются
только `source_name`/`source_url`) — то есть на **первом** запуске по
новому источнику классификатор в принципе не может увидеть антибот/SPA/
CAPTCHA-маркеры (они детектируются только по HTML, которого ещё нет).
Для 80%+ источников вне жёстко прошитого списка первая классификация —
это фактически угадывание «FAST, без защиты», которое почти наверняка
неверно для SPA-новостных порталов и сайтов с Cloudflare/DataDome/QRATOR.

**Второй эффект: классификация не учится на опыте.** После того как
`AgenticOrchestrator` реально продеградировал до, скажем, STEALTH и
получил контент, ни `AdaptiveParser.parse()` (processing/parser.py:364-379),
ни `AdaptiveBridgeParser.parse()` (integration/bridge.py), ни
`AdaptiveRunner.run_task()` **не обновляют** сохранённую в Redis
`SourceClassification` реальным `strategy_result.strategy`. Классификация
кэшируется один раз (TTL 7 дней, `CLASSIFICATION_TTL_SECONDS`) и продолжает
говорить «FAST» даже после десятков успешных попыток через STEALTH. Это
означает, что **каждый** повторный запуск по источнику со сложной защитой
заново проходит через FAST → CRAWL4AI → BROWSER, прежде чем дойти до
рабочей STEALTH-стратегии — то есть каждый раз платит полную стоимость
деградации (несколько таймаутов по 30-60 сек) вместо мгновенного
попадания в нужную стратегию.

### 4.2 Определение стратегии сбора

Стратегия выбирается в три слоя:

1. **`SourceClassifier._pick_strategy()`** (детерминированно):
   API → FAST; captcha → HITL; antibot → STEALTH; SPA → BROWSER; иначе FAST.
2. **`AIAgent.choose_strategy()`** (`processing/llm.py:521-537`) — уточняет
   стратегию через LLM-промпт `STRATEGY_CHOICE_PROMPT`
   (`_llm/prompts.py:242-248`) поверх той же классификации; при недоступности
   LLM — эвристика `heuristic_strategy()` (дублирует правило из п.1
   практически один в один). Вызывается только если классификация уже
   есть в кэше (`processing/parser.py:345`) — то есть на **первом** запуске
   по источнику агент не консультируется вообще.
3. **`AgenticOrchestrator.fetch_with_degradation()`** (`orchestrator.py:393-498`)
   — фактическая защитная сетка: пробует стратегии по кольцу
   `FAST → CRAWL4AI → BROWSER → WAYBACK → STEALTH → HITL`, начиная с
   `start_with` и «дозаходя» с начала цепочки. Считает страницу успешной,
   только если она одновременно (а) ≥ `MIN_CONTENT_LENGTH` символов и
   (б) содержит ≥ 3 ссылок для не-браузерных стратегий (`_is_informative_html`,
   защита от «пустого JS-skeleton», строки 38-64) — качественная эвристика,
   решающая реальную проблему (SPA отдают HTTP 200 с пустым `<div id="root">`).

**Сильные стороны.** Сама деградационная лестница спроектирована
разумно: правильно отличает «пустой каркас» от контента, использует
`page.wait_for_selector` по нескольким шаблонам селекторов результатов
поиска (`_NEWS_CONTAINER_SELECTORS`) вместо ненадёжного `networkidle`,
гарантированно освобождает ресурсы браузера через `asyncio.shield` даже
при отмене по таймауту (строки 338-351). Это зрелый, продуманный код.

**Слабые стороны, влияющие на устойчивость:**

- **Слепой холодный старт** (см. 4.1) — двухслойная «умная» часть
  (классификатор + LLM-агент) почти не работает на первом запуске для
  неизвестных источников, вся нагрузка ложится на дорогую по времени
  деградационную лестницу.
- **Порядок деградации фиксирован и не персонализируется.** `CRAWL4AI`
  всегда пробуется вторым, даже для источников, где заведомо нужен
  `STEALTH` (антибот) — то есть, например, для сайта с Cloudflare
  тратятся 2 заведомо бесполезные попытки (FAST + CRAWL4AI) перед
  переходом к рабочей стратегии, если классификация не сработала верно.
- **`_ssl_unverified_context()`** (`orchestrator.py:85-99`) отключает
  проверку TLS-сертификата глобально как fallback для FAST/STEALTH —
  риск MITM без документированного обоснования уровня риска (см. TODO.md
  п.12); для инструмента конкурентной разведки, тянущего данные о
  бизнесе, это стоит явно документировать/ограничить только известными
  гос.доменами с самоподписанными сертификатами, а не применять глобально.
- **`Crawl4AIStrategy`/`StealthStrategy`** зависят от опциональных пакетов
  (`crawl4ai`, `playwright`) — при их отсутствии/несовместимости
  исключение ловится и превращается в `success=False` с логом
  `warning` (хорошо), но в проде это тихо понижает эффективную цепочку
  до `FAST → BROWSER → WAYBACK → HITL`, и никакой метрики/алерта об этом
  нет (см. 4.3 и TODO.md п.19 «нет метрик качества»).
- **`HITL`** требует видимого браузера и присутствия человека
  (`timeout_s=120` по умолчанию) — в полностью автоматическом
  Celery-конвейере это по факту эквивалент отказа, если не настроен
  специальный процесс мониторинга HITL-очереди. Нет данных о том, что
  такой процесс существует за пределами `ProfileManager`/кэша cookies.

### 4.3 Промпты к ИИ (`adaptive/processing/_llm/prompts.py` + `prompt_builders.py`)

Инвентаризация всех промптов:

| Промпт | Назначение | Вызывается из | Используется в бою? |
|---|---|---|---|
| `SITE_CLASSIFICATION_PROMPT_V2` | Детальная категоризация сайта (20 типов, подтип, бизнес/технические признаки, сложность) | `LLMClient.classify_with_llm` | **Нет** (см. 4.1) |
| `SELECTOR_EXTRACTION_PROMPT_V2` | Извлечение CSS-селекторов (расширенный вариант) | Нигде не вызывается напрямую (есть более простой `_ANALYSIS_HEADER`+`_ANALYSIS_RESPONSE_RULES`, используемый `build_analysis_prompt`) | **Нет** — дублирующий мёртвый промпт |
| `_ANALYSIS_HEADER` + `_ANALYSIS_RESPONSE_RULES` | Извлечение селекторов (реальный, короткий вариант) | `LLMClient.analyze_structure` → `_llm_analyze` | Да — основной путь генерации адаптера |
| chunk-промпт (инлайн в `prompt_builders.build_chunk_prompt`) | Извлечение селекторов из одного чанка большой страницы | `LLMClient.analyze_structure_chunked` | Да |
| `STRATEGY_CHOICE_PROMPT` | Выбор стратегии обхода по классификации | `AIAgent.choose_strategy` | Да, но только когда классификация уже в кэше |
| `RESULT_ANALYSIS_PROMPT` | Анализ результата парсинга, рекомендации | `AIAgent.analyze_result` | **Нет** — не вызывается ни из `AdaptiveParser`, ни из `AdaptiveRunner`, ни из `cli.py` (только `llm_test.py`) |
| `RELEVANCE_PROMPT` | Пакетный скоринг релевантности новостей конкуренту/теме | `AIAgent.score_relevance` (через `RelevanceFilter`) | Да, но **выключено по умолчанию** (`bp1_relevance_mode = 'off'`) |
| `ENRICHMENT_PROMPT` | Извлечение published_at/author/keywords/summary/mentioned_company/sentiment | `AIAgent.enrich_event` | Да, но **выключено по умолчанию** (`bp1_enrichment_enabled = False`) |
| `ARTICLE_TEXT_PROMPT` | Извлечение основного текста статьи из HTML | `LLMClient.extract_article_text` | Да — часть каскада CSS→readability→LLM→сниппет |

**Итого из 9 промптов в бою реально участвуют 5, а из них 2
(`RELEVANCE_PROMPT`, `ENRICHMENT_PROMPT`) отключены дефолтными
настройками.** Это важно для оценки «интеллектуальности» системы:
формально пакет заявляет богатый LLM-слой, а по факту рабочая цепочка —
это извлечение селекторов + извлечение текста статьи + (иногда) выбор
стратегии. Категоризация, релевантность и обогащение либо не
подключены, либо выключены по умолчанию.

**Качество промптов и инженерии вокруг них — сильная сторона:**
- Все промпты требуют **строго JSON**-ответ, разбор — через
  `json_utils.parse_json()` (`_llm/json_utils.py:20-66`), который
  трёхступенчато пытается распарсить: прямой JSON → markdown-блок
  ` ```json ``` ` → первый `{...}` фрагмент в тексте. Устойчиво к типичным
  «болтливым» ответам модели.
- `temperature=0.0` для всех детерминированных задач извлечения/
  классификации/релевантности/обогащения (`constants.py:31,37,42`) —
  правильный выбор для стабильности повторяемого JSON-вывода.
- Ретраи с экспоненциальной задержкой (`client.py:86-119`,
  `RETRY_BASE_DELAY_S=1.0` → `RETRY_MAX_DELAY_S=8.0`, 3 попытки) на
  уровне HTTP-вызова к LLM.
- Response-схемы типизированы через Pydantic (`_llm/schemas.py`) и
  маппятся в доменные модели (`mappers.py`) — невалидные/отсутствующие
  поля превращаются в дефолты, а не в падение пайплайна.
- Везде, где LLM недоступен или ключ не задан (`has_llm_config()` →
  `bool(settings.llm_api_key)`), есть эвристический fallback
  (`heuristics.py`) — пакет функционально жив без LLM, просто менее точен.
- Чанкирование больших страниц (`StructuredChunker`, `max_chunk_size=8000`,
  `overlap_size=500`, до 10 чанков, до 5 параллельно) с последующим
  `ResultMerger` — разумный инженерный подход к контекстным лимитам.

**Проблемы промптов:**
- `SELECTOR_EXTRACTION_PROMPT_V2` — полностью дублирует функциональность
  `_ANALYSIS_HEADER`/`_ANALYSIS_RESPONSE_RULES`, но не используется;
  наличие двух непересекающихся промптов для одной задачи — источник
  путаницы при поддержке (правки в одном не попадут в реально работающий).
- `RESULT_ANALYSIS_PROMPT` (анализ результата → рекомендация по
  улучшению адаптера) не подключён в цепочку обратной связи: даже если
  бы он вызывался, `analyze_result()` **только возвращает** рекомендацию
  строкой — нет кода, который бы применял `recommendation` к
  `AdapterState` (например, сбрасывал кэш адаптера при низком качестве).
  Т.е. это в лучшем случае наблюдаемость, а не самоисправление.
- `RELEVANCE_PROMPT`/`ENRICHMENT_PROMPT` отправляют **весь список
  новостей одним запросом** (`build_relevance_prompt`) — при большом
  `max_news` это упирается в `RELEVANCE_MAX_TOKENS=2048` и может обрубать
  ответ модели для >15-20 новостей; сейчас риск замаскирован тем, что
  `bp1_max_news_per_source=3` (см. 4.4), но при увеличении лимита новостей
  без пересмотра батчирования релевантность начнёт молча деградировать
  (JSON обрежется, `parse_json` вернёт `{}`, отработает fallback на
  эвристику без предупреждения пользователю о причине).
- Промпт классификации (`SITE_CLASSIFICATION_PROMPT_V2`) передаёт
  «HTML (первые 12000 символов)» **до** очистки в некоторых путях — в
  `classify_with_llm` очистка есть (`HtmlCleaner`), но раз метод не
  вызывается в бою, вопрос неактуален до момента интеграции (см.
  рекомендации).

### 4.4 Прочие узкие места устойчивости

- **`bp1_max_news_per_source = 3`** (`core/config.py:179`) — по умолчанию
  за один прогон собирается **всего 3 новости** с источника. В сочетании
  с тем, что пагинация (`_collect_news_with_pagination`) останавливается,
  как только набрано `max_news` элементов, это резко ограничивает охват:
  для источника с активными упоминаниями конкурента система систематически
  не увидит события 4-е и далее в рамках одного запуска. Это не «баг», а
  явная настройка экономии, но именно она — а не отказы стратегий — может
  быть причиной субъективного ощущения «мало данных» в бою.
- **`_max_pages()` жёстко возвращает `10000`** (`processing/parser.py:643-646`,
  подтверждено в TODO.md п.10) — практического лимита пагинации нет,
  единственный тормоз — `max_news`. Если `max_news` увеличат без
  привязки лимита страниц, возможен неконтролируемый по времени прогон.
- **Классификация без учёта прошлых отказов конкретной стратегии.**
  `UnifiedCache` умеет блокировать источник целиком (circuit breaker,
  `is_source_blocked`/`block_source`, `source_disable_threshold=3` подряд
  полных отказов → `Source.is_active=False`), но не запоминает «эта
  стратегия для этого источника не работает» на уровне отдельной
  стратегии — только на уровне «всё упало». При частичных сбоях (FAST
  падает, STEALTH работает) это нормально покрывается деградацией внутри
  одного запуска, но между запусками теряется (см. 4.1, «классификация не
  учится»).
- **`SearchUrlProber`** (`integration/search_probe.py`) — частично стаб;
  `AdaptiveRunner` уже подключил реальные `_default_probe_fetch`/
  `_default_looks_like` (TODO.md отмечает как исправленное), но форма
  (`POST`) и переформулировки поискового запроса остаются заглушками —
  для источников с поиском через форму/JS (а не GET `?q=`) вероятность
  найти рабочий search URL ниже.
- **Дедупликация в `raw_storage`** — `NoOpDeduplicator` всегда возвращает
  `False` (подтверждено, TODO.md п.4/15) — не влияет на «сбор» данных
  напрямую, но означает, что Bronze Layer может копить дубликаты сверх
  той дедупликации, что даёт Redis-хэш в `storage.py`.

## 5. Оценка эффективности в боевом применении

### 5.1 Сильные стороны архитектуры

- Многоуровневая деградация с содержательной проверкой «информативности»
  HTML — редкое для подобных систем внимание к деталям (JS-shell problem).
- Полный набор эвристических fallback'ов на каждом уровне (LLM недоступен →
  эвристика; Redis недоступен → работа без кэша; сеть недоступна →
  следующая стратегия) — пакет не имеет единой точки отказа "нет LLM/нет
  Redis = вообще ничего не работает".
- Circuit breaker и авто-отключение мёртвых источников — предохраняет от
  бесконечных повторных попыток по заведомо недоступным сайтам.
- Source-aware выбор поискового параметра (ИНН для реестров, имя для
  остального) и per-source URL-шаблоны — устраняет класс ошибок
  «искали не по тому полю».
- Каскад извлечения текста статьи (CSS-селектор → `trafilatura`/
  `readability` → LLM → сниппет с докачкой обрезанного хвоста) — сильный,
  редко встречающийся уровень проработки полноты текста.
- 5-уровневый Quality Gate с персистентным карантином — проблемные записи
  не теряются молча.

### 5.2 Что реально ограничивает стабильность на уровне 80-90%

Собранные в разделе 4 находки формируют одну сквозную причину: **слой
«интеллекта» (категоризация + выбор стратегии через LLM) почти не
участвует в определении поведения на новых/неизвестных источниках** —
либо потому что вызывается без входных данных (HTML), либо потому что
не вызывается вовсе (`classify_with_llm`), либо потому что результат
успешного прогона не запоминается (классификация не обновляется). Реальную
устойчивость сейчас обеспечивает не «умная категоризация», а «грубая сила»
оркестратора деградации — рабочий, но медленный и не обучающийся механизм.

Для источников из `_KNOWN_SOURCES`/`_REGISTRY_DOMAINS` (6 доменов) и
явных news-доменов по ключевым словам — категоризация и стратегия
выбираются корректно с первого раза. Для всех остальных источников
(а именно они, по духу задачи — «конкурентная разведка» с произвольными
сайтами конкурентов, составляют большинство) первый прогон почти
гарантированно тратит время на 1-2 заведомо проигрышные стратегии, а
устойчивый успех (80-90%) достигается только за счёт полного перебора
цепочки — то есть ценой времени выполнения, а не точности предсказания.

## 7. Рекомендации для устойчивого сбора 80-90%

Порядок — по влиянию на итоговый % успешных сборов при минимальных
трудозатратах.

### 7.1 Высокий приоритет — устраняют системную причину нестабильности

1. **Подключить `classify_with_llm` как основной путь категоризации новых
   источников**, а не мёртвый код. Схема: при первом обращении к
   источнику — сначала быстрый детерминированный `classify()` (для
   мгновенного ответа и как fallback), затем — если `has_llm_config()` —
   уточнение через `classify_with_llm()` **после первого удачного fetch**
   (см. п.2), результат которого перезаписывает кэш. Это закрывает N1 и
   резко повышает точность категоризации для source вне хардкод-списков.
2. **Классифицировать по реальному HTML, а не вслепую.** Изменить
   порядок в `AdaptiveParser.parse()`/`AdaptiveRunner.run_task()`:
   сначала дешёвая попытка `FAST`-стратегией (не для выбора финальной
   стратегии, а для получения HTML/заголовков), затем
   `SourceClassifier.classify(html=..., headers=...)` по её результату, и
   только потом полноценная деградация с уже осмысленным `start_with`.
   Закрывает N2.
3. **Персистентно обновлять классификацию по факту успешной стратегии.**
   После `strategy_result.success` в `AdaptiveParser.parse()` — вызывать
   `cache.set_classification()` с обновлённым `recommended_strategy =
   strategy_result.strategy`, а не только кэшировать один раз на 7 дней.
   Это самое дешёвое по трудозатратам изменение с наибольшим эффектом на
   latency повторных прогонов (закрывает N3, косвенно и N4 — при
   прогретом кэше агент вызывается сразу с верной классификацией).
4. **Персонализировать порядок деградации по типу обнаруженной защиты.**
   Если классификация (даже эвристическая) уже говорит `has_antibot=True`,
   пропускать заведомо бесполезные `FAST`/`CRAWL4AI` и начинать сразу со
   `STEALTH`, оставляя лёгкие стратегии только для источников без
   признаков защиты. Механизм `start_with` в `fetch_with_degradation`
   уже это умеет — не хватает более агрессивного использования результата
   классификации на входе (частично закрывается через N2, но стоит
   явно исключать заведомо провальные шаги, а не просто переставлять
   порядок начала). Закрывает N10.
5. **Включить `RELEVANCE_MODE=filter` (или `rank`) и `ENRICHMENT_ENABLED`
   в бою**, предварительно устранив риск N7 (см. 7.2, п.3) — иначе
   заявленная «адаптивность» ограничена извлечением селекторов, а не
   пониманием релевантности данных, что напрямую нужно для «устойчивого
   сбора», а не только «устойчивого скачивания HTML».

### 7.2 Средний приоритет — повышают полноту и надёжность конкретных путей

1. Реализовать `NoOpDeduplicator` (T2) — без реальной дедупликации Bronze
   Layer накапливает шум, который потом ошибочно считается «новыми
   данными» на нижних слоях конвейера.
2. Довести `SearchUrlProber` до реализации POST-форм и переформулировок
   (T4) — расширяет список источников, где поисковый URL вообще
   находится.
3. Батчировать `RELEVANCE_PROMPT`/`ENRICHMENT_PROMPT` по фиксированному
   размеру пачки (например, 10-15 элементов на запрос) вместо одного
   запроса на весь список, с агрегацией ответов — закрывает N7 и снимает
   блокер для увеличения `bp1_max_news_per_source` (N9) без риска молчаливой
   деградации LLM-ответа.
4. Поднять `bp1_max_news_per_source` выше 3 (например, 15-20) **только
   после** выполнения п.3 — иначе рост охвата увеличит частоту усечения
   JSON-ответа релевантности/обогащения.
5. Параметризовать `_max_pages()` (T5) и синхронизировать его с новым
   `max_news`, чтобы рост охвата не превращался в неограниченный по
   времени прогон.
6. Реализовать конкурентность в `AdaptiveRunner.run_all()` через уже
   существующий, но неиспользуемый `max_concurrent` (T1) — без этого
   рост числа источников линейно увеличивает время полного прогона.
7. Задокументировать/ограничить `_ssl_unverified_context()` (N11) явным
   списком доменов, где это осознанно допустимо (гос. порталы с известными
   самоподписанными сертификатами), вместо глобального fallback для всех
   FAST/STEALTH-запросов.

### 7.3 Низкий приоритет — наблюдаемость и гигиена

1. Добавить метрики по уровням `DataQualityGate` (T6) и по частоте
   деградации до каждой стратегии на источник — без этого невозможно
   отследить регресс раньше, чем «упадёт процент успешных сборов».
2. Удалить мёртвый промпт `SELECTOR_EXTRACTION_PROMPT_V2` (N5) либо явно
   подключить его вместо текущего, если он лучше по качеству — сейчас
   поддерживаются два промпта на одну задачу.
3. Либо подключить `AIAgent.analyze_result()`/`RESULT_ANALYSIS_PROMPT` в
   цепочку авто-коррекции адаптера (сброс кэша селекторов при низком
   confidence/качестве), либо удалить как нереализованную функцию,
   которая создаёт ложное ощущение самообучения системы (N6).
4. Превратить `llm_test.py` в автотест с моками (уже сделано частично —
   `test_prompt_builders.py`, `test_json_utils.py` покрывают сборку
   промптов и разбор ответов, но не проверяют реальные лимиты токенов
   при большом числе элементов — см. T7).
5. Синхронизировать `raw_storage/README.md` с фактическими полями моделей
   (TODO.md, средний приоритет).

## 8. Итоговая оценка

Инженерная база пакета (деградация стратегий, каскад извлечения текста,
устойчивый JSON-парсинг, эвристические fallback'и, circuit breaker) —
качественная и хорошо продумана на уровне отдельных механизмов. Текущее
узкое место — не в отдельных компонентах, а в том, что они слабо связаны
в контур обратной связи: категоризация выполняется вслепую и один раз,
самый точный инструмент категоризации (LLM) не подключён к продакшену,
а опыт успешных сборов не переиспользуется на следующих прогонах.
Рекомендации раздела 7.1 (пункты 1-4) устраняют именно эту системную
причину и являются минимально достаточным набором изменений для
приближения к устойчивым 80-90% успешных сборов без пересмотра
архитектуры — остальные рекомендации повышают полноту и
эксплуатационную наблюдаемость поверх уже устойчивого ядра.
