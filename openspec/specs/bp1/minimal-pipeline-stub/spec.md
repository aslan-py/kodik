# bp1/minimal-pipeline-stub Specification

## Purpose

Заглушка этапа 1 пайплайна заливает фиксированный минимальный набор данных вместо полного демо-датасета, чтобы сквозная проверка этапов 2-7 через пайплайн/админку не расходовала токены LLM и лимиты внешних API впустую.

## Requirements

### Requirement: Заглушка этапа 1 заливает минимальный набор
Заглушка этапа 1 конвейера ОБЯЗАНА при каждом запуске заливать фиксированный минимальный набор: один конкурент, один снимок (`raw_item`), шесть новостей со спроектированными исходами по фильтрам BP-2 — две доходят до `status=ok` в `normalized_item` (пригодны для дальнейшей категоризации BP-3), четыре отклоняются разными механизмами отсева (чёрный домен, стоп-слово, антишум по повторяющемуся домену).

#### Scenario: Запуск заглушки этапа 1
- **WHEN** запрошен запуск этапа 1 (по кнопке в админке, через CLI или как часть `run_all()`)
- **THEN** в `raw_item` появляется ровно один новый снимок на одного конкурента с шестью новостями, который после прогона BP-2 (при заполненных чёрном домене/стоп-слове/лимите антишума под эти новости) даёт ровно две строки со `status=ok` в `normalized_item`

### Requirement: Полный демо-сидер остаётся отдельной командой
Полный демо-датасет (`core/scripts/stages/bp1.py`, ~49 конкурентов) ОБЯЗАН оставаться доступным только через явный самостоятельный запуск (`python -m core.scripts.stages.bp1`), не через заглушку этапа 1 в реестре пайплайна.

#### Scenario: Запуск полного демо-сидера не затрагивает заглушку пайплайна
- **WHEN** кто-то запускает `python -m core.scripts.stages.bp1` напрямую
- **THEN** заливается полный демо-датасет как раньше, и это никак не меняет поведение заглушки этапа 1 при последующих запусках через реестр пайплайна

#### Scenario: Запуск заглушки этапа 1 не требует и не трогает флаги окружения
- **WHEN** запускается заглушка этапа 1
- **THEN** объём заливаемых данных не зависит ни от каких переменных `.env` — минимальный набор заливается всегда, независимо от конфигурации окружения
