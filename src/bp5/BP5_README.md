# BP-5: Детектор значимых событий и алертинг

BP-5 берёт новые/изменившиеся строки витрины (`showcase_event`, BP-4), ищет
среди них значимые события по ключевым словам и рассылает алерты конкретным
людям по матрице маршрутизации. Управляется пятью справочниками — их
заполняет аналитик без изменения кода.

---

## Справочники

### `event_type` — типы значимых событий
Чем ловим («судебный/надзорный риск», «выигранный тендер»…) и по каким
словам-маркерам.

| Поле | Тип | Описание |
|------|-----|---------|
| `name` | string | Название типа — для отчёта и для поиска правила маршрутизации |
| `keywords` | string[] | Слова-маркеры: `[«прокуратура», «суд», «иск»]`. Ищем вхождение любого в `title` витрины (без учёта регистра) |
| `is_active` | bool | `true` — тип участвует в детекции |

`keywords` и `name` — для разного: `keywords` **ловит** событие,
`name` его **называет**. Массив, а не строка через запятую — по образцу
`region.name_aliases` (тот же GIN-индекс, тот же принцип «список альтернатив»).

### `channel` — каналы доставки
`telegram`, `email`, `dashboard`. Просто тип связи; конкретный адрес
(куда именно слать) лежит не здесь, а в `user`.

### `user` — получатели алертов
Конкретные люди, а не отделы.

| Поле | Тип | Описание |
|------|-----|---------|
| `full_name` | string, nullable | ФИО — для читаемости в админке, не критично |
| `department_id` | FK → `department` | В каком отделе числится. **Справочно**, не источник для рассылки |
| `email` | string, unique, not null | Адрес для канала `email` |
| `telegram_login` | string, unique, not null | Логин для канала `telegram` |
| `is_active` | bool | Уволен/в отпуске — гасим флагом, историю алертов не теряем |

**Почему не через отдел.** Список получателей курируется вручную и может
не совпадать со штатом отдела: сегодня алерт нужен троим из пяти юристов,
завтра — одному. `department_id` в `routing_rule` для этого не годится:
отдел не говорит, КОМУ конкретно слать. Отдел не теряется — он виден через
`user.department_id`, просто не хранится отдельным полем там, где решается
маршрутизация.

### `routing_rule` — матрица маршрутизации
Тип + приоритет → получатель + канал + режим. Аналитик заполняет заранее,
читается как «если событие такого типа и такого приоритета — шли вот этому
человеку в этот канал».

| Поле | Тип | Описание |
|------|-----|---------|
| `event_type_id` | FK → `event_type` | Для какого типа события |
| `priority` | enum | Для какого приоритета срабатывает правило |
| `user_id` | FK → `user` | Кому конкретно |
| `channel_id` | FK → `channel` | В какой канал |
| `mode` | enum | `instant` (П1, сразу) \| `digest` (П2, сводкой) |
| `is_active` | bool | `true` — правило активно |

**Несколько получателей и/или каналов на одну пару (тип, приоритет) — это
просто несколько строк.** Хотите добавить четвёртого юриста в рассылку по
судебным рискам — одна новая строка, без правки кода. Пример: у «судебный/
надзорный риск + П1» в демо-данных три строки — два канала для одного
человека и один канал для другого, то есть три алерта на одно событие.

**Порог значимости — не константа в коде, а сам этот справочник.** Значимо
то событие, для которого нашлась строка на пару (тип, приоритет). Не
нашлась — не значимо. Если аналитик решит алертить и на П3 (как уже сделано
для «расширение» в демо-данных) — это одна новая строка, а не доработка кода.

## Выходная таблица `alert`

Журнал доставок. `status=ok` → значит: событие проверили, нашлась строка
`routing_rule`, алерт записан. Одна строка `alert` = одна доставка одному
получателю в один канал.

| Поле | Тип | Описание |
|------|-----|---------|
| `id` | int | Первичный ключ |
| `showcase_event_id` | int | По какому событию витрины сработал алерт |
| `event_type_id` | int | Какой тип распознан |
| `priority` | enum | Приоритет события **на момент алерта** (снимок, не ссылка) |
| `user_id` | int | Кому ушло |
| `channel_id` | int | Каким каналом |
| `mode` | enum | Снимок режима из правила: `instant` \| `digest` |
| `status` | enum | `queued` → `sent` / `failed` |
| `error_message` | string, nullable | Текст ошибки при `status=failed` |
| `created_at` | datetime | Когда завели алерт |
| `sent_at` | datetime, nullable | Когда фактически доставлено |

**Почему снимок, а не ссылка.** `priority` и `mode` копируются в момент
записи, а не читаются каждый раз из `routing_rule`/`showcase_event`: правило
завтра поменяют, пользователь сменит отдел — а история уже отправленных
алертов должна остаться прежней.

**`UNIQUE(showcase_event_id, channel_id, user_id)`** — защита от повторной
отправки: тот же получатель в тот же канал по тому же событию не получит
алерт дважды, даже если детектор перепроверит событие ещё раз.

## Как работает прогон

```
select_pending_events  →  detect_event_type  →  build_alert_rows  →  insert_alerts  →  mark_checked
     (crud.py)              (pipeline.py)         (pipeline.py)        (crud.py)         (crud.py)
```

Запуск: `run_bp5()` из `src/bp5/pipeline.py` — открывает свою сессию и
коммитит. Внутри чужой транзакции (так делает сидер) — `sync_alerts(session)`.

### Критерий «событие нужно проверить»

```
showcase_event.alerted_at IS NULL
ИЛИ showcase_event.updated_at > showcase_event.alerted_at
```

**Почему не по журналу `alert`.** Событие может быть честно проверено и не
дать ни одного алерта (ключевые слова не совпали, или правила для найденного
типа и приоритета нет). Критерий «id отсутствует в `alert`» не отличил бы
«ещё не проверено» от «проверено — не значимо»: такое событие проверялось бы
заново на каждом прогоне впустую. `alerted_at` — маркер на самой витрине,
проставляется **независимо от результата** (тот же приём, что `raw_item.
updated_at` в BP-1 и `categorized_at > showcase_event.updated_at` в BP-4).

Если BP-4 позже пересоберёт строку витрины (переразметка BP-3) —
`updated_at` сдвинется вперёд, и BP-5 честно перепроверит событие заново.

### Детекция и маршрутизация

`title.lower()` против `keywords` каждого активного `event_type` —
первое совпадение побеждает (порядок из БД). Если заголовок подходит сразу
под два типа, поймается только первый; матчинг всех подошедших типов —
расширение на будущее, сейчас не требуется.

Найденный тип + приоритет события ищутся в `routing_rule`. Каждая найденная
строка правила даёт одну строку `alert`.

### Доставка

`instant` помечается `status=sent` сразу — это **заглушка**, реального
обращения к Telegram Bot API / SMTP пока нет. `digest` остаётся
`status=queued` — сборка и отправка пачки по расписанию (джоба-сводка)
не реализована в этом заходе. Обе задачи — за рамками текущей версии,
см. ниже.

## Осознанно не реализовано

- **Реальная отправка в telegram/email.** Интеграция с Bot API / SMTP —
  отдельная задача.
- **Джоба-сводка для `digest`.** ТЗ требует «П2 — в составе регулярной
  сводки»: сборка `WHERE mode='digest' AND status='queued'` по расписанию
  и массовая отправка — отдельный модуль.
- **Celery-обвязка.** В проекте её пока нет ни для одного BP; `run_bp5()`
  вызывается напрямую, как `run_bp2()`/`run_bp4()`.
- **Несколько типов на одно событие.** Сейчас — первое совпадение по
  порядку из БД, не все подошедшие типы разом.

## Известное ограничение

Добавление колонки в `showcase_event` **не** подхватывается инкрементом
BP-5 (он реагирует на `updated_at`, а не на изменение схемы) — тот же
случай, что описан в `src/bp4/BP4_README.md`. После такой миграции нужен
разовый пересбор.
