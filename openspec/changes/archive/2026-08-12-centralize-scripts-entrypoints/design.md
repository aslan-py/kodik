Что лежит в `core/scripts/` и что о нём известно:

| Модуль | Строк | В README | Кто вызывает | Судьба |
|---|---|---|---|---|
| `seed_all.py` | 66 | да | вручную | оставить |
| `clear_data.py` | 64 | да | вручную | оставить |
| `universal_script_1.py` | 359 | да, текст устарел | вручную | обновить или удалить |
| `seed_data.py` | 579 | **нет** | никто | оставить, документировать |
| `migrate_raw_files.py` | 167 | **нет** | никто | вероятно удалить |
| `stages/*.py` | — | частично | реестр, вручную | оставить |

`seed_data.py` читает `core/data/*.csv` через `Path`, а не импортом — поэтому поиск по зависимостям его связь с данными не показывает. Это та же ловушка, что описана в `cleanup-bp1-dead-code`: файл, который открывают по пути, выглядит несвязанным.

Три способа наполнить первый этап после подключения реального сбора:

```
реальный сбор       →  живые источники, требует search_task, стоит времени и лимитов
stages/bp1.py       →  ~49 конкурентов, 100+ новостей из CSV — наполнить витрину для BI
stages/bp1_stub.py  →  6 синтетических новостей — проверить конвейер целиком за секунды
```

## Goals / Non-Goals

**Goals:**
- По README можно понять, что запускать под конкретную задачу, не читая исходники скриптов.
- В папке не остаётся исполняемых модулей, о назначении которых нельзя узнать из документации.

**Non-Goals:**
- Не меняем поведение сидеров и состав демо-данных.
- Не переносим скрипты между папками и не переименовываем — только документация и удаление лишнего.
- Не заводим единую точку входа вместо нескольких команд.

## Decisions

**README строится от сценариев, а не от перечня файлов.** Текущая таблица «команда → что заполняет» отвечает на вопрос «что делает этот файл», тогда как читателю нужен ответ на «что мне запустить». Разделы становятся сценарными: развернуть с нуля, залить боевую конфигурацию, прогнать на тестовых данных, наполнить витрину, почистить. Таблица «команда → что заполняет» остаётся, но как справочник в конце, а не как основное содержание. _Альтернатива —_ дополнить существующую таблицу недостающими строками: отвергнута, это лечит неполноту, но не главную проблему — по таблице всё равно не выбрать между тремя способами наполнить первый этап.

**`seed_data.py` и `core/data/` остаются и получают явный статус отдельного тестового набора.** Соблазн удалить их велик: не описаны, никем не вызываются, выглядят как остатки ранней итерации. Но это единственный готовый набор с правдоподобными источниками и ИНН конкурентов — то, на чём удобно проверять реальный сбор, не выдумывая данные заново. В README он разводится с демо-данными `scripts_data/`, которыми пользуются `seed_all.py` и `stages/bp1.py`: два набора существуют параллельно, и путаница между ними — часть той же болезни, что и неописанные скрипты.

**`migrate_raw_files.py` удаляется, а не документируется.** Одноразовая миграция формата хранения сырья: она либо уже применена везде, где были старые данные, либо неприменима — актуальные развёртывания создают файлы сразу в нужном формате. Держать в папке скрипт, который нельзя осмысленно запустить сегодня, — та же болезнь, что описана в задаче. Перед удалением проверить, что формат, к которому он приводил, действительно текущий. _Альтернатива —_ описать его как исторический: отвергнута, README не должен объяснять, чего запускать не надо.

**Судьба `universal_script_1.py` решается по факту, а не заранее.** Он делает то, что уже покрыто комбинацией других команд (миграции + сидинг + запуск сервера), и его описание успело устареть — что само по себе признак того, что им не пользуются и за ним не следят. Но сценарий «одна команда, чтобы посмотреть всё целиком» ценен для нового человека в проекте. Решение принимается при выполнении: если после переписывания README сценарий разворачивания с нуля читается как две-три понятные команды — скрипт удаляется; если он остаётся, его докстринг и описание приводятся в соответствие с текущим составом конвейера.

**Правило на будущее: исполняемый модуль в `core/scripts/` либо описан в README, либо его нет.** Без явного правила папка зарастёт снова — она уже зарастала дважды. Правило записывается в сам README, чтобы попадалось на глаза тому, кто добавляет новый скрипт.

## Risks / Trade-offs

- [Риск] **`migrate_raw_files.py` может понадобиться при подъёме старого дампа.** → Митигация: перед удалением убедиться, что формат хранения, к которому он приводит, совпадает с текущим; код остаётся в истории git и восстанавливается по имени файла.
- [Риск] **`seed_data.py` не проверен в работе** — он не описан и не вызывался, поэтому мог отстать от текущей схемы БД. → Митигация: прогнать его на чистой базе в рамках проверки; если не работает — это отдельная находка, а не повод удалять данные, которые он заливает.
- [Компромисс] **README становится длиннее.** Сценарное изложение объёмнее таблицы. Приемлемо: документ читают, когда не знают, что делать, и в этот момент важнее полнота, чем краткость.
