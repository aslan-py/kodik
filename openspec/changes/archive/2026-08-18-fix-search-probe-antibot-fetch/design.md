## Context

См. `proposal.md` — почему это нужно. Технический контекст, важный для
решения:

- `AdaptiveRunner.__init__` жёстко подключает `SearchUrlProber(fetch=self
  ._default_probe_fetch, ...)` — голый `urllib`-GET, без браузера и без
  учёта известной защиты источника (`runner/core.py:138-141`).
- Классификация источника резолвится и доступна ДО вызова пробера
  (`_resolve_classification`, `runner/core.py:337`), но не доходит до
  выбора fetch-транспорта — пробер получает только `source_type`, не
  `has_antibot`/`is_spa`/`recommended_strategy`.
- `AgenticOrchestrator.fetch_with_degradation(url, classification=...)`
  уже умеет сокращать лестницу деградации по классификации (не пробует
  FAST/CRAWL4AI при известном антиботе) — переиспользуем существующий
  API, не изобретаем новый.
- Перебор кандидатов сейчас рассчитан на дешёвый fetch: до 7 параметров +
  форма + 5 реформулировок = до ~13 запросов на одну задачу сбора.
  С деградационным fetch (реальный браузер) такая ширина перебора
  становится дорогой и медленной.
- Пробинг для одной задачи сейчас выполняется дважды независимо: прямой
  `self._prober.probe(...)` (`runner/core.py:425`, результат идёт только в
  `matched_variant`/имя конкурента) и `_get_or_probe_url` →
  `probe_async()` (`runner/core.py:492`, результат — реальный URL для
  парсинга). Эти два прогона МОГУТ выбрать разные варианты.
- `_get_or_probe_url` кэширует результат неудавшегося перебора как
  `ProbedUrl(confidence=0.0)` (fallback на шаблон) и на следующий вызов
  отдаёт его из кэша БЕЗ повторной попытки — источник с исправленным
  пробером всё равно останется на неверном URL, пока кэш не истечёт
  (TTL 7 дней) или не будет сброшен вручную.
- Проверка поискового эндпоинта при регистрации источника
  (`SourceRegistrationService.probe_search_endpoint`,
  `sources.py:329-363`) использует отдельный проубер
  (`_default_prober()`, тоже голый `urllib`+POST) и не видит
  классификацию вовсе.

## Goals / Non-Goals

**Goals:**

- Перебор поисковых параметров должен получать содержательный ответ от
  источников с известной антибот/SPA-защитой, а не всегда пустой ответ.
- Стоимость перебора (число дорогих fetch-запросов) должна расти только
  для источников, которым это действительно нужно, и оставаться
  ограниченной даже для них.
- Уже закэшированный неудачный fallback не должен блокировать повторную
  попытку после того, как fetch-транспорт исправлен.
- Устранить расхождение между двумя независимыми прогонами перебора на
  одну задачу.

**Non-Goals:**

- Не меняем саму лестницу деградации (`AgenticOrchestrator`) и её пороги —
  переиспользуем как есть.
- Не добавляем ручной реестр `query=` для конкретных доменов
  (`_SEARCH_URL_TEMPLATES`) как основной механизм — это точечный костыль,
  не масштабируется на новые антибот-источники. Остаётся доступным как
  ручной оверрайд, но не является целью этого изменения.
- Не меняем бизнес-логику выбора самого поискового параметра (цепочка
  `_DEFAULT_PARAM_CHAIN`, причинная проверка через `_looks_unfiltered`) —
  она уже корректна, проблема только в том, что до неё не доходит
  контент.

## Decisions

### Эскалация fetch по классификации, а не замена транспорта

`SearchUrlProber.probe()`/`probe_async()` принимают опциональный параметр
`classification: SourceClassification | None`. Если
`classification.has_antibot`, `classification.is_spa` или
`classification.recommended_strategy` требует деградации сильнее FAST —
`fetch` для этого конкретного вызова оборачивается в вызов
`AgenticOrchestrator.fetch_with_degradation(url,
classification=classification)` вместо переданного/дефолтного лёгкого
fetch. Источники без такой классификации продолжают использовать
`_default_probe_fetch`, поведение и стоимость для них не меняются.

Альтернатива — всегда использовать `fetch_with_degradation` — отвергнута:
для источников без защиты это замедлило бы и удорожило бы каждый прогон
без всякой пользы (у большинства источников `recommended_strategy=FAST`,
голый HTTP и так работает).

### Сужение перебора для эскалированного fetch

Когда используется деградационный fetch, порядок и глубина перебора
меняются: сначала `prefer_param` (подсказка источника, если есть), затем
не более 2 словарных параметров (`q`, `query`) — вместо полных 7 + форма +
5 реформулировок. Причинная проверка (`_looks_unfiltered` против базовой
ленты) остаётся без изменений — она уже единожды кэширует `baseline_urls`
на весь `probe()`, так что лишних fetch не добавляет.

Если ни один из приоритетных кандидатов не прошёл проверку — перебор
завершается без победителя (как и сейчас), fallback на шаблон остаётся
крайним случаем, а не первым, что происходит для каждого антибот-
источника.

Альтернатива — оставить полный перебор (7+1+5) с деградационным fetch на
каждый кандидат — отвергнута: до ~13 браузерных запросов на одну задачу
сбора неприемлемо дорого и медленно, особенно при повторении для каждого
конкурента на источнике.

### Fallback с `confidence=0.0` не считается подтверждённым результатом

`_get_or_probe_url` при чтении из кэша (`runner/probing.py:186-203`)
проверяет `cached.confidence`: запись с `confidence == 0.0` (fallback,
не найденный перебором вариант) считается неподтверждённой и не
блокирует повторную попытку перебора — в отличие от записи с
`confidence > 0.0` (реально найденный и провалидированный вариант),
которая продолжает использоваться из кэша как раньше. Это делает
починку транспорта самовосстанавливающейся: не нужно вручную чистить
Redis после деплоя, старые fallback-записи сами перепробуются на
следующий боевой запуск.

Альтернатива — снижать TTL для fallback-записей — отвергнута: TTL всё
равно требует ждать до 7 дней или ручного вмешательства; проверка
`confidence` при чтении решает проблему сразу.

### Регистрация источника переиспользует ту же эскалацию

`SourceRegistrationService.probe_search_endpoint` получает классификацию
источника (уже вычисляется на шаге `classify()` внутри `register()`) и
передаёт её в `prober.probe_async(...)` тем же способом, что и
`AdaptiveRunner`. Общий выбор fetch-транспорта по классификации живёт в
одном месте (внутри `SearchUrlProber`), обе вызывающие стороны просто
передают свою резолвленную классификацию.

### Устранение дублирующего прогона перебора

Прямой вызов `self._prober.probe(...)` в `_execute_parsing_task`
(`runner/core.py:423-460`) удаляется. Вместо него `matched_variant`
берётся из результата `_get_or_probe_url` (единственного источника
истины для URL парсинга) — `_get_or_probe_url` должен дополнительно
возвращать `matched_variant` победившей попытки (сейчас отбрасывается,
видна только через `ProbePlan`, не через `ProbedUrl`). Расширяем
`ProbedUrl` полем `matched_variant: str | None`, чтобы это состояние не
терялось на пути через кэш.

## Risks / Trade-offs

- [Деградационный fetch медленнее и может занимать секунды на кандидат] →
  сужение перебора для эскалированной ветки ограничивает худший случай
  тремя fetch вместо тринадцати.
- [`fetch_with_degradation` может сам по себе быть недоступен/упасть в
  контексте пробинга, где раньше был только простой HTTP] → как и
  сейчас, ошибки одного кандидата не прерывают весь `probe()` — попытка
  помечается неудачной, перебор идёт к следующему кандидату.
- [Снятие проверки `confidence` при чтении кэша увеличивает число
  повторных проб для источников, которые *реально* ничего не находят
  (не из-за транспорта, а потому что конкурента там нет)] → повторная
  проба не более 3 попыток за прогон — то же ограничение, что и для
  первого прогона, лишней нагрузки не создаёт.
- [Расширение схемы `ProbedUrl` полем `matched_variant`] → поле
  опциональное, старые закэшированные записи без него читаются как
  `None` (как сейчас `matched_variant` вычисляется заново из HTML при
  отсутствии), обратная совместимость сохраняется.

## Migration Plan

1. Выкатить код изменений (без миграций БД/Redis — расширение схемы
   `ProbedUrl` обратно совместимо, старые записи дочитываются с
   `matched_variant=None`).
2. Ничего специально чистить в Redis не требуется — записи с
   `confidence=0.0` перестают быть «залипающими» сами по себе после
   деплоя фикса (см. решение выше).
3. Прогнать контролируемый сбор по rbc.ru × «Сбербанк» (то же, что
   проверялось вручную при диагностике) — убедиться, что перебор находит
   `query=` и выдача действительно фильтруется по конкуренту.
4. При откате — предыдущий образ продолжает работать с теми же
   закэшированными записями (поле `matched_variant` в `ProbedUrl`
   игнорируется старым кодом, не ломает десериализацию).
