## Purpose

Предоставляет фронтенду защищённый HTTP-контракт для запуска pipeline, просмотра его истории и управления эффективным расписанием без ожидания выполнения этапов.

## ADDED Requirements

### Requirement: API запускает полный конвейер и отдельный этап
API SHALL принимать запуск всего pipeline через `POST /pipeline/runs` и отдельного BP1—BP7 через `POST /pipeline/stages/{stage}/runs`. Успешно принятый запрос SHALL отвечать HTTP 202 и представлением созданного прогона.

#### Scenario: Запуск всего pipeline
- **WHEN** авторизованный пользователь с правом управления отправляет корректный `POST /pipeline/runs`
- **THEN** API отвечает 202 с `run_id`, типом полного прогона и статусом `queued`

#### Scenario: Запуск отдельного этапа с параметрами
- **WHEN** авторизованный пользователь отправляет `POST /pipeline/stages/2/runs` с поддерживаемым параметром пересборки
- **THEN** API отвечает 202, а сохранённый прогон относится только к BP2 и содержит переданный параметр

#### Scenario: Неизвестный этап
- **WHEN** клиент запрашивает номер этапа вне диапазона BP1—BP7
- **THEN** API отвечает ошибкой валидации и не создаёт прогон

#### Scenario: Pipeline уже занят
- **WHEN** клиент запрашивает запуск при наличии активного прогона
- **THEN** API отвечает HTTP 409 с идентификатором активного прогона и не ставит новую задачу в очередь

### Requirement: API предоставляет историю и состояние прогонов
API SHALL предоставлять список прогонов через `GET /pipeline/runs` и подробности прогона с этапами через `GET /pipeline/runs/{run_id}`. Ответы SHALL отражать постоянное состояние, а не требовать доступности result backend Celery.

#### Scenario: Получение списка прогонов
- **WHEN** авторизованный пользователь запрашивает историю с параметрами пагинации
- **THEN** API возвращает прогоны от новых к старым с источником, типом, статусом и временными отметками

#### Scenario: Получение подробностей полного прогона
- **WHEN** пользователь запрашивает существующий `run_id` полного pipeline
- **THEN** API возвращает общий статус и упорядоченные записи BP1—BP7 с результатами или понятными ошибками

#### Scenario: Прогон не найден
- **WHEN** пользователь запрашивает неизвестный `run_id`
- **THEN** API отвечает HTTP 404

### Requirement: API читает и изменяет эффективное расписание
API SHALL возвращать эффективные `enabled`, cron-выражение и часовой пояс, источник каждого значения (`env` или `admin`), время следующего запуска и данные последнего обработанного слота через `GET /pipeline/schedule`. API SHALL позволять пользователю с правом управления устанавливать или сбрасывать runtime override через `PATCH /pipeline/schedule`.

#### Scenario: Используются значения из env
- **WHEN** runtime override отсутствует
- **THEN** GET возвращает эффективные значения из `.env`, источник `env` и рассчитанное время следующего запуска

#### Scenario: Расписание изменено без перезапуска
- **WHEN** пользователь с правом управления отправляет валидные новые значения расписания
- **THEN** API сохраняет override и последующий GET возвращает его как эффективное значение с источником `admin`

#### Scenario: Override сброшен
- **WHEN** пользователь запрашивает сброс runtime override
- **THEN** сохранённый override удаляется, а эффективное расписание снова наследуется из `.env`

#### Scenario: Невалидное расписание отклонено
- **WHEN** PATCH содержит невалидное cron-выражение или часовой пояс
- **THEN** API отвечает ошибкой валидации и сохраняет прежнее эффективное расписание

### Requirement: Операции pipeline защищены ролями
Просмотр расписания и прогонов SHALL быть доступен авторизованным ролям чтения, а запуск и изменение расписания SHALL быть доступны только ролям, которым разрешено управление pipeline.

#### Scenario: Пользователь только для чтения
- **WHEN** пользователь с правом просмотра читает историю или расписание
- **THEN** запрос выполняется успешно

#### Scenario: Пользователь только для чтения изменяет pipeline
- **WHEN** тот же пользователь запускает прогон или изменяет расписание
- **THEN** API отвечает HTTP 403 и состояние системы не меняется
