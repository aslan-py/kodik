## Context

См. proposal.md — Why. Здесь — устройство текущей маршрутизации и то, что в нём мешает.

Как события теряются сегодня (`src/bp5/pipeline.py::sync_alerts`):

```
для каждого события витрины:
    matched_type_id = detect_event_type(title, event_types)
    если matched_type_id is None:  →  continue      ← событие П1 выпадает целиком
    rules = routing_rules[(matched_type_id, priority)]
    если правил нет:               →  continue
    собрать строки алерта
```

Ограничения в БД, которые задевает изменение:

```
routing_rule:  event_type_id NOT NULL
               UNIQUE (event_type_id, priority, channel_id, user_id)
alert:         event_type_id NOT NULL
               UNIQUE (showcase_event_id, channel_id, user_id)
```

Правила загружаются один раз на прогон и группируются по ключу `(event_type_id, priority)` — `Bp5Crud.load_routing_rules`.

## Goals / Non-Goals

**Goals:**
- Выразить базовое требование ТЗ: «слать все события такого-то приоритета» — без обязательной привязки к ключевым словам.
- Сохранить существующее поведение правил с указанным типом без изменений.

**Non-Goals:**
- Не меняем детекцию типа по ключевым словам — она остаётся как есть и продолжает работать.
- Не меняем доставку (каналы, песочница, режимы `instant`/`digest`).
- Не вводим правила по другим признакам (категория, конкурент, регион) — только приоритет.

## Decisions

**Отсутствие типа в правиле означает «любой тип», а не отдельный вид правила.** Реализуется необязательным полем: пусто — правило применяется к событию нужного приоритета независимо от заголовка. _Альтернатива —_ завести служебную запись в справочнике типов вроде «любое событие» с пустым списком ключевых слов: отвергнута, это данные, изображающие логику; такую запись видно в админке наравне с настоящими типами, её можно случайно отредактировать или деактивировать, и смысл её неочевиден.

**Правила ищутся в два прохода: сначала по типу, затем по одному приоритету.** Группировка правил при загрузке становится двухуровневой: ключ `(тип, приоритет)` для типовых правил и ключ `приоритет` для правил без типа. Событие сначала пытается сматчиться по типу (поведение как сегодня), затем к результату добавляются правила, заданные только приоритетом. Событие без распознанного типа проходит только второй проход. _Альтернатива —_ один проход с `тип IS NULL OR тип = найденный`: отвергнута, потребовала бы либо запроса в БД на каждое событие, либо более запутанной структуры в памяти; сейчас справочники грузятся один раз на прогон, и это свойство хочется сохранить.

**Наложение правил разрешается до записи в журнал, а не ограничением уникальности.** Если на событие сработали и типовое правило, и правило по приоритету с тем же получателем и каналом, до вставки остаётся одна строка. Полагаться на существующий `UNIQUE (showcase_event_id, channel_id, user_id)` нельзя: он схлопнет дубль молча, но какая из двух строк уцелеет — определяется порядком в пачке, а от этого зависит записанный в журнал тип события. Приоритет отдаётся типовому правилу: оно точнее описывает, почему сработал алерт. _Альтернатива —_ слать обе доставки: отвергнута, это два одинаковых письма одному человеку по одному событию.

**Тип в журнале алертов становится необязательным.** Алерт, созданный правилом без типа при нераспознанном типе события, писать не с чем — а подставлять произвольный тип значило бы записать в историю неправду. Пустое значение читается однозначно: «сработало правило по приоритету, тип не распознан». Если тип распознан, он записывается даже когда сработало правило без типа — это бесплатная и полезная информация.

**Ограничение уникальности правила пересматривается с учётом поведения `NULL` в Postgres.** Обычный `UNIQUE` не считает две строки с `NULL` в одной колонке дубликатами, поэтому после снятия NOT NULL текущее ограничение перестанет ловить дубли среди правил без типа. Лечится частичным уникальным индексом для случая «тип не задан» — приём в проекте уже применён (`uq_search_task_no_trigger` в `src/bp1/models.py`), заводить новый подход не требуется.

## Risks / Trade-offs

- [Риск] **Правило по приоритету создаёт заметно больше алертов, чем ожидает заполняющий.** Одна строка «П1 → email» превращает каждое событие П1 в письмо, тогда как типовое правило отсекало большинство. При переходе на реальный сбор объём П1 заранее неизвестен. → Митигация: возможность добавляется, но в демо-справочники по умолчанию не заводится; в README отмечается, что правило без типа — самое широкое из возможных.
- [Риск] **Пустой тип в правиле можно принять за незаполненное поле.** В админке пустая ячейка выглядит как забытая, а не как осмысленное «любой тип». → Митигация: подпись поля и подсказка в админке должны явно говорить, что пусто означает «любой тип события»; проверить, как это отображается в списке правил.
- [Риск] **Событие может получить алерт по приоритету раньше, чем аналитик заведёт для него точный тип.** Это меняет смысл журнала: раньше запись в нём означала «распознан значимый тип», теперь — ещё и «подошёл по приоритету». → Митигация: пустой тип в журнале как раз и позволяет отличить одно от другого при разборе.
- [Компромисс] **Порог значимости перестаёт быть единственным механизмом.** Раньше ответ на вопрос «почему сработал алерт» был один — нашёлся тип. Теперь их два. Это цена за выразимость требования ТЗ; оба механизма живут в одном справочнике и видны в одном списке.

## Migration Plan

Миграция снимает NOT NULL с двух полей и заменяет ограничение уникальности правил на пару «обычное ограничение + частичный индекс для случая без типа». Существующие строки не меняются: у всех тип заполнен, поведение сохраняется. Откат — обратная миграция; она выполнима, только если к тому моменту не заведено ни одного правила без типа и ни одного алерта без типа, что для отката сразу после выкатки верно.
