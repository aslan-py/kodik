## Context

BP-3 влит из отдельной ветки коллеги и сейчас не запускается (см. proposal.md — Why). Проект уже придерживается паттерна «один `pipeline.py` на BP с `run_bpN()` + свой `if __name__ == '__main__'`» для BP-2/4/5; BP-3 исторически выбивался — у него был отдельный корневой `main.py` с собственным (уже разошедшимся) списком модулей. BP-3 сознательно остаётся синхронным (не async) — см. [[bp3-bp6-coordination]], поэтому у него не может быть общего с остальным проектом `AsyncSessionLocal`.

## Goals / Non-Goals

**Goals:**
- Сделать `run_bp3()` (реальную точку входа админки/CLI) источником истины по списку модулей BP-3.
- Убрать корневой `main.py`, свести ручную отладку к `python -m src.bp3.pipeline` — как у BP-2.
- Убрать дублирование ручной sync-сборки БД-подключения между `fetch_data.py` и `save_results_module.py`.

**Non-Goals:**
- Не переводим BP-3 на async — вне рамок этого изменения и вне текущей договорённости с коллегой.
- Не трогаем заглушки этапов 1 и 6 — отдельные changes.
- Не чиним `UNIQUE` на `source_candidate.domain` — известная мелочь, не блокер, отдельная задача при желании.

## Decisions

**Единая точка входа — `src/bp3/pipeline.py`, не корневой `main.py`.** Обоснование: у BP-2/4/5 уже есть этот паттерн (`run_bpN()` + `if __name__ == '__main__'` внутри `pipeline.py`), `core/pipeline/cli.py`/`registry.py` — уже существующий единый оркестратор ВСЕХ 7 этапов (preflight, reparse, сводка), а не просто «ручной запуск». Держать параллельно ещё и корневой `main.py` означало бы второй, независимо поддерживаемый список модулей — именно это и стало причиной текущего рассинхрона (`ExpectedResultModule` есть в одном месте и нет в другом). Альтернатива (оставить `main.py` как «главную» точку входа проекта, а `run_bp3()` звать из него) отвергнута — она меняла бы порядок зависимости в обратную сторону: `core/pipeline/registry.py` и так уже вызывает `run_bp3()` напрямую, переносить логику в `main.py` пришлось бы обратно импортировать оттуда, что создаёт цикл понятий «где правда».

**Общий `src/bp3/db.py` вместо копипаста `DATABASE_URL`/`engine`/`Session`.** Оба места (`fetch_data.py`, `save_results_module.py`) собирают синхронный `create_engine`/`sessionmaker` идентичным кодом. `core/database.py` даёт только async — переиспользовать нечего, поэтому заводим один модуль `src/bp3/db.py` с `engine`/`Session`, оба файла импортируют из него. Это не меняет поведения, чисто устраняет дублирование.

**Порядок правок внутри `save_results_module.py`.** Блок сохранения `source_candidate` перемещается на уровень цикла `for news_id, fields in data_by_id.items()` — то есть выполняется ОДИН раз после этого цикла (не внутри него), иначе при N категоризированных новостях в одном прогоне каждый найденный домен вставился бы в `source_candidate` N раз.

## Risks / Trade-offs

- [Риск] Метрика `domains_found` в сводке `run_bp3()` меняет смысл (было — число ключей словаря = число конкурентов, станет — суммарное число найденных доменов) → Митигация: это приведение к изначальному смыслу метрики (проверено при разборе «почему domains_found: 5»), не новая путаница, а исправление существующей; отдельно нигде не потребляется программно (только выводится в сводку).
- [Риск] Удаление `main.py` — операция необратимая одним git-действием, если кто-то ссылался на него в документации/скриптах → Митигация: проверить перед удалением, что ничего в проекте (README, CI, скрипты) не ссылается на `python main.py`.
