## Why

Этап 1 конвейера сейчас существует только в виде заглушки: реестр (`core/pipeline/registry.py`) заводит на него `core/scripts/stages/bp1_stub`, который заливает 6 синтетических новостей. Настоящий сбор данных (`src/bp1/adaptive/`, ~250 КБ кода с 15 файлами тестов) в проект уже влит, но к конвейеру не подключён — его нельзя запустить ни кнопкой в админке, ни через `core/pipeline/cli.py`, ни по расписанию Celery.

Просто заменить заглушку реальным парсингом нельзя: весь тестовый контур проекта (`simple_dictionaries` + `bp1_stub`) спроектирован под предсказуемые синтетические заголовки — стоп-слово «промокод», чёрный домен `compromat-test.ru`, антишум по `shared-site-test.ru`, ключевое слово «прокуратура» для алертинга. Реальные новости этот контур обнуляют, а он нужен для дешёвой проверки этапов 2-7 без расхода токенов LLM и внешних лимитов. Обе реализации должны сосуществовать с явным переключателем.

## What Changes

- **Новый `src/bp1/pipeline.py`** с `run_bp1()` — точка входа этапа 1 по образцу остальных этапов (`src/bp2/pipeline.py`…`src/bp7/pipeline.py`): открывает сессию и Redis-клиент, вызывает `AdaptiveRunner.run_all()`, возвращает сводку прогона. Сегодня BP-1 — единственный из семи без своего `pipeline.py`.
- **Настройка `TRUE_PARSING`** (`.env`, `.env.example`, `core/config.py`) — выбирает реализацию этапа 1: `False` (по умолчанию) — заглушка, `True` — реальный сбор. По образцу уже существующего `TRUE_ALERTING`, который так же выбирает поведение, а не включает/выключает этап.
- **`core/pipeline/registry.py`**: у этапа 1 появляется вторая точка входа (заглушка) рядом с основной (реальный сбор) — по образцу уже имеющегося `run_reparse` у этапа 2. Признак `is_stub` перестаёт быть константой `True` и отражает реально выполненную реализацию, иначе сводка прогона врёт при `TRUE_PARSING=True`.
- **`core/pipeline/runner.py`**: `run_stage(1)` выбирает реализацию по настройке с возможностью разового переопределения; preflight этапа 1 в реальном режиме требует хотя бы одну активную задачу сбора (`search_task`), в режиме заглушки — не требует (заглушка создаёт задачу сама).
- **`core/pipeline/cli.py`**: аргумент для разового переопределения режима (по образцу `reparse` у этапа 2).
- **Админка** (`api/admin/pipeline_control.py`): у кнопки этапа 1 — переключатель выбора реализации, по образцу переключателя «пересобрать» у этапа 2.
- **BREAKING (поведение заглушки)**: `bp1_stub.clear()` перестаёт сносить таблицу `search_task` целиком. Сейчас он вызывает `clear_from(session, SearchTask)`, что удаляет ВСЕ задачи сбора — включая заведённые аналитиком вручную через админку (`SearchTaskAdmin`) или API. С подключением реального сбора это превращается в потерю боевой конфигурации при случайном запуске заглушки. Заглушка должна чистить только созданное ею самой.
- **`core/scripts/SCRIPTS_README.md`**: как запустить реальный сбор и чем он отличается от двух существующих сидеров этапа 1.

## Capabilities

### New Capabilities
- `bp1/adaptive-collection-run`: реальный прогон сбора данных — читает активные задачи сбора, обходит источники адаптивным парсером, пишет снимки в `raw_item` с дедупликацией.

### Modified Capabilities
- `bp1/minimal-pipeline-stub`: заглушка перестаёт быть единственной реализацией этапа 1 и перестаёт удалять задачи сбора, созданные не ею.
- `core/pipeline-stage-runner`: этап 1 выбирает реализацию (реальный сбор / заглушка) по настройке приложения с возможностью разового переопределения; предусловия этапа 1 зависят от выбранной реализации.
- `admin/pipeline-control`: переключатель режима у этапа появляется не только для пересборки, но и для выбора реализации этапа 1.

## Impact

- Код: новый `src/bp1/pipeline.py`; правки в `core/config.py`, `core/pipeline/registry.py`, `core/pipeline/runner.py`, `core/pipeline/cli.py`, `api/admin/pipeline_control.py`, `core/scripts/stages/bp1_stub.py`, `core/scripts/SCRIPTS_README.md`.
- Конфигурация: новая переменная `TRUE_PARSING` в `.env` и `.env.example`.
- БД: миграций нет — используются существующие таблицы. Меняется только объём удаляемого при очистке заглушки.
- Внешние зависимости: реальный режим требует работающего Redis (дедупликация снимков, кэш профилей источников) и сетевого доступа к источникам; заглушка не требует ни того, ни другого.
- Не входит в эту задачу: чистка мёртвого кода BP-1 и перевод `os.getenv` на `settings` внутри `adaptive/` (отдельная задача), наведение порядка в `.env` (отдельная задача).
