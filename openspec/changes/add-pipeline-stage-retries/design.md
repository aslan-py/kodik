## Context

См. `proposal.md` — «Почему». Сейчас `PipelineStageRun` уже хранит число
попыток и результат этапа, а задачи BP-1--BP-7 выполняются последовательно в
Celery-цепочке. Общие настройки Celery содержат максимум повторов и параметры
задержки, но задачи-обёртки не вызывают механизм повтора Celery. Поэтому
временный сбой записывается как окончательная ошибка.

Повтор должен быть наблюдаемым через уже существующие историю прогона и
админ-панель, не допускать параллельного запуска того же прогона и не создавать
новых контейнеров.

## Goals / Non-Goals

**Goals:**

- Дать каждому этапу BP-1--BP-7 одинаковый ограниченный автоматический повтор
  при временном инфраструктурном сбое.
- Сделать значение `CELERY_TASK_MAX_RETRIES` однозначным: это число
  *дополнительных* попыток; при значении `3` всего возможно четыре запуска.
- Сделать ход повторов и их окончательный исход понятными из API и админки.
- Исключить переход к следующему этапу, пока текущий ожидает повтор.

**Non-Goals:**

- Повторять ошибки данных, предусловий или бизнес-правил.
- Автоматически повторять вручную отменённые прогоны либо запускать новый
  прогон поверх активного.
- Давать гарантию exactly-once для внешней системы, которая сама не поддерживает
  идемпотентность; вместо этого защищать собственную запись прогона и
  документировать требование идемпотентного этапа.
- Менять cron-расписание, число worker'ов или добавлять отдельный сервис для
  ретраев.

## Decisions

### Явная классификация повторяемых ошибок

В `core.pipeline.errors` будет введён отдельный базовый тип временной ошибки
конвейера и узкие подклассы для доступности сети/внешнего сервиса. Обёртка
этапа будет переводить в этот тип только известные временные исключения внешних
клиентов; `SoftTimeLimitExceeded` также относится к повторяемым сбоям.
`PipelinePreconditionError`, `PipelineBusinessError` и ошибки валидации будут
завершаться сразу. Неизвестное исключение также не будет повторяться: это
безопаснее, чем скрывать программную ошибку несколькими попытками.

Альтернатива — повторять любое исключение — отклонена: она способна множить
неисправные операции и задерживать диагностику ошибок кода.

### Celery управляет задержкой, БД хранит состояние

Задачи-обёртки будут bound-задачами и при повторяемой ошибке вызовут штатный
`self.retry`. Номер повторов берётся из контекста Celery; обратный отсчёт
вычисляется как `min(начальная_задержка * 2^номер_повтора, максимум_backoff)`.
При начальной задержке 60 секунд, максимуме 600 секунд и трёх дополнительных
попытках последовательность ожиданий составит 60, 120 и 240 секунд.

Перед вызовом `self.retry` в транзакции обновляется запись этапа: новый статус
`retrying`, число уже выполненных запусков, последняя ошибка и `next_retry_at`.
При новом запуске той же Celery-задачи статус переводится в `running`; при
успехе или исчерпании лимита — в конечный статус. Так Celery остаётся
исполнителем отложенной задачи, а БД — источником данных для API и
восстановления наблюдаемости.

Альтернатива — самостоятельно создавать новую задачу через `apply_async` —
отклонена: он усложняет подсчёт попыток, связь задач и защиту от дублей.

### Активный слот сохраняется до окончательного результата

Прогон с этапом `retrying` остаётся `running`; финализатор цепочки не получит
результат этого этапа до успешного выполнения или окончательного исчерпания
попыток. Проверка запуска по расписанию продолжит отвергать новый прогон, пока
есть активный. После окончательной ошибки текущая семантика конвейера
сохраняется: последующие этапы получают результат-ошибку предыдущего этапа и
могут отработать по своим правилам, а финализатор ставит `partial_failed`.

Задача, убитая жёстким лимитом или потерей worker'а, не может надёжно выполнить
код обработки в своём процессе. Для неё будет использован имеющийся механизм
поиска устаревших активных прогонов: он помечает такой прогон конечным, а не
имитирует небезопасный повтор. Это намеренное ограничение первой версии.

### Идемпотентность и защита от двойного выполнения

Перед запуском обёртка будет блокировать строку `PipelineStageRun` и принимать
к исполнению только ожидаемую попытку. Повторно доставленная уже завершённая
задача возвращает сохранённый исход без повторного вызова бизнес-этапа. Каждый
этап обязан сохранять собственные результаты идемпотентно; для обращений к
внешним сервисам, где это возможно, используется стабильный ключ прогона и
этапа. Последняя ошибка и история номеров попыток сохраняются до финального
результата, а не затираются следующим запуском.

Альтернатива — полагаться только на `task_id` Celery — отклонена, поскольку
задача после `retry` меняет фактическое исполнение, а процесс может быть
доставлен повторно.

### Миграция и контракт API

В перечисление статусов этапа добавляется `retrying`; в `PipelineStageRun`
добавляется nullable-поле времени следующей попытки. Схемы истории и UI
получают статус, `attempts`, максимальное число всех попыток, последнюю ошибку
и `next_retry_at`. Конечные этапы возвращают `next_retry_at = null`.

Это расширение обратно совместимо: существующие клиенты продолжают читать
прежние поля, а новые поля являются дополнительными.

## Risks / Trade-offs

- [Внешняя операция успела выполниться перед таймаутом, но ответ не получен] →
  собственная БД защищается блокировкой и идемпотентностью; интеграциям передаётся
  стабильный ключ, где они его поддерживают.
- [Повторяемая ошибка определена слишком широко] → повторяются только явные
  типы и `SoftTimeLimitExceeded`; неизвестные исключения остаются конечными.
- [Worker погиб после сохранения `retrying`, но до публикации повтора] →
  механизм поиска устаревших прогонов делает результат наблюдаемым и освобождает
  слот; восстановление пропавшей публикации не входит в эту версию.
- [В PostgreSQL требуется миграция enum] → миграция добавляет значение статуса
  безопасно для уже существующих строк и разворачивается до выпуска worker'ов.

## Migration Plan

1. Добавить миграцию статуса и времени следующей попытки, затем применить её.
2. Развернуть API и worker'ы с новой логикой одновременно; сначала оставить
   расписание выключенным или использовать ручной одиночный запуск.
3. Проверить в Flower и истории прогона тестовый временный сбой, успех повтора
   и исчерпание лимита.
4. При откате сначала остановить worker'ы новой версии, затем вернуть код; новые
   строки `retrying` перевести штатной очисткой устаревших прогонов в конечный
   статус. Значение enum в PostgreSQL можно безопасно оставить: оно не мешает
   предыдущей версии кода.
